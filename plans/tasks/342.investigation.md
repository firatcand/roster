# Investigation: #342 Opus release blockers

Date: 2026-08-01

## Reproduction 1 — create-only comparison misreports larger existing files

1. Create a regular workspace file whose bytes are longer than a proposed create-only payload.
2. Call `publishCreateOnly(root, path, shorterPayload)`.
3. Observe `READ_LIMIT_EXCEEDED` and the remedy to reduce the existing file instead of the ratified `WRITE_CONFLICT` adopt-or-refuse result.
4. The same path is reachable when `withWorkspaceLock` republishes the seven-byte `.roster/.gitignore`, and when `roster init` compares an existing longer `ROSTER.md` with newly rendered bytes.

### Hypothesis tested

The EEXIST comparison is bounded by the proposed payload length, so the bounded reader rejects a larger existing file before the exact-byte comparison can run.

### Root cause

Confirmed at `src/lib/workspace-io.ts`: the EEXIST branch calls `readAnchoredWorkspaceFile(..., Math.max(bytes.byteLength, 1))`. This bound describes the new payload, not the unknown existing file. The initial stat therefore raises `READ_LIMIT_EXCEEDED` whenever the existing file is larger.

### Fix approach

Use `MAX_WORKSPACE_FILE_BYTES` for the EEXIST comparison read. Retain payload-sized reads only after publication/adoption where equality has already established the expected size. Add regressions using the real `ROSTER.md` and `.roster/.gitignore` paths, proving larger pre-existing bytes yield `WRITE_CONFLICT` and remain byte-identical.

## Reproduction 2 — v2 workspace becomes unsafe when legacy scan reaches its budget

1. Create a healthy v2 workspace with regular `roster.yaml` and `ROSTER.md`.
2. Add a non-skipped top-level directory containing more than 1,024 regular entries.
3. Call `probeWorkspace` or a read-only v2 command such as discover/validate.
4. Observe `v2Signals: ['roster.yaml']`, an unsafe `probe-directory-entry-limit-exceeded` signal, and final kind `unsafe` / `UNSAFE_WORKSPACE_MARKER`.

### Hypothesis tested

The bounded legacy detector records capacity exhaustion in the same collection as unsafe filesystem types, and the final classifier lets any unsafe signal override a positive v2 sentinel.

### Root cause

Confirmed at `src/lib/workspace-probe.ts`: `boundedEntries` appends directory/total budget exhaustion to `unsafeSignals`, while final classification always prioritizes non-empty unsafe signals over `v2Signals`. Capacity exhaustion is not an unsafe marker and should not invalidate an already-identified v2 workspace.

### Fix approach

Track traversal-budget exhaustion separately from unsafe filesystem signals. Preserve fail-closed refusal for an uninitialized/no-sentinel directory where the legacy scan is inconclusive. When a regular `roster.yaml` positively identifies v2, return kind `v2` (or `mixed` if actual legacy markers are found) and expose the bounded-scan diagnostic without classifying it as unsafe. Add regressions for both the healthy-v2 large-directory case and the no-sentinel fail-closed case.

## Reproduction 3 — incidental legacy-scan findings override a positive v2 sentinel

1. Initialize a healthy v2 workspace with a regular `roster.yaml`.
2. Add an entry that is relevant only to heuristic legacy discovery, such as a symlink at `scripts/new-agent.sh`, a regular file at `company/projects`, or an unrelated directory that the bounded scan cannot inspect.
3. Call `probeWorkspace`, `discoverWorkspace`, or `validateWorkspace`.
4. Observe the positive `v2Signals: ['roster.yaml']` together with an incidental legacy-scan entry in `unsafeSignals`, final kind `unsafe`, and `UNSAFE_WORKSPACE_MARKER` from every v2 entry point.

### Hypothesis tested

Legacy discovery passes all filesystem anomalies into the same collection used for concrete type violations on canonical Roster markers. Final classification therefore cannot distinguish a compromised Roster contract from uncertainty in an optional heuristic scan.

### Root cause

Confirmed at `src/lib/workspace-probe.ts`: `detectV04Signals`, candidate-directory inspection, and `legacySignatureSignals` append incidental scan failures to `unsafeSignals`. Final classification lets any unsafe entry override a regular `roster.yaml`, even though the ratified unsafe boundary covers canonical markers rather than arbitrary repository paths.

### Fix approach

Reserve `unsafeSignals` for concrete failures on the workspace root and canonical Roster markers: `roster.yaml`, `ROSTER.md`, `config/project.yaml`, and `.roster/scaffold-manifest.json`. Route uncertainty and type mismatches encountered only while heuristically detecting legacy layouts or signatures through `inconclusiveSignals`. A positive regular `roster.yaml` may proceed and exposes those diagnostics; without the sentinel, the same inconclusive observations remain fail-closed through the final probe result. Preserve actual legacy signature hits and `projects/` directory hits so a v2 workspace with real legacy content remains `mixed`. Init must likewise revalidate heuristic candidate identity tokens only for the no-sentinel path; it always revalidates the workspace root, but optional legacy candidates must not reintroduce a v2 lockout after classification. Add regressions for each reproduced incidental path, the no-sentinel boundary, canonical-marker safety, and v2 init under unrelated candidate churn.

## CI reproduction — integration harness invokes removed v1 init grammar

1. Open PR #374 and run the GitHub Actions `verify` job.
2. Observe the production unit, package, and smoke gates complete before `pnpm e2e:schedule` exits at workspace bootstrap.
3. The packaged CLI reports `unsupported init flag '--no-git'` and documents the supported sparse grammar.

### Root cause

`test/e2e-schedule.sh` and the non-CI `test/perf.sh` still invoked the removed v1 `--no-git` flag. The schedule E2E also asserted eager v1 artifacts (`CLAUDE.md` and `gtm/`) that sparse v2 init deliberately no longer creates. Product behavior and the CLI regression were correct; the published-package harness had not been migrated with #342.

### Fix approach

Use the supported `roster init <workspace-id> --silent` grammar in both harnesses. In the schedule E2E, assert the sparse contract (`roster.yaml`, `ROSTER.md`, and exactly two root entries) before exercising the independent legacy scheduling path. Preserve every crontab safety and cleanup assertion. Verify `pnpm e2e:schedule`, `pnpm perf`, shell syntax, and diff checks before pushing the CI repair.

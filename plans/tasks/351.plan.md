# Issue #351 implementation plan — stabilize company Brain identity and source lifecycle

## Status and authority

Status: ready for implementation-plan review. There is no owner-approval gate or
unanswered product-boundary question in this plan.

This plan implements live GitHub issue #351 against committed Roster v2 product
authority:

- `spec/BRIEF.md`
- `spec/PRD.md`
- `spec/SPEC.md`
- `spec/CONTEXT.md`
- live issue #351, “Stabilize company Brain identity and source lifecycle”

Issue #350, the sole live dependency, is closed. The accepted contract is:

> One logical Roster workspace owns one PostgreSQL database and one configured
> S3 namespace. The database is the cross-workspace boundary. Function, agent,
> and plan scopes are retrieval labels, not authorization principals.

The superseded shared-database, Brain-space, workspace-binding, per-binding
login, and RLS design is not an implementation option. This task also does not
add `source_state_events` or `source_heads`; the SPEC explicitly gives
`logical_sources` one current-version pointer.

## Outcome

After #351:

1. A tracked, secret-free `roster.yaml` describes one workspace's Brain
   authority: stable `workspace_id`, Infisical path/reference, and normalized
   S3 bucket/region/endpoint/path-style/root-prefix organization.
2. Protected database metadata records the same `workspace_id` and a
   fingerprint of the configured S3 namespace.
3. Every Brain command gates every physical database connection with the
   protected-metadata handshake before company-content reads, S3 access, or
   mutation. The protected database identity is the sole namespace-binding
   authority; #351 does not add an S3 marker or second bootstrap authority.
4. One typed ingestion pipeline derives continuing identity for workspace files
   and fetched media, requires a host stable key for inline text, structured
   records, and produced artifacts, writes immutable content-addressed bytes,
   and transactionally publishes an immutable source version.
5. Durable ingest intent state makes Postgres/S3 partial failures resumable.
   Tombstone/restore lifecycle is retained with a one-time recorded restoration;
   source versions, object records, and version provenance are immutable.
6. Runtime credentials can use only fixed read/write surfaces. They cannot own
   database objects, create or alter schema/tables, mutate protected identity or
   provenance, select a stronger assurance level, or reach admin privileges.
7. Existing entities, aliases, facts, events, edges, merge history, document
   chunks, mount history, file-ledger history, and verifiable S3 bytes remain in
   place with IDs and history preserved.

### Certified context protocol replacement

Removing `brain.binding` is a deliberate breaking `host-context.v2` refreeze,
not a terminology-only edit:

- seeded Brain candidates delete the required `binding` field and use the
  already-required `scope.workspace` as their sole workspace namespace;
- candidate evaluation compares `scope.workspace` with the tracked
  `workspace_id`, replaces `cross-binding` with `workspace-mismatch`, and
  replaces `cross-scope` with `scope-ineligible` for narrower retrieval-label
  mismatch. The workspace comparison is removed from the narrower-scope
  predicate so the two reasons remain mutually exclusive;
- the output `workspace.brain_binding` field becomes
  `workspace.brain_configured: boolean` and the compact adapter tuple becomes
  `brainConfigured`;
- missing tracked config produces one `BRAIN_NOT_CONFIGURED` diagnostic and no
  evidence candidates; wrong DB/namespace remains a fatal command handshake,
  never a candidate exclusion; and
- `BRAIN_NOT_BOUND` is retired completely from current code, generated
  artifacts, fixtures, tests, and active docs; and
- all strict key sets, ordered exclusion enums, compact legends, generated
  adapters, certification fixtures, canonical bytes, hashes, and budgeting
  expectations are regenerated and recertified. No assertion may claim the old
  request/result bytes remain unchanged.

## Target configuration and protected authority

Tracked registry shape:

```yaml
schema_version: 2
workspace_id: my-roster
brain:
  secrets_path: /my-roster
  storage:
    bucket: my-roster-vault
    region: eu-central-1
    root_prefix: brain
    # endpoint: https://s3.example.com
    # force_path_style: false
```

`brain` remains optional. The parser rejects unknown fields, credentials,
database URLs, secret values, URL userinfo/query/fragment, unsafe endpoints,
unsafe bucket values, and root prefixes containing absolute, empty, dot, or
traversal components. Normalization is deterministic across clones.

The namespace fingerprint is SHA-256 over versioned canonical JSON containing
only:

```text
provider=s3
bucket
region
normalized endpoint or the versioned AWS-default sentinel
force_path_style
normalized root_prefix
```

`secrets_path` is not part of storage identity and is never resolved or
printed by Roster. Roster consumes already-injected
`ROSTER_BRAIN_ADMIN_URL`, `ROSTER_BRAIN_URL`, and AWS credentials.

The legacy `brain_meta.config` keys `files.bucket`, `files.region`,
`files.endpoint`, `files.prefix`, and `files.force_path_style` are never read by
v2 runtime code. Fresh initialization has no such rows. Legacy adoption must
compare them with the approved tracked manifest before content access; a
mismatch is a migration conflict. After the verified snapshot/backfill,
migration 011 removes those exact live keys and all public setters while the
snapshot preserves their historical values. No fallback or dual authority
survives.

### Mandatory handshake order

For every non-bootstrap Brain command:

1. Resolve the workspace root and parse the tracked registry.
2. If `brain` is absent, return the existing command-specific
   `BRAIN_NOT_CONFIGURED` behavior before constructing a pool or S3 client.
3. Open a database connection and perform only the protected
   `brain_meta.workspace_identity` query.
4. Require exactly one singleton whose `workspace_id` and namespace
   fingerprint exactly match tracked configuration and whose protected
   `migration_state` is `ready`.
5. Cache success only on that physical client object. Every newly created or
   swapped pooled connection repeats the check before caller-visible SQL.
6. Only then permit company-content SQL.
7. If the operation needs S3, construct a store confined to the already
   fingerprinted bucket/root prefix and only then perform S3 content access or
   mutation.

Mismatch, missing identity, and malformed metadata fail closed with redacted
diagnostics. No fallback chooses a
different database, bucket, prefix, legacy binding, or “default” workspace.

Explicit admin bootstrap/adoption is the only exception. It may inspect
`pg_catalog`, migration metadata, and the protected singleton to prove
eligibility, but it cannot read company tables or S3 content before it has
stamped the exact authority described in a supplied manifest.

### Initialization state

`brain_meta.workspace_identity` is a create-once singleton. Its identity and
namespace columns never update. A clean admin bootstrap validates that the
database is new/empty, applies the locked migrations and final grants, then
inserts the exact workspace/fingerprint with `migration_state=ready`. An
identical replay succeeds without mutation; a different value conflicts.

A nonempty legacy database without identity returns
`BRAIN_LEGACY_ADOPTION_REQUIRED` so #363 can perform the approved migration.
That explicit path inserts the approved immutable identity plus
`migration_state=migrating` and a manifest SHA-256, then may advance only
`migrating → ready` after verified backfill and grant closure. Runtime reads the
minimal projection and blocks while migrating; a different manifest cannot
resume. These two operational columns are the only admin-updatable singleton
fields and are not an alternate namespace authority.

## Source identity and input contracts

All IDs use domain-separated, length-framed UTF-8 inputs and lowercase SHA-256
digests with stable prefixes. Hash inputs are versioned; changing a
canonicalization rule requires a new identity version.

| Kind | Continuing identity | Byte input |
|---|---|---|
| `file` | `workspace_id + normalized workspace-relative POSIX path` | Bounded, component-safe regular-file read. Absolute paths, traversal, symlinks, devices, FIFOs, and sockets fail. |
| `fetched-media` | `workspace_id + canonical provider/origin + upstream stable ID`; canonical HTTPS URL only when no provider ID exists | Bytes already selected and staged by the host/tool. Roster performs no fetch. |
| `inline-text` | `workspace_id + kind + host stable key` | Exact UTF-8 bytes from stdin or a confined staged file. |
| `structured-record` | `workspace_id + kind + host stable key` | Bounded JSON parsed with duplicate/depth/size checks and serialized as canonical JSON bytes. |
| `produced-artifact` | `workspace_id + kind + host stable key` | Exact bounded artifact bytes from stdin or a confined staged file. |

`brain fs` is the one named specialization of `produced-artifact`. Its
host-supplied stable key and continuing origin key are the NFC-normalized,
segment-safe address `<kind>/<slug>/<filename>` under the fixed origin namespace
`roster-fs`; the logical ID frame still includes `workspace_id` and source kind.
Runtime and legacy backfill call the same address canonicalizer. No S3 key,
checkout path, content hash, or mutable bucket configuration enters this
identity.

The stable key is a bounded opaque domain key, not an absolute path, content
hash, random retry token, secret, or whole source body. Kind separation prevents
the same key text from colliding across text, structured records, and artifacts.

IDs:

- `logical_source_id`: deterministic from the canonical identity envelope.
- `object_id`: `sha256:<digest-of-exact-stored-bytes>`.
- `ingest_intent_id`: deterministic from workspace plus the caller's required
  idempotency key; reuse with different canonical request bytes is a conflict.
- `source_version_id`: deterministic from the logical source, object, media
  type, immutable classification, source time, locator, and canonical
  provenance. It excludes retry/idempotency metadata. A deliberate A→B→A
  sequence therefore reuses version/object A while three completed intents and
  source generations preserve all three publish transitions.

The version-ID frame is pinned to these fields, in this order and with a format
version: `logical_source_id`, `object_id`, normalized media type, privacy,
trust class, actor assurance class, scope kind/function/agent/plan tuple,
normalized source timestamp-or-NULL, locator kind/value, and stable origin
provenance. Omitted `--source-time` is NULL, never `now()`. Stable origin
provenance may contain provider/upstream identity, canonical origin URL, or
legacy manifest locator; it may not contain ingestion/verification time,
idempotency key, attempt, run/session ID, transient actor/tool observation, or
row creation time. Those request observations live in the intent and therefore
cannot defeat deterministic version reuse.

Typed retrieval scope is stored as `scope_kind` plus nullable
`function_id`, `agent_id`, and `plan_id` columns with CHECK constraints
for the exact hierarchy. The registry validates referenced components before
ingest. `workspace_id` is implicit in the dedicated database. No scope value
changes database privilege.

Privacy is versioned policy metadata. Trust and actor assurance are derived or
ceiling-checked by the broker: ordinary external bytes are untrusted,
host-submitted assertions are host-asserted/caller-unverified, and migration
rows are `legacy-unverified`. Callers cannot request a stronger class.

### Structured company-knowledge assertions

`source_versions.object_id` is always non-null: PostgreSQL stores structured
knowledge and indexes, while the exact canonical assertion bytes live in the
workspace S3 namespace like every other accepted source kind. The unit is one
semantic broker call, not one fact row:

1. `brain save|event|link|merge` requires a host-supplied `--source-key` and
   `--idempotency-key` in v2.
2. Roster canonicalizes that call's complete bounded structured payload once,
   ingests one `structured-record` source version/object, then writes all rows
   from the call through one fixed database broker citing that version.
3. The source key is a continuing host domain key; Roster never derives it from
   content, slug, actor, time, or the idempotency key. Reusing the source key
   with changed canonical bytes creates a new immutable version.
4. Ordinary host calls are `caller-unverified`; stronger assurance cannot be
   selected by flags. This intentionally adds one conditional S3 put per
   semantic broker call and is the cost of exact source citation. Consequently
   `save|event|link|merge` now require S3 availability: storage failure leaves
   only a resumable prepared intent and performs no structured-knowledge write.
5. Legacy import groups rows only by an explicit deterministic manifest batch,
   stores the exact canonical legacy-row payload as a `structured-record`
   object, and marks it `legacy-unverified`. It never claims that reconstructed
   row JSON is the unavailable original document/source.

## PostgreSQL schema

### Migration 010 — `010_workspace_source_lifecycle.sql`

Create exactly six new tables and no tenancy/RLS wrapper:

1. `brain_meta.workspace_identity`: create-once singleton with `workspace_id`,
   fingerprint format version, S3 namespace fingerprint, initialization time,
   protected `migration_state`, and optional approved manifest digest. The
   singleton/digest/state formats are checked; runtime gets only `SELECT`.
   Identity fields never update; a guarded admin function performs only the
   one-way `migrating → ready` transition.
2. `brain.objects`: immutable exact-byte SHA-256 object identity, generated
   `objects/<first-two>/<digest>` key, size, optional provider version/ETag,
   verification time, and creation time. Media type is version metadata, not
   object identity. Provider observations are insert-time only; if unavailable
   they remain NULL permanently, while later verification belongs to the
   intent/doctor report. Reject `UPDATE` and `DELETE` in addition to grant
   denial.
3. `brain.logical_sources`: deterministic logical-source ID, source kind,
   origin namespace/key, optional display name, `current_version_id`, and a
   monotonic `state_generation`. Enforce unique canonical source identity.
4. `brain.source_versions`: immutable source/object pair plus media type,
   privacy, trust class, actor assurance, typed hierarchical scope columns,
   source time, one typed primary locator, bounded canonical provenance JSON,
   and creation time. Enforce that `(logical_source_id, current_version_id)`
   points to a version owned by that same source. Absolute paths are allowed
   only as `legacy-path` under the admin importer with `legacy-unverified`.
5. `brain.source_tombstones`: immutable tombstone identity/request,
   reason/assurance/provenance, generation, and time, with optional all-or-none
   restore fields. A partial unique index permits at most one active tombstone.
   Runtime ingestion cannot restore implicitly; the only runtime restore path
   is an exact `restore_tombstone_id` supplied with new bytes and recorded
   atomically by the publish broker.
6. `brain.ingest_intents`: immutable idempotency key, request fingerprint,
   bounded sanitized canonical request, expected digest/size, and a monotonic
   `prepared → object-verified → complete` stage. Completed rows store the
   source head/generation and active tombstone ID observed during prepare,
   exact source/version/object result, prior/current head at completion,
   published generation, and outcome
   (`current|unchanged|superseded-concurrent`); intents therefore are the
   publish-transition ledger without a separate head/event table.

Use `text + CHECK` constraints following repository conventions, not database
enums. Add only lifecycle indexes: version history/object/scope-policy lookup,
current pointer, active/recent tombstone, pending intent, expected object, and
completed head transitions. Do not add extraction/vector indexes owned by
#370. Add nullable `source_version_id` citations to the existing structured
knowledge rows that need exact lineage; model explicit assertions as
`structured-record` source versions with `caller-unverified` assurance instead
of adding provenance/locator/knowledge-sidecar tables.

Relational invariants:

- `workspace_identity` permits at most one row and validates the existing
  lowercase-kebab workspace-ID contract plus a versioned 64-hex fingerprint.
- `objects.object_id` is the exact 64-hex byte digest; the generated object key
  cannot contain caller-controlled path material. Immutable tables have
  reject-update/delete triggers so admin mistakes fail too.
- `logical_sources` is unique on
  `(source_kind, origin_namespace, origin_key)`. Its composite
  `(logical_source_id, current_version_id)` foreign key can point only to a
  version owned by the same source. A column guard permits changes only to
  `current_version_id` and forward-only `state_generation`; canonical identity
  and display metadata never mutate through the runtime broker.
- Scope CHECKs require exactly: no IDs for workspace; function only for
  function; function+agent for agent; function+agent+plan for plan. Privacy is
  `public|internal|secret`; trust uses the committed trust taxonomy; ordinary
  runtime assurance is fixed to `caller-unverified`.
- At most one unrestored tombstone exists per source. Restore fields are
  all-null or all-present, use their own idempotency fingerprint, and advance
  generation. A restore must name the exact active tombstone and publish
  caller-presented bytes in the same transaction; no standalone or normal
  ingest can reactivate a source.
- Intent identity/request fields never change, stages advance only forward,
  completed rows never change, and stage-specific CHECKs require exactly the
  observations/results valid at that stage. `canonical_request` is bounded,
  sanitized JSON metadata—never bytes, credentials, secret-bearing URLs,
  arbitrary errors, or non-legacy absolute paths.

Migration 010 does **not** create `extractions`, new `chunks`,
`embedding_indexes`, a retrieval index, an evidence schema, a tenancy
wrapper, a binding table, a source-state event log, a source-head table, or
separate locator/provenance tables.

### Migration 011 — `011_closed_runtime_api.sql`

Create fixed, admin-owned database brokers:

- `brain.begin_ingest(...)`
- `brain.mark_ingest_object_verified(...)`
- `brain.publish_ingest(...)`
- `brain.note_ingest_failure(...)`
- `brain.tombstone_source(...)`
- the existing semantic `save`/`event`/`link`/`merge` operations rewritten as
  fixed brokers that require an immutable assertion source-version citation.

Functions use a fixed search path, fixed tables, typed parameters, no dynamic
identifiers, no caller SQL, no role switching, and no trust/assurance elevation.
They are admin-owned `SECURITY DEFINER` functions with a pinned `search_path`;
every function revokes `EXECUTE` from `PUBLIC` before granting the exact runtime
role, following migration 006's import-lock pattern.
`publish_ingest` locks the logical-source row, verifies the
intent/object/version and tombstone-or-exact-restore preconditions, inserts or
reuses immutable rows, advances the
current pointer, and completes the intent with the head transition in one
transaction. Every immutable conflict is followed by an exact field comparison;
no immutable row uses `ON CONFLICT DO UPDATE`.

Migration 011 revokes runtime:

- database/schema CREATE;
- ownership or membership in any owner/admin role;
- direct INSERT/UPDATE/DELETE/TRUNCATE on protected source/provenance/meta
  tables;
- EXECUTE on `brain.create_table`;
- unsafe PUBLIC/default privileges; and
- direct mutation of identity, source pointers, object metadata, provenance,
  intent request fields, tombstones, and classification.

It also deletes the five verified legacy `files.*` configuration rows, removes
their setters, and proves no shipped v2 S3 path imports or calls
`filesConfig()`. All object-store construction takes only the already-verified
tracked namespace.

Runtime receives only:

- SELECT on the protected handshake projection and an explicit allowlist of
  existing structured-knowledge tables plus the six v2 lifecycle tables needed
  by exact `get`, history, deduplication, and internal repository reads; there
  are no wildcard/default grants to future tables;
- fixed structured-knowledge brokers after they require an immutable
  caller-unverified source-version citation;
- EXECUTE on the fixed source brokers; and
- exact sequence/function privileges required by those surfaces.

No table enables or forces RLS. Tests assert zero policies and demonstrate that
trusted workspace credentials can read rows carrying sibling retrieval labels;
later retrieval code, not PostgreSQL authorization, filters those labels.
`brain query` remains disabled in #351, so no context path reads these base
tables directly. #352 must add and use a current, non-tombstoned,
privacy-filtered citation view before enabling retrieval; secret rows remain
available only to an explicit exact `brain get`, never seeded context.

### Migration runner sequence

The implementation must not add migration 010 before the old-schema snapshot
path can read a database whose latest applied migration is 009.

The Brain wrapper first acquires a **session-scoped** advisory lock on one
dedicated admin client using the existing Brain migration lock key and holds it
across snapshot, 010, backfill, verification, 011, and ready transition. Every
other Brain migrate/init/repair path takes the same key, so a second clone
blocks before applying 011 mid-backfill. The shared migration core gains a
client-bound `runMigrationsThrough(..., maxPrefix)` primitive while its existing
all-migrations API remains unchanged for other ledgers. Each stage commits
independently while the session lock remains held. The through-prefix helper
must execute on that **same** client (same-session advisory locking is
re-entrant); acquiring the lock on one connection and migrating on another can
hang indefinitely. The client-bound helper owns each stage's explicit
`BEGIN/COMMIT/ROLLBACK`; it does not reuse today's all-files-in-one-transaction
wrapper.

1. Extend the internal legacy snapshot inspection to recognize exact schemas without
   requiring the installed migration set to match first.
2. Capture a deterministic database snapshot plus complete S3 version/delete
   marker manifest.
3. Revalidate schema hashes, counts, role state, S3 manifest, and configured
   authority.
4. Apply through migration 010 under the existing advisory/hash lock.
5. Initialize the exact protected identity in `migrating` state with the
   approved manifest digest; a different identity or digest is a hard conflict.
6. Run the bounded legacy backfill, resumably.
7. Verify counts, IDs, canonical merge redirects, object hashes/versions,
   locators, provenance classifications, and current pointers.
8. Apply migration 011 and its final grants.
9. Advance the protected migration state to `ready` and record the exact
   completed migration fingerprint for #363's cutover report.

The migration runner gains a bounded “through migration” option rather than a
second migration authority. If the session dies, PostgreSQL releases the lock;
the migration ledger, protected manifest digest/state, and ingest intents are
the durable resume record. Failed or repeated runs use the same hash-locked
files and immutable manifest.

## Object namespace and ingestion data flow

Relative keys inside the validated root prefix:

```text
objects/<first-two-sha256-chars>/<full-sha256>
evidence/<run-id>/<artifact-id>   # reserved for the evidence owner
exports/<export-id>               # reserved for migration evidence
```

No runtime API accepts a raw S3 key or exposes delete/overwrite. Conditional
creation verifies the winning object's exact size and SHA-256 before reuse.
Equal bytes across different logical sources share one object row/key without
merging sources. S3 version IDs are observations and are recorded when the
provider supplies them.

Ingest flow:

```text
tracked config
  → protected DB handshake on this physical connection
  → validate source identity/scope/privacy/input
  → bounded exact-byte read and hash
  → begin/reuse durable ingest intent
  → create-or-verify content-addressed object
  → record verified object in a short DB transaction
  → one publish DB transaction:
       register object
       lock/create logical source
       reject tombstone unless exact restore is recorded
       insert/reuse immutable source version
       set logical_sources.current_version_id
       increment generation once when head or tombstone visibility changes
       complete intent with previous/current head
  → return source/version/object IDs, generation, and index_state=pending
```

The database transaction never spans an S3 request.

The three database boundaries are explicit:

1. **T1 — prepare:** read the canonical logical source's current head,
   generation, and active tombstone ID, then insert-or-load by idempotency key
   with those expected-state fields. Compare the complete request fingerprint,
   return a stored completed
   result without touching S3, or commit a `prepared` intent before object I/O.
   A reused key with different input rolls back as `IDEMPOTENCY_CONFLICT`.
2. **S3 then T2 — verify object:** conditionally create the deterministic key.
   If it already exists, verify a trustworthy provider SHA-256 or re-read and
   hash exact bytes; size and ETag alone are insufficient. Lock the intent,
   insert-or-compare every immutable object field, and advance only to
   `object-verified`.
3. **T3 — publish:** lock the intent and canonical logical-source row. Reject an
   active tombstone unless the canonical request and T1 observation both name
   its exact `restore_tombstone_id`; on an exact match, close that tombstone and
   publish the caller-presented version atomically. A requested tombstone that
   is no longer the active row is a conflict, never a normal put.
   Insert-or-compare the deterministic immutable version.
   Move the current pointer only if the locked head/generation still equals the
   T1 expectation. If it diverged, retain the version in history, complete as
   `superseded-concurrent`, and return `INGEST_HEAD_DIVERGED`; never overwrite a
   newer head. Otherwise update generation when the head or tombstone visibility
   changes (once when both happen together) and complete with prior/current head
   and restore identity in the same transaction.

Concurrent identical requests converge. Concurrent different requests prepared
from one head serialize; only the first successful transition changes current,
while later divergent versions remain in history and require an intentional
new idempotency key prepared against the new head. Completed or repaired intent
replay never reapplies an old transition or rewinds the head.

## Failure states and recovery

Stable redacted diagnostics:

| Code | Meaning and recovery |
|---|---|
| `BRAIN_NOT_CONFIGURED` | No tracked Brain block. Brain verbs fail with setup guidance; `roster context` preserves its one nonfatal empty-evidence warning. No pool or S3 client is created. |
| `BRAIN_IDENTITY_UNINITIALIZED` | Schema exists without authority. Only clean admin init or #363's explicit adoption may proceed. |
| `BRAIN_MIGRATION_IN_PROGRESS` | The exact approved legacy manifest is mid-backfill. Runtime remains blocked; only the same manifest under the remote lock may resume. |
| `BRAIN_WORKSPACE_MISMATCH` | Database identity differs. Stop after protected metadata; do not inspect content or S3. |
| `BRAIN_NAMESPACE_MISMATCH` | Tracked namespace fingerprint differs from database metadata. Stop before content/S3. |
| `BRAIN_LEGACY_ADOPTION_REQUIRED` | A nonempty pre-v2 database has no protected identity. Do not auto-stamp; #363 must supply an approved manifest. |
| `SOURCE_IDENTITY_INVALID` | Origin/stable key/scope/path is invalid. No intent or object is created. |
| `EXTERNAL_PATH_GRANT_REQUIRED` | Input escapes the workspace and lacks an exact host-obtained path grant. |
| `IDEMPOTENCY_CONFLICT` | One idempotency key names different canonical input/policy. Return the original fingerprint/result metadata without mutation. |
| `SOURCE_TOMBSTONED` | Source is tombstoned. Ordinary ingest cannot reactivate it; re-present bytes with the exact active tombstone ID and a new idempotency key after host-native approval. |
| `TOMBSTONE_RESTORE_CONFLICT` | The requested tombstone is absent, already restored, or no longer the active row observed at prepare. Do not publish; reload state and require a new approved request. |
| `OBJECT_HASH_CONFLICT` | A content-addressed key contains different bytes/size. Quarantine the intent and require admin investigation. |
| `OBJECT_MISSING` | Postgres references bytes not found at the recorded version/current key. Never fabricate from chunks; re-present exact verified bytes through the explicit repair/restore precondition. |
| `INGEST_HEAD_DIVERGED` | The source changed after this intent prepared. Preserve the verified version in history, do not move current, and require a new intentional idempotency key to publish against the new head. |
| `INGEST_REPAIR_REQUIRED` | Intent is aged or failed between stores. `brain doctor` reports it; `--repair` resumes only provable intent-owned work. |
| `BRAIN_RETRIEVAL_NOT_READY` | v2 query/reindex is unavailable until #352/#370 installs policy-correct retrieval/indexing; never fall back to legacy authority. |
| `BRAIN_RUNTIME_ROLE_REQUIRED` | The ambient runtime URL is missing, cannot connect as a pre-provisioned login, or owns unsafe creator privileges. Provision/fix it through Neon/Infisical; Roster never mints credentials. |
| `BRAIN_ROLE_INVARIANT_FAILED` | Runtime ownership, DDL, destructive grant, SET ROLE reachability, default ACL, or unsafe security-definer function is detected. Block runtime commands until admin repair. |

Recovery rules:

- Crash after intent but before S3: replay stores/verifies the expected object.
- Crash after S3 but before database publish: replay verifies the exact object
  and publishes only if the recorded expected head still matches; otherwise it
  completes as `superseded-concurrent` without rewinding current.
- Crash during database publish: transaction rollback leaves the previous
  current pointer; replay is safe.
- Commit succeeds but client loses the response: replay reads the completed
  intent and returns the same IDs.
- Missing/wrong-hash bytes: report and stop. Repair never synthesizes bytes.
- Object with a provable intent but no row: repair may register/publish it after
  exact verification.
- Object with no provable intent: report as non-authoritative; do not delete or
  adopt automatically.
- Repeated repair is a no-op after convergence and is report-only unless the
  user explicitly supplied `--repair` with admin credentials.

```text
roster brain ingest
  --kind file|fetched-media|inline-text|structured-record|produced-artifact
  --input <workspace-relative-path|->
```

Kind-specific flags are mutually constrained. Content is never accepted as an
argv value. Structured JSON is canonicalized; all other bytes remain exact.
Output contains only stable IDs, sizes/hashes allowed by privacy policy,

The canonical semantic verbs add mandatory
`--source-key <host-domain-key> --idempotency-key <stable-operation-key>` and

structured payload and performs the single source ingest before its closed
knowledge broker. Omitting either key fails before S3 or database mutation.

The canonical filesystem façade keeps the familiar address but adds explicit
mutation identity:

```text
roster brain fs put --kind <kind> --slug <slug> --idempotency-key <key>
  [--filename <name>] [--restore-tombstone <exact-id>]
  <workspace-relative-input>
roster brain fs rm --kind <kind> --slug <slug> --idempotency-key <key> <filename>
roster brain fs get --kind <kind> --slug <slug> <filename> [--out <path>]
roster brain fs ls [--kind <kind>] [--slug <slug>]
```

- Remove the public `brain mount`, `brain table`, `brain sql`, `brain config`,

   remove creates the active tombstone; a later put names and closes that exact

9. Link mounts/files to source versions. Leave all 5,656 chunks and their
   embeddings untouched for #370.
   `brain.current_documents` remains a legacy view only; no v2 read/context

## Edge cases and required behavior

- Same clone at a different checkout root derives the same file source ID.
- `brain fs put` then `get` resolves one `roster-fs` produced-artifact source;
  a migrated legacy row at the same `(kind, slug, filename)` resolves the same
  logical-source ID and current bytes.
- `brain fs put → rm → put` refuses the ordinary second put; the exact
  approved `--restore-tombstone` put records one restoration/publish transition
  and makes the address readable again without changing its logical-source ID.
- A copied registry with a different `workspace_id` cannot activate the same
  database or namespace.
- Same workspace ID with a changed bucket, endpoint, or prefix refuses before
  content access.
- Pooler/client swap repeats the handshake; process-wide verification caching is
  forbidden.
- Missing Brain config is fatal for Brain verbs but remains the one nonfatal
  `BRAIN_NOT_CONFIGURED` warning/empty evidence behavior for `roster context`.
- Source path normalization handles Unicode deterministically and rejects
  backslashes, case-ambiguous traversal, symlinks, devices, FIFOs, sockets, and
  oversized inputs.
- Fetched identity prefers provider stable ID; URL fallback strips fragments,
  rejects credentials/non-HTTPS, and has one documented canonicalization
  version.
- Inline/structured/artifact ingest without stable key fails before intent.
- Duplicate JSON keys, nonfinite values, excess depth/nodes/bytes, and malformed
  Unicode fail structured ingest.
- Same idempotency key/same request returns the original result; same key/changed
  request fails without mutation.
- Concurrent identical intents converge; concurrent different intents for one
  source serialize on the logical-source row, preserve both versions, and only
  the intent whose expected head still matches may advance current.
- An aged A intent repaired after B became current completes as
  `superseded-concurrent` and cannot rewind B.
- Same bytes across different sources share an object only.
- Changed bytes or privacy/scope/provenance classification creates a new source
  version; history remains immutable.
- A→B→A with three intentional keys records three completed head transitions
  while reusing immutable version/object A.
- Tombstoned source never reappears through ingest or default current views.
- Secret-class bytes are never embedded or returned by context; #370/#352
  enforce their later stages, while #351 preserves the classification.
- Config/identity diagnostics contain no URL credentials, AWS identifiers,
  source bodies, absolute paths, raw stable keys, or secrets.
- Backup/import detects schema hash drift, missing/tampered manifests, object
  hash mismatch, and unsupported newer schema before mutation.
- Legacy custom tables are inventoried and preserved read-only; runtime table
  creation is not retained to support them.

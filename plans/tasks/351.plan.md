# Issue #351 implementation plan — establish workspace Brain authority

## Ticket

- GitHub: `firatcand/roster#351`
- Forge task: `P2-T01`
- Branch: `feat/351`
- Type / estimate: foundation / M
- Dependency: #350, merged

## Outcome

Give one logical Roster workspace one portable, secret-free Brain description
and bind it to exactly one protected PostgreSQL identity plus one configured S3
namespace.

After this ticket:

1. `roster.yaml` may contain a strict Brain configuration. It identifies the
   workspace's Infisical path and non-secret S3 organization, never credentials.
2. PostgreSQL stores one create-once protected record containing the same
   `workspace_id`, a canonical S3 namespace fingerprint, and a random database
   authority ID that distinguishes this physical database from a separately
   initialized database with otherwise identical metadata.
3. A caller cannot receive an admin or runtime client until that physical
   connection has passed the protected-metadata handshake.
4. Clean initialization is idempotent. An unidentified database with company
   state is not guessed or adopted; it returns a reviewed-adoption requirement
   for #382/#384.
5. Runtime can read the protected identity but cannot insert, update, delete, or
   otherwise mutate it.
6. Context reports `brain_configured`; no configuration remains a successful
   local-only response with one `BRAIN_NOT_CONFIGURED` warning.

Claude Code or Codex remains the runtime. Roster only supplies the authority,
validation, and context contract.

## Approved decisions

- One logical workspace owns a different PostgreSQL database and S3 namespace.
  Clones with the same authored `workspace_id` may share that authority.
- The host owns the least-privilege runtime credential in Infisical. Roster
  validates and uses the ambient URL for first initialization but never mints,
  stores, returns, or prints it.
- Function, agent, and plan scopes are retrieval labels, not database
  authorization principals.
- The five-ticket split is authoritative:
  - #351 — authority only
  - #381 — recoverable source lifecycle
  - #382 — read-only legacy inventory
  - #383 — closed runtime and public Brain surface
  - #384 — reviewed legacy backfill
- Legacy command removal belongs to #363. Until then the phase-2 public runtime
  will recognize legacy spellings only to fail closed; #383 owns that parser
  behavior, not this ticket.
- #383 also owns doctor and retained-command routing through the authority API.
  #351 changes only the existing `brain init` path because adding the authority
  migration without atomic identity initialization would create an unsafe
  migrated-but-unidentified database.
- One surgical bridge is required: legacy `brain import` currently invokes the
  migration runner itself. #351 keeps the parser name but returns the shared
  stable `BRAIN_LEGACY_COMMAND_DISABLED` diagnostic before config, URL, pool,
  filesystem, or database access; #383 applies that policy uniformly to the
  remaining legacy spellings.
- `legacy-unverified` retrieval policy and S3 byte retention are durable in
  SPEC/PRD but have no implementation in this authority-only ticket.

No product or architecture question remains open for #351.

## Contracts

### Tracked configuration

The optional authored shape is:

```yaml
schema_version: 2
workspace_id: my-roster
brain:
  secrets_path: /my-roster
  storage:
    bucket: my-roster-vault
    region: eu-central-1
    # root_prefix: brain
    # endpoint: https://s3.example.com
    # force_path_style: false
```

Rules:

- reject unknown fields and any credential, URL userinfo, query, fragment, or
  secret-looking value;
- the retired `brain.binding` shape is not a compatibility input: reject it as
  an unknown field with a migration hint to author `secrets_path` and `storage`
  instead;
- `secrets_path` is an absolute Infisical path with bounded safe components;
- bucket and region are required, length-bounded, and canonical, including the
  S3-compatible `auto` region token; root prefix is optional and, when present,
  is at most 757 bytes so the longest durable key family
  (`evidence/<128-byte-run-id>/<128-byte-artifact-id>`) still fits S3's
  1,024-byte key limit, is relative, and has no empty/dot components, C0/C1
  controls, or backslashes;
- omitted root prefix canonicalizes to the bucket root without manufacturing a
  path segment;
- a custom endpoint is an HTTPS origin only and rejects credentials, paths,
  queries, fragments, trailing-dot localhost aliases, and every non-global
  literal address (including private, link-local, mapped, multicast, benchmark,
  and carrier-grade NAT ranges); no private-endpoint exception field is
  introduced by this ticket;
- the exact custom public HTTPS endpoint authored in tracked `roster.yaml` is
  the explicit trust affirmation for that non-standard public endpoint; private
  or link-local deployment authorization is unsupported here and requires a
  separate reviewed product decision before use; #381 owns that explicit
  private-endpoint exception together with the first S3-access boundary;
- `force_path_style` defaults to `false`;
- normalization never reads Infisical, DNS, PostgreSQL, S3, or the checkout's
  absolute path.

The namespace fingerprint hashes fixed-order canonical JSON containing the
domain/version `roster.brain.s3-namespace.v1`, provider `s3`, bucket, region,
normalized endpoint or the AWS-default sentinel, path-style mode, and root
prefix or an explicit absent sentinel. It contains no secret reference,
credential, DNS result, or machine path.

Workspace ID and namespace fingerprint do not rotate through ordinary init.
The version field makes an unsupported format fail distinctly; adopting a
legacy namespace in #363/#384 or changing an established namespace/format later
requires an explicit reviewed migration that first preserves/reconciles object
history and deliberately replaces the SQL guard. Silent config-driven rotation
is forbidden.

### Protected database identity

Migration `010_workspace_authority.sql` adds only the authority contract:

- a constant singleton primary key/check enforces at most one
  `brain_meta.workspace_identity` row; successful initialization and normal
  verification require exactly one;
- fields are `workspace_id`, `fingerprint_format_version`,
  `namespace_fingerprint`, an initialization-time random UUID named
  `database_authority_id`, initialization time, and
  `migration_state = migrating | ready`;
- constraints validate IDs, fingerprint format, and state;
- guards keep workspace ID, fingerprint format, namespace fingerprint,
  database authority ID, and initialization time immutable, block delete and
  truncate, and permit only the admin-owned monotone `migrating → ready` state
  transition needed by later reviewed adoption;
- runtime receives schema usage plus `SELECT` on this table and no mutation
  privilege;
- no lifecycle, content, object, retrieval, or backfill table/function is added.

All migrations executed by this atomic path must remain transaction-safe; a
migration using non-transactional DDL such as `CREATE INDEX CONCURRENTLY` is
rejected or moved to a separately designed lifecycle before it can enter the
Brain migration set. Before any DDL or grant refresh, the recorded ledger must
be an exact ordered prefix of the loaded migration set with matching hashes;
unknown/future rows, duplicates, or gaps fail closed instead of letting an
older binary call a newer database current.

Each workspace receives a distinct cluster-global PostgreSQL login role whose
bounded name is deterministically derived from a domain-separated hash of the
authored workspace ID and the validated role base. This matters even when each
workspace has a different database because PostgreSQL roles and passwords span
every database in one cluster. An existing derived role is replay-safe only
when it is already registered in this database; an unregistered collision
returns `BRAIN_RUNTIME_ROLE_COLLISION` and the bootstrap transaction rolls back.
The legacy `--role` option is a role-name base, never an exact shared login that
can bypass workspace qualification. The database pins one derived role/base;
ordinary replay with a different base is a collision, not credential rotation.

Roster does not mint, return, or print the runtime credential. Before first
initialization, the host chooses a password, stores a `ROSTER_BRAIN_URL` under
the tracked Infisical path, and invokes Roster with that ambient secret. Its URL
username must equal the expected derived role name. After percent-decoding, its
password must be 43–128 base64url characters (`A-Z`, `a-z`, `0-9`, `_`, `-`),
which excludes quotes, backslashes, NUL, C0/C1 controls, and ambiguous SQL
literal bytes independent of `standard_conforming_strings`; the host should
generate at least 32 random bytes rather than choose a phrase. A missing or
mismatched URL fails before database access with a stable redacted diagnostic
that includes only the expected non-secret role name and tracked Infisical path,
so the host can prepare the secret and retry. The secret is supplied to
PostgreSQL only for initial role creation, is never retained by Roster, and is
never rotated during idempotent replay. Roster output/logs remain secret-free;
the PostgreSQL/provider administrator is responsible for disabling statement or
parameter logging that would record credentials during role creation.

#383 owns explicit runtime credential rotation through a previously authenticated
runtime role (or a reviewed provider-admin recovery path). Until that ships, a
compromised or prematurely changed Infisical credential returns a redacted
remedy to restore the prior valid secret or reset the role through Neon/provider
controls; `brain init` never silently changes an existing role password.

### Handshake and initialization

The authority-managed connection wrapper gates both `connect()` and `query()`:

1. acquires a physical client;
2. reads only `brain_meta.workspace_identity`;
3. compares workspace ID, fingerprint format, namespace fingerprint, and ready
   state; when initialization supplies the exact database authority ID, it also
   rejects a separately initialized database even if all authored metadata is
   identical;
4. destroys/releases a failed client without invoking caller code;
5. marks a successful physical client verified for that immutable authority
   using the existing `BoundPool`/`WeakSet` pattern without wrapping caller work
   in a transaction;
6. invokes caller code, then releases the client normally.

Verification is once per physical connection, not once per pool and not once per
SQL statement. Different authorities never share a verified marker.

Stable redacted outcomes distinguish:

- `BRAIN_NOT_CONFIGURED`;
- `BRAIN_IDENTITY_UNINITIALIZED`;
- `BRAIN_MIGRATION_IN_PROGRESS`;
- `BRAIN_WORKSPACE_MISMATCH`;
- `BRAIN_NAMESPACE_MISMATCH`;
- `BRAIN_DATABASE_AUTHORITY_MISMATCH`;
- `BRAIN_RUNTIME_ROLE_COLLISION`;
- `BRAIN_RUNTIME_CREDENTIAL_INVALID`; and
- `BRAIN_LEGACY_ADOPTION_REQUIRED`.

`brain init` may use an unverified admin connection only inside the authority
bootstrap boundary. It resolves and validates `roster.yaml` before resolving
the ambient admin/runtime URLs or constructing a pool. It validates the runtime
URL's non-secret role name and presence of a password without printing either
URL or the password. On one physical admin client it then:

- when `roster.yaml` is absent, returns `WORKSPACE_NOT_FOUND`; when it is a valid
  v2 registry without `brain`, returns `BRAIN_NOT_CONFIGURED`; both occur before
  credential resolution or database access;

1. acquires the existing Brain migration advisory-lock key `8135135` with the
   single-bigint `pg_advisory_lock($1)` form at session scope, so it occupies the
   same lock space as legacy single-bigint transaction-lock callers;
2. begins one caller-owned transaction;
3. probes catalogs for the identity relation before selecting it, then checks
   an existing identity or classifies the database from bounded catalog
   metadata before the first schema or data mutation;
4. treats only a genuinely uninitialized database as clean: `pg_catalog`,
   `information_schema`, `pg_toast*`, the default object-free `public` schema,
   and objects owned by approved installed extensions are exempt; any custom
   schema or any non-extension relation, sequence, type/domain, collation,
   operator, or routine in `public` or another user schema is company/ambiguous
   state and requires adoption, even when row counts happen to be zero;
5. when a `ready` identity already matches, applies any pending schema
   migrations and refreshes grants inside the same locked transaction while the
   identity remains `ready`; transactional DDL is invisible until commit and a
   failure leaves the prior version intact;
6. for a clean database, runs migrations `001`–`010` on that same client,
   inserts identity as `migrating` with a newly generated database authority
   UUID, creates only the workspace's qualified registered runtime role with
   the host-supplied ambient password (or reuses that registered role without
   password rotation), performs the one permitted transition to `ready`, and
   installs runtime grants before commit;
7. rolls back the complete transaction on any failure, so a retry never sees a
   half-migrated unidentified database;
8. commits, releases the advisory lock in a `finally` on both success and
   rollback paths before closing the raw bootstrap pool, then
   verifies through newly constructed normal authority-managed admin and
   runtime pools, requiring both to return the exact committed database
   authority ID, so the production physical-connection gate, same-database
   invariant, and supplied runtime credential are all exercised; and
9. returns a no-op result only when identity, migration hashes, and grants are
   already current.

Because the runtime credential proof occurs after commit, authentication or
authority failure there returns a redacted credential/authority diagnostic and
leaves a complete valid initialized authority rather than pretending it rolled
back. Correcting the ambient runtime URL and retrying converges without schema,
identity, grant, role, or password rotation.

The client-bound inner migration primitive does not connect, lock, begin,
commit, or roll back; bootstrap owns all five. An already identified mismatch
or `migrating` state fails before further mutation. A nonempty or ambiguous
unidentified database returns `BRAIN_LEGACY_ADOPTION_REQUIRED` without creating
migration metadata, inserting identity, reading row bodies, touching S3, or
changing legacy state. #382 produces the inventory and #384 owns reviewed
adoption/backfill.

The clean-path `migrating` row is not externally observable because it becomes
`ready` in the same transaction. The state exists so #384 can later expose a
durable reviewed-adoption boundary; runtime verification always rejects it.

Interim phase-2 consequence: a pre-existing unidentified Brain cannot apply
`010`, so legacy `brain gc` sees a pending migration and its old “run init”
remedy ends at `BRAIN_LEGACY_ADOPTION_REQUIRED` until #384 performs reviewed
adoption. This is an intentional fail-closed window, not a repair path for
#351; #383 retires legacy `gc` behavior while preserving the stable diagnostic.
Legacy import is also unavailable: pre-#351 backups cannot satisfy the new
authority schema, and the command cannot create/migrate a fresh target. #384
preserves/backfills reviewed history and #363 owns the real adopter cutover.

### Context refreeze

- Replace registry metadata/output `brain_binding` with
  `brain_configured: boolean`.
- Replace `BRAIN_NOT_BOUND` with `BRAIN_NOT_CONFIGURED`.
- Config absence returns the complete mandatory local bundle, empty optional
  Brain evidence, and exactly one nonfatal warning.
- Config presence does not itself fetch evidence; #352 owns retrieval.
- Remove the required candidate `binding` field and binding serialization.
  Workspace eligibility uses the already required candidate workspace scope;
  narrower scope remains selection only.
- Rename `cross-binding` to `workspace-mismatch` and `cross-scope` to
  `scope-ineligible`. Keep them mutually exclusive by removing workspace
  comparison from the narrower-scope predicate.
- Regenerate only canonical host/context artifacts and hashes affected by this
  protocol change.

## 5. Independent eligibility, and proving label correlation (B1)

### 5.1 Assembler-side derivation

Executed by the pure assembler with no adapter input beyond `label_keys`:

1. Validate every `label_keys` entry against the four generated shapes (local regex mirroring `011:126-133`), bounded by `MAX_CANDIDATE_LABEL_KEYS = 64` (≥ `MAX_SOURCE_LABELS`). Violation → `malformed`.
2. Compute the allowlist **from `ResolvedLocalContext`**, never from the request:
   `allowed = { 'workspace', 'function:'+F, 'agent:'+F+'/'+A } ∪ { 'plan:'+q : q ∈ closure }`.
3. `eligible = label_keys ∩ allowed`; empty → `scope-ineligible`.
4. Derive the **narrowest** eligible label (`plan > agent > function > workspace`); ties among equally-specific labels — possible only when several closure plans label one version — break on **code-point-minimum `label_key`**.
5. The derived scope must equal the adapter-supplied `scope`; disagreement → `malformed`.
6. Emitted `fragment.scope` and `candidate_scope` come from the **derived** label.

`allowed` is a bound `text[]` of at most `3 + |closure|` exact strings, so retrieval cannot reach a label outside it and no label combination widens anything.

### 5.2 The two distinct label uses in adapter SQL

```sql
-- (a) eligibility, correlated
EXISTS (SELECT 1 FROM brain.source_version_labels l
         WHERE l.source_version_id = chunk_row.source_version_id
           AND l.label_key = ANY($allowed::text[]))
-- (b) projection, correlated
LEFT JOIN LATERAL (
  SELECT array_agg(l2.label_key ORDER BY l2.label_key COLLATE "C") AS label_keys
    FROM brain.source_version_labels l2
   WHERE l2.source_version_id = chunk_row.source_version_id
) labels ON true
```

### 5.3 Stated limitation

The pure assembler cannot verify that projected `label_keys` truly belong to that `source_version_id`. That correlation is a SQL-shape obligation discharged by (b) plus the mutation test below.

### 5.4 The corrected mutation test (B1)

Revision 2's test mutated **(a)**, which independent eligibility makes redundant — `V_foreign` is rejected by the assembler either way, so the absence assertion survived and proved nothing. The test now targets **(b)**:

- Fixture: `V_eligible` labeled `{workspace, agent:gtm/social-manager}`; `V_narrow` labeled `{plan:gtm/social-manager#opportunity-discovery}`; `V_foreign` labeled `{function:other}` only. All three match the lexical query.
- Assertions, per returned candidate, taken from the **raw adapter output** (`retrieveBrainContextEvidence(request)` is called directly, so `evidence.candidates[i].label_keys` is observable):
  1. `label_keys` equals **exactly** the fixture's label set for that `source_version_id` — deep-equal, order-sensitive;
  2. the bundle's emitted `candidate_scope` equals the **fixture-computed** expected narrowest label (computed in the test from the fixture, never from the adapter);
  3. `V_foreign` is absent from the bundle.
- Mutation harness: delete `l2.source_version_id = chunk_row.source_version_id` from **(b)**. The projection then returns the workspace-wide label union, so assertion 1 fails for every candidate and assertion 2 fails for `V_eligible` (its derived narrowest label becomes the plan label). The test **must** fail under the mutation; a passing mutation run fails the suite.

## 6. Arms, fusion, required coverage, and ordering (B4, B7)

**Arms** (per selector, over the eligibility-filtered pool):

1. **structured** — `extraction.structured @? $path::jsonpath`, a **value-equality** predicate built by the adapter from the selector id (a strict kebab local id) and passed as a bound parameter.
2. **lexical** — `chunk.tsv @@ websearch_to_tsquery('english', $text)` with `$text` = selector id tokens + sorted descriptions + request query/step hint; `ORDER BY ts_rank_cd(...) DESC, chunk_id COLLATE "C" ASC`.
3. **embedding (optional)** — only when the provider resolves: `ORDER BY embedding <=> $vec LIMIT k`, joined through `current_source_chunks`, filtered to the registered `embedding_spec_id`. `selectCurrentChunkEmbeddings` (capped at 1 000 rows/call, `embedding-index.ts:19`) is used only as the exact-parity oracle in tests.
4. **graph — deferred.** Reported as `graph: { status: 'unavailable', reasons: ['unmeasured', 'no-cited-edge-relation'] }`. `search.graph_hops` is deliberately **not** consulted: its default is `1` (`config.ts:43`), so honouring it would activate unmeasured adjacency against `spec/SPEC.md:555,566`. `brain.edges` (`001:41-47`) carries no `source_version_id` and cannot satisfy acceptance 4.

**Fusion — integer only.** `fused = Σ_arms floor(1_000_000 / (rrf_k + rank_in_arm))`, `rrf_k` from `search.rrf_k` (default 60, `config.ts:42`), re-read inside the transaction (§7).

**No assignment step.** A chunk records **every** selector it matched in `selectors` (code-point sorted): `required` = any matched selector is required; `exact` = any equals the normalized request; `unrequested-selector` fires if any entry is outside the catalog. One candidate per chunk, so `duplicate` remains a genuine defect signal. This eliminates the round-1 A={x,y}/B={x} starvation entirely.

### 6.1 Coverage-tracked reservation, and the single reported set M (B4, B7)

Revision 3's reservation pass excluded only *already-reserved candidates*, never *already-covered selectors*. A candidate matching `{x, y}` was reserved for `x`; the pass then reached `y`, found that candidate ineligible for reuse, and spent a **second** slot on a different candidate that covered nothing new. With enough overlap the 64 slots were exhausted while selectors that the selected set already covered were counted as uncovered. Revision 3 then reported truncation from a cardinality inequality rather than from what was actually delivered. Both were corrected in Revision 4 and the algorithm below is unchanged from it.

What **Revision 5 changes** is only what the adapter *reports*. Revision 4 had the adapter compute `deliveredCoverage` and `truncatedSelectors` itself and hand the assembler a second, independent claim. Revision 5 deletes both computations: the adapter reports **only M**, and the assembler derives the split (§6.2). Truncation stops being a claim and becomes a derivation.

Let `TOTAL_CANDIDATE_LIMIT = 64`, `PER_SELECTOR_ARM_LIMIT = 8`, `P` = the eligibility-filtered arm pool **before** any cap, `R` = the required selectors of the catalog (`|R| ≤ MAX_CONTEXT_SELECTORS = 4_096`), and

```
M = { s ∈ R : ∃ c ∈ P with s ∈ c.selectors }        // required selectors that have real matches
```

1. **Global key `K`** — `required desc → fused desc → best-arm-rank asc → selectors[0] asc → chunk_id asc`, compared in JS with `compareUnicodeCodePoints` (normative; all SQL text ordering additionally uses `COLLATE "C"` so the database collation can never disagree).

2. **Reservation pass with coverage tracking.**

```
reserved   : Candidate[] = []
reservedId : Set<string> = ∅
covered    : Set<string> = ∅                       // required selectors already covered

for s of sortedByCodePoint(M):
    if covered.has(s)                    continue  // ← the fix: a covered selector costs no slot
    if reserved.length === TOTAL_CANDIDATE_LIMIT  break
    c = argmin_K { c ∈ P : s ∈ c.selectors and not reservedId.has(c.candidate_id) }
    reserved.push(c); reservedId.add(c.candidate_id)
    for t of c.selectors: if R.has(t) covered.add(t)   // credit every required selector c covers
```

   The `reservedId` guard is provably vacuous and is retained only as a defensive assertion that must never fire: if `c` is reserved then every required `t ∈ c.selectors` is in `covered`, so the loop `continue`s past every later selector `c` could have served. Implementation asserts this; a firing assertion is a defect, not a degradation path.

   This is the deterministic greedy heuristic, not optimal set cover (which is NP-hard and out of scope). That is safe precisely because **the shortfall is derived from the bundle, not from the heuristic** — §6.2.

3. **Fill pass.** Remaining slots are filled from `P \ reserved` in `K` order until `|delivered| = TOTAL_CANDIDATE_LIMIT`. `delivered = reserved ∪ fill`.

4. **Adapter-side coverage accounting: none.** The adapter computes **no** `deliveredCoverage` and **no** `truncatedSelectors`. Its entire required-coverage output is the one set it alone can know:

```
report.required_selectors_with_matches = sortedByCodePoint(M)      // ids, code-point ASCENDING and strict
```

   `covered` remains a purely internal variable of step 2's loop and is never emitted. The reason this is strictly better than Revision 4: `deliveredCoverage` was a quantity the assembler can recompute exactly (it sees every delivered candidate and every selector on it), so having the adapter also assert it created a second source of truth that could disagree; `M` is the one quantity the assembler provably cannot recompute, because `P` never crosses the boundary.

   **Adapter-side invariant (asserted, and tested in the PG suite).** `M ⊇ { s ∈ R : ∃ c ∈ delivered with s ∈ c.selectors }`, because `delivered ⊆ P`. This is the same containment the envelope re-checks as V3 in §6.2 — asserting it on both sides means a violation is a caught defect rather than a silent mislabel.

   **Adapter-side invariant (retained from Revision 4, now feeding §6.2's).** Every loop iteration that does not `continue` pushes exactly one reservation and adds at least `s` to `covered`, so the pass makes at most `|M|` reservations; if `|M| ≤ TOTAL_CANDIDATE_LIMIT` the `break` never fires and every `s ∈ M` ends in `covered ⊆ deliveredCoverage`. Delivery shortfall is therefore reachable only under genuine slot pressure.

5. **Ordinals.** `delivered` is sorted by `K` alone (reservation affects membership, never order) and assigned `retrieval_rank = 0..n-1`. The ordinal stays a pure function of `K` over the selected set; the assembler's own comparator performs the final ranking.

The `required_selectors_with_matches` id array is bounded by `|R| ≤ 4_096` entries, each a kebab local id under `MAX_SELECTOR_OR_LOCATOR_BYTES = 4_096` (`workspace-context.ts:1146`); it never reaches the emitted bundle and is covered by the existing 16 MiB envelope bound (`:1300-1302`).

### 6.2 Assembler-side split — single-sourced from M, authoritative, never droppable (B4, B7)

`src/lib/workspace-context.ts:1915-1918` today derives `matchedSelectors` from `evaluation.candidate!.selector` (singular) over the eligible candidates *in the envelope*, and `:1649-1657` turns any shortfall into the mandatory warning `CONTEXT_REQUIRED_EVIDENCE_MISSING` — "Required-intent Brain selectors have no eligible evidence." For a selector the 64-cap dropped, that statement is false. The assembler now splits it, **from one report field**:

```
bundleCoverage = ⋃ { c.selectors : evaluation.reason === null }     // eligible candidates, widened from .selector
required       = { s.selector : s ∈ local.selectors, s.required }
missing        = required \ bundleCoverage
M              = new Set(report.required_selectors_with_matches)    // validated below; M ⊆ required

truncatedSet   = { s ∈ missing :  M.has(s) }
unmatchedSet   = { s ∈ missing : !M.has(s) }

budget.required_selectors_unmatched = |unmatchedSet|                // #346 meaning, now TRUE
budget.required_selectors_truncated = |truncatedSet|                // new, always emitted
```

`matchedSelectors` at `:1917` changes from the singular `evaluation.candidate!.selector` to the union over the `selectors` array — the §6 "no assignment step" widening, unchanged from Revision 4. Both counters are `0` when `!brainConfigured` or `evidenceStatus !== 'seeded'`, exactly as today.

**Why this kills the one-directional intersection.** `truncatedSet` and `unmatchedSet` are, by construction, a **partition of `missing`** by membership in a single set: they are disjoint, their union is exactly `missing`, and no selector can be in both. Revision 4 intersected two independently-produced claims, which is why a stale report could shift a selector out of `truncated` without anything moving it into `unmatched`, and why an over-report could put a selector in `truncated` that the other claim disagreed about. With one source there is nothing to disagree with: whatever M says, `|truncated| + |unmatched| = |missing|` holds exactly.

**Meaning of `truncated`, stated precisely.** A required selector is `truncated` when retrieval matched it (`s ∈ M`) but no eligible candidate carrying it reached the bundle. The dominant cause is the `TOTAL_CANDIDATE_LIMIT` cap. The secondary causes are the assembler's own exclusions — `privacy-incompatible`, `duplicate`, `scope-ineligible`, `unauthorized`, `malformed` — each of which is separately counted in `budget.exclusions` and echoed in `CONTEXT_EVIDENCE_FILTERED`, so no information is lost by folding them into one label. In the normal path all five are `0` (the adapter SQL-filters `secret`, emits one candidate per chunk, filters by `allowed`, and SQL-excludes `legacy-unverified` without the flag), so `truncated` means exactly the cap; when one of them is nonzero it is a defect or attack signal, and "retrieval matched it but it did not reach the bundle" is still the true statement — strictly more truthful than #346's "no eligible evidence" for every honest report (adversarial M bounded per §6.3 P3).

**Report validation (envelope-level, before use).** `validateEvidenceEnvelope` is widened from `(input)` to `(input, local)`; it is an internal function called from `assembleResolvedContext` (`:1637`), which already has `local` in scope, so no exported signature moves. Four rules over `report.required_selectors_with_matches`:

- **V1 — shape and order.** An array of at most `MAX_CONTEXT_SELECTORS` strings in **strictly ascending** code-point order, which enforces sorted-and-deduplicated in one check.
- **V2 — catalog containment.** Every id is present in `local.selectors` with `required === true`. Formally `M ⊆ required`. An unknown id, or a known id whose entry is not required, is a violation.
- **V3 — coverage containment.** Every required selector carried by **any** candidate in the envelope is in M: `{ s ∈ required : ∃ c ∈ input.candidates with s ∈ c.selectors } ⊆ M`. This is derivable from the envelope and the local catalog alone, and it is exactly §6.1 step 4's adapter-side invariant restricted to `delivered`. A violation means the report **contradicts the candidate array it shipped with** — provably wrong, not merely stale. The check reads only string entries of `c.selectors` and skips structurally malformed candidates (which `evaluateCandidates` catches later as `malformed`), so it can only under-check, never false-positive.
- **V4 — status.** When `status !== 'seeded'`, M must be empty.

Validation runs in two places for the same reason `validateEvidenceEnvelope` already exists: the retriever wrapper `resolveWorkspaceContextWithRetrieval` validates the returned envelope **before** the assembler sees it and, on violation, substitutes `status: 'unavailable'` with `unavailable_reason: 'query-failed'` — the existing containment rule, so an incoherent adapter never produces a fatal context; and `validateEvidenceEnvelope` re-checks as the assembler's own defensive gate, so a caller hand-building an envelope for `assembleWorkspaceContext` gets the existing evidence failure rather than a silent mislabel.

Both counters ride mandatory carriers: `ContextBudget` is emitted unconditionally, and the two diagnostics in §8 are mandatory. Budget pressure can drop the optional `CONTEXT_EVIDENCE_FILTERED` echo without erasing the distinction.

### 6.3 The trust boundary, stated as an invariant (B7)

Truncation knowledge exists only where truncation happens: the assembler never sees `P`, so it cannot recompute M, and no amount of envelope validation can. Rather than leave that implicit, it is stated as three properties — two proved, one documented — and all three are in the test matrix.

**P1 — shortfall visibility, unconditional over validated envelopes** (round-5 qualification: P1 quantifies over every M that passes V1–V4 on a `status: 'seeded'` envelope; a V2/V3-invalid M never reaches the partition — the envelope is converted to `unavailable` with both counters zero, which is the containment path, not a partition). `truncatedSet ⊎ unmatchedSet = missing`, disjointly, for **every** value of M: the empty set, the full catalog, and any arbitrarily wrong set. `missing` is computed from `bundleCoverage` and `local.selectors` **before M is read**, so M appears only in the partition and can never change `|missing|`. Every required selector with no eligible evidence in the bundle is therefore counted exactly once, in exactly one counter, and — because each counter is nonzero-triggered on a **mandatory** warning (§8) — at least one mandatory warning always fires when anything is missing. A wrong M can degrade the *label*; it can never reduce, hide, or split the *shortfall*.

**P2 — no fabrication.** A required selector that **is** covered in the bundle is never reported in either counter, whatever M says, for the same reason: it is not in `missing`. The report cannot invent a shortfall. (This is the case Revision 4 already tested; it survives verbatim.)

**P3 — the residual, and its exact shape.** Which of the two labels a missing selector receives depends on M, and M is the adapter's own honest signal about its own pool. This is deliberate and irreducible. The design reduces it to the minimum: **one** field instead of two claims; a **partition** instead of an intersection, so the labels can never contradict; **V2** so M cannot name anything outside the required catalog; **V3** so M cannot contradict the candidates shipped beside it; and the same containment asserted adapter-side in §6.1 so a violation is caught at the source. What remains is exactly two mislabelings, both tested:

- *Under-reported M* (blocker case 1 — a stale report omits a genuinely truncated selector): the selector moves from `truncated` to `unmatched`. Direction of error is **conservative** — `CONTEXT_REQUIRED_EVIDENCE_MISSING` is the more alarming reading ("no evidence exists", remedy "ingest current cited evidence") than `CONTEXT_REQUIRED_EVIDENCE_TRUNCATED`. Total is exact.
- *Over-reported M* (blocker case 2 — a report names a required-but-unmatched selector): the selector moves from `unmatched` to `truncated`. Direction of error understates severity, but the selector still emits a mandatory warning whose remedy is "narrow the request or raise the retrieval candidate budget" — and an operator who narrows the request lands on a smaller `P`, where the selector reappears as `unmatched`. The degradation is bounded; a stale or adversarial adapter is not forced honest by retry — the guarantee is only that the selector stays visible under a mandatory warning (round-5 qualification).

Neither case changes `|missing|`, neither suppresses a warning, and neither can be reached by an honest adapter. This is the trust boundary; it is documented rather than papered over.

**Assembler comparator with the legacy floor** (retained from Revision 2, confirmed sound):

```
legacy asc  (legacy-unverified = 1, else 0)
→ required desc → trustRank asc  (index in CONTEXT_TRUST_CLASSES, src/lib/context-trust.ts:1-11)
→ exact desc → overlap desc → retrieval_rank asc → scope desc → candidate_id asc
```

`legacy-unverified` always ranks below every non-legacy candidate regardless of required intent; within non-legacy, required intent dominates; within equal required-ness, trust-class order decides.

**Privacy and trust.** `privacy_class = 'secret'` is filtered in SQL and independently mapped to `privacy-incompatible` (`:1519-1520`); `internal` and `public` both return with `privacy` on the fragment (`spec/SPEC.md:783`). `legacy-unverified` is SQL-excluded by default; with `--include-legacy-unverified` it returns, labelled, floored, and confined to `brain_evidence`. A `legacy-unverified` candidate arriving without the flag is rejected with the reserved `unauthorized` reason (`:83`), normally 0 and acting as a leak detector.

**Citation envelope per result:** derived `scope`; `trust`; `inclusion_reason`/`retrieval_reason`; `privacy`; `retrieval_modes`; and `citation = { logical_source_id, source_version_id, object_id, extractor_id, extractor_version, locator, content_hash }`, where extractor identity comes from the durable active registry and `content_hash = 'sha256:' + content_sha256` **over the candidate's rendered content**. The locator discriminates on extractor kind (amended post-implementation-round-2, reviewer-confirmed round 3, because #370's structured extractor deliberately assigns whole-object regions to rendered projections — `extractors.ts:352-354` — so a universal exact-re-slice claim was false for structured records): `roster-text` chunks use `'chunk:<chunk_id>#<idx>@bytes:<a>-<b>;lines:<a>-<b>'` where the content **is** the byte slice (exact re-slice proof holds); `roster-structured` chunks use `'chunk:<chunk_id>#<idx>@object:<a>-<b>'` where the region is the exact citable source region the rendered projection derives from — the region hashes to `object_id`, `content_hash` covers the rendered content matching the durable `source_chunks` row, and the region is deliberately **not** byte-equal to the content. Both forms satisfy `safeCitationLocator`; no structured locator may carry `@bytes:`.

## 9. `BRAIN_CONFIGURATION_INCOMPLETE`, confined to the context path (B5)

**Why the parse-time change is abandoned.** `parseBrainConfig` reaches `schemaFailure` → `YAML_INVALID` (`workspace-record.ts:220-222`, `:329-331`) for an absent `storage` or `secrets_path`. Changing the thrown code there would propagate to `discover` and `scaffold`, which fail immediately on a registry parse throw, and to `validate`, which cannot then inspect the remaining local records — conflicting with `spec/SPEC.md:166,336`, which require local operations to stay available under partial Brain configuration. The reviewer is right; Revision 2's "acknowledged risk" did not resolve it.

**Design.** A *representation* + a *caller policy*, with the behavior of the other three readers held byte-identical:

1. **Representation.** `parseBrainConfig` keeps its thrown **code (`YAML_INVALID`), message, and remedy exactly as today**. The only edit is one additive, typed `details` discriminator that no existing reader consumes:
   `details.brain_configuration = 'incomplete'` and `details.missing = [<sorted field names>]`, emitted only when the `brain` block is present and a completeness field — `secrets_path`, `storage`, `storage.bucket`, `storage.region` — is **absent**. Wrong-typed or bad-valued fields carry no discriminator and stay ordinary `YAML_INVALID`. No value is ever echoed.
2. **Caller policy.** Exactly one consumer: `sanitizeContextFailure` (`workspace-context.ts:2391-2409`), the context command's single choke point (`src/commands/context.ts:24`). When `isWorkspaceFailure(error) && error.code === 'YAML_INVALID' && error.details.brain_configuration === 'incomplete'`, it returns a freshly constructed `workspaceFailure('BRAIN_CONFIGURATION_INCOMPLETE', <fixed message>, <fixed remedy>, { missing })` — details built explicitly, not through `sanitizedDetails`, so no unrelated key leaks. Because the failure originates at registry parse, `roster context` exits nonzero with **no bundle** having contacted neither store (`spec/SPEC.md:166`). `discover`, `scaffold`, and `validate` never read the discriminator and keep today's behavior.
3. **Registration.** Add `BRAIN_CONFIGURATION_INCOMPLETE` to `WORKSPACE_DIAGNOSTIC_CODES` (`src/lib/workspace-diagnostics.ts:3-53`) and a fixed entry to `SANITIZED_CONTEXT_FAILURES`.
4. **Tests for all three other readers.** For each of `discover`, `scaffold`, `validate`, against a workspace missing `brain.storage` and again missing `brain.secrets_path`: assert the emitted envelope's `code`, `message`, `remedy`, and process exit status are **byte-identical to the pre-change baseline** (golden strings captured from `origin/main`). Plus a context test asserting the stable fatal code, nonzero exit, absent bundle, sorted `details.missing`, and — via a spy on the pool factory — that no connection was attempted.
5. **Scope note, stated plainly.** `spec/SPEC.md:336` additionally wants `roster validate` to report local structural results *and then* exit nonzero with this code. Validate throws today, so #352 does not regress it and does not claim to fix it; that partial-report work stays with #383.

## 10. The v1 → v2 cited structured-record contract (B6, B8)

Acceptance 5 names v1 table names (`001_init.sql:15-47`) that carry no `source_version_id` and cannot be cited. #352 therefore defines the **durable retrieval-side contract** for v2 structured records: the shape #383's semantic writes must produce and #384's backfill must satisfy. It adds no tables — these are `structured-record` logical sources (an existing `source_kind`, `011:32`) extracted by `roster-structured` into `source_extractions.structured` plus rendered chunks (`src/lib/brain/extractors.ts:321-380`).

### 10.1 Why Revision 3's interpolated identity was not implementable

v1 `entities.kind`, `entities.slug`, `facts.key`, and `edges.rel` are plain `text NOT NULL` with **no CHECK** (`001_init.sql:18-19`, `:29`, `:46`) — any Unicode string of any length, including `/`, `:`, `#`, whitespace, control characters, and values well past 256 bytes. `SourceOriginInput.stableKey` is validated against `STABLE_KEY = /^[A-Za-z0-9][A-Za-z0-9._:@/+~-]*$/u` at `MAX_SOURCE_STABLE_KEY_BYTES = 256` (`source-contracts.ts:41`, `:56`, `:376`). Revision 3's `entity:<kind>/<slug>` is therefore neither **total** (forbidden characters, oversize values) nor **injective** (a slug containing `/` collides with a different `(kind, slug)` pair). Interpolation is abandoned for a hash-based derivation, the construction #384 already uses for file addresses.

### 10.2 Canonical identity — exact, total, bounded

One additive pure export in `src/lib/brain/source-identity.ts`, the module that already owns domain-separated canonical digests (`canonicalDigest`, `:38-40`) and already imports `node:crypto` and `canonicalSourceJson` (`:1-9`). No new dependency, no new file.

```ts
export const LEGACY_RECORD_DOMAIN = 'roster.brain.legacy-record.v1';

export type LegacyRecordKey =
  | Readonly<{ kind: 'entity'; entityKind: string; slug: string }>
  | Readonly<{ kind: 'fact'; entityKind: string; slug: string; key: string }>
  | Readonly<{ kind: 'event'; id: string }>            // canonical decimal bigint, §10.4
  | Readonly<{ kind: 'edge'; fromKind: string; fromSlug: string; rel: string;
                             toKind: string; toSlug: string }>;

export function legacyRecordStableKey(record: LegacyRecordKey): string {
  const tuple: readonly string[] =
      record.kind === 'entity' ? ['entity', record.entityKind, record.slug]
    : record.kind === 'fact'   ? ['fact', record.entityKind, record.slug, record.key]
    : record.kind === 'event'  ? ['event', record.id]
    :                            ['edge', record.fromKind, record.fromSlug, record.rel,
                                          record.toKind, record.toSlug];
  const hex = createHash('sha256')
    .update(canonicalSourceJson({ domain: LEGACY_RECORD_DOMAIN, value: tuple as SourceJsonValue }), 'utf8')
    .digest('hex');
  return `legacy.${record.kind}.v1:${hex}`;
}
```

Four checkable properties:

- **Grammar and bound.** `^legacy\.(entity|fact|event|edge)\.v1:[0-9a-f]{64}$`. Every character is inside the `STABLE_KEY` class and the first is `l`; the longest form is `legacy.entity.v1:` (17 bytes) + 64 = **81 bytes**, far under 256. Conformance holds for *every* input, so ingest can never refuse a legacy record on key shape.
- **Total.** The only variable-length inputs sit inside the digest. `canonicalSourceJson` delegates strings to `JSON.stringify` (`source-contracts.ts:266-275`), which is total over every JS string (well-formed stringify escapes lone surrogates), so no v1 text is unrepresentable and nothing needs rejecting, truncating, or escaping.
- **Injective / delimiter-free.** The preimage is a canonical JSON **array of strings**, never a concatenation, so no delimiter is interpretable: `["entity","a/b","c"]` and `["entity","a","b/c"]` are distinct preimages. This is exactly the construction already shipped as `legacyRelationIdentity` (`src/lib/brain/legacy-inventory.ts:215-216`). The leading tuple element plus the `domain` wrapper give cross-kind and cross-purpose separation, matching `LOGICAL_SOURCE_DOMAIN` / `SOURCE_VERSION_DOMAIN` practice (`source-identity.ts:12-15`).
- **Collision.** Rests on the same sha256 assumption already load-bearing for `source_id` and `origin_fingerprint` (`011:31`, `:35`) and for `content_hash`.

An **entity reference** inside a body is the referenced entity's own identity string (`legacy.entity.v1:<hex>`) — never a bigint id, which is not portable across databases, and never an interpolated `kind/slug`. The raw pair travels beside it as body data (§10.3) so lexical retrieval still works on human text.

Reserved but outside #352's proof: `legacy.alias.v1`, `legacy.merge.v1`, and `legacy.document.v1` are reserved for #384's remaining relations (`005_dedup_merge.sql:3-22`, `001_init.sql:50-56`). #352 pins only the four kinds acceptance 5 names.

### 10.3 Envelope and per-kind body

```jsonc
{ "envelope": "roster.brain.record.v1",
  "kind": "entity" | "fact" | "event" | "edge",
  "identity": "<legacyRecordStableKey(...)>",   // == the ingest source stableKey
  "body": { /* per-kind, below */ },
  "legacy": { /* §10.4 — present only on #384 backfill, absent on #383 native writes */ } }
```

| kind | identity tuple | `body` members | v1 source columns |
|---|---|---|---|
| `entity` | `["entity", kind, slug]` | `{ kind, slug, title, body }` — **no `asserted`** | `entities.kind`, `.slug`, `.title`, `.body` (`001:18-21`); natural key `UNIQUE (kind, slug)` (`001:22`) |
| `fact` | `["fact", entityKind, entitySlug, key]` | `{ subject, subject_kind, subject_slug, key, value, asserted }` | `facts.entity_id` resolved to the owning entity's `(kind, slug)`, `.key`, `.value` (`001:28-30`); `asserted = { source, confidence, actor }` (`003:4-6`) |
| `event` | `["event", id]` | `{ subject, subject_kind, subject_slug, kind, payload, event_key, asserted }` | `events.entity_id`, `.kind`, `.payload` (`001:36-38`); `asserted = { actor }` (`003:8`) |
| `edge` | `["edge", fromKind, fromSlug, rel, toKind, toSlug]` | `{ from, from_kind, from_slug, to, to_kind, to_slug, rel, props, asserted }` | `edges.src_id`, `.dst_id`, `.rel`, `.props` (`001:44-46`); `asserted = { actor }` (`003:10`); natural key `(src, dst, rel)` matching `current_edges` (`001:64-67`) |

`subject` / `from` / `to` are entity-reference strings; `*_kind` / `*_slug` carry the raw v1 text verbatim. `subject` is `null` for a subjectless event (`events.entity_id` is nullable, `001:36`), in which case `subject_kind` and `subject_slug` are `null` too. Entity ids resolve through `entities.id`, **not** `entities.canonical_id` — a later merge must not retroactively change a fact's or edge's logical-source identity; merges are their own records (`008_canonical_id_and_merge.sql`). §10.4 item 3 turns that sentence into a proved property.

**Attribution — the Revision-3 contradiction, fixed.** Revision 3's prose said `events.actor` and `edges.actor` map into `body.asserted` while its own table listed `event` and `edge` bodies without an `asserted` member. The schema is not at fault: both columns exist (`003_attribution.sql:8`, `:10`). `asserted` is now present on `fact`, `event`, and `edge`, and explicitly **absent** from `entity`, because `003_attribution.sql` alters only `facts`, `events`, and `edges` and adds nothing to `brain.entities`. Every `asserted` member is emitted with an explicit `null` when the v1 column is NULL, so the shape is fixed rather than optional. All of it stays caller-asserted and untrusted (`003:1-3`) and carries **no** authority; real provenance is the 011 source-version envelope — `actor_assurance`, `provenance`, `trust_class`, `privacy_class`, labels — and backfilled records take `trust_class = 'legacy-unverified'` (`011:69-77`), so they are default-excluded by §6 and floored when explicitly requested.

### 10.4 Ids, timestamps, version ordering, and the merge view (#384 history parity) (B6, B8)

#384's acceptance requires preserving "stable IDs/timestamps/redirects". Three additions make that expressible without touching identity.

1. **The `legacy` member**, present only on backfilled records:

```jsonc
"legacy": {
  "table": "entities" | "facts" | "events" | "edges",
  "id": "12345",                                  // /^(0|[1-9][0-9]*)$/ — canonical decimal, no sign, no leading zeros
  "recorded_at": "2024-01-31T09:15:00.000Z"       // RFC3339 UTC, exactly 3 fractional digits, literal 'Z'
}
```

`id` is a **string**, never a JSON number: v1 ids are `bigint GENERATED ALWAYS` (`001:16`, `:26`, `:34`, `:42`) and JSON numbers lose precision past 2^53, which `canonicalSourceJson` would silently bake into any digest computed over them. The timestamp form is the narrowest shape accepted by the `RFC3339` pattern at `source-contracts.ts:61` (which permits 1–3 fractional digits), pinned to exactly 3 and to UTC so it is byte-canonical. The same instant is also the source version's `source_timestamp`.

2. **Version ordering.** v1 last-write-wins resolves by **`id DESC`**, not by `recorded_at`: `current_facts` is `DISTINCT ON (entity_id, key) … ORDER BY entity_id, key, id DESC` (`001:59-62`) and `current_edges` is `DISTINCT ON (src_id, dst_id, rel) … ORDER BY src_id, dst_id, rel, id DESC` (`001:64-67`). Therefore #384 publishes, per logical source, **one `source_versions` row per v1 row in ascending `id` order**, and never orders by `recorded_at` — a `DEFAULT now()` timestamptz that can tie or invert under clock adjustment and is explicitly *not* what the v1 views use. After replay, each logical source's `current_version_id` is the v1 row with the greatest `id`, giving row-by-row parity with the v1 view that a test can assert directly.
   - `entity`: `UNIQUE (kind, slug)` yields one row per identity, hence exactly one version.
   - `event`: identity is per-row, hence exactly one version per event logical source; there is no ordering question.
   - `fact` / `edge`: multiple versions, ordered as above; the sequence number is the ascending publish order.

`body.event_key` exists so #383's native writes can carry a caller-supplied natural key; for #384 backfill it is exactly the decimal `id` string (digits only, so no escaping question arises). Revision 3's "derived by #384 from the v1 `(id, recorded_at)` pair" is **withdrawn**: `id` alone is the primary key (`001:34`), so pairing it with `recorded_at` added no uniqueness and had no canonical encoding. `recorded_at` is preserved in `legacy.recorded_at` and in `source_timestamp`, which is where history parity belongs.

3. **The merge view — `brain.resolved_current_facts` (B8).** Item 2 pins `current_facts` and `current_edges`, both of which group by **raw** entity identity, matching §10.3's identity rule. The merge-aware view does not: it groups by the **canonical** entity while v2 fact identity stays keyed on the raw `(entityKind, slug, key)` triple, so it needs its own property and its own fixture. Its definition, verbatim (`008_canonical_id_and_merge.sql:174-179`):

```sql
CREATE OR REPLACE VIEW brain.resolved_current_facts AS
  SELECT DISTINCT ON (en.canonical_id, f.key)
         f.id, f.recorded_at, en.canonical_id, f.key, f.value, f.source, f.confidence, f.actor
  FROM brain.facts f
  JOIN brain.entities en ON en.id = f.entity_id
  ORDER BY en.canonical_id, f.key, f.id DESC;
```

Migration 008 replaced 005's function-based definition (`005_dedup_merge.sql:72-76`, which called the STABLE `brain.canonical_id(entity_id)` per row) with this join over the materialized `entities.canonical_id` column (`008:14` added, `008:35` `SET NOT NULL`, `008:37` indexed, filled by the `entities_set_canonical_trg` BEFORE INSERT trigger at `008:31-33`). **The ordering key is `f.id DESC` in both definitions**, so the property below is stable across the migration and does not depend on which one a given database has applied.

**Property M1 — the winner.** For a canonical group `G = { e ∈ brain.entities : e.canonical_id = g }` and a key `k`, the view selects the fact row with the **globally greatest `facts.id`** among `{ f : f.entity_id ∈ G, f.key = k }` — greatest across *all* merged members, not greatest per member.

**Property M2 — parity after replay.** After ascending-id replay, that winner is the `current_version_id` of exactly **one** member logical source: the member whose own head carries the greatest `legacy.id`. Equivalently, the v2 side recomputes the view's winner without any merge-specific replay rule — take the `current_version_id` of every member source `legacy.fact.v1:sha256(["fact", kind(e), slug(e), k])` for `e ∈ G`, read each head's `legacy.id`, compare them **numerically as bigints** (they are canonical decimal strings per item 1, so no precision is lost and no lexicographic surprise arises), and take the greatest.

**Proof.** Four steps.

   (i) *Fact logical sources are merge-invariant.* Identity is `["fact", entityKind, entitySlug, key]` over `entities.id`, never `entities.canonical_id` (§10.3). `brain.merge_entities` writes only `brain.entity_merges` and `brain.entity_aliases` (`008:144-160`) and then calls `brain.refresh_canonical` (`008:162`), which updates only the `canonical_id` column (`008:71-74`). It never mutates `entities.kind` or `entities.slug` of either member. So a merge creates no logical source, destroys none, splits none, and merges none — every member of `G` keeps its own per-key source with the same id it had before the merge.

   (ii) *Per-source head.* Item 2 already proves each logical source's `current_version_id` is the row with the greatest `facts.id` of that source, because replay publishes one version per row in ascending `id` order.

   (iii) *The view orders on `facts.id` alone.* `DISTINCT ON (en.canonical_id, f.key) … ORDER BY en.canonical_id, f.key, f.id DESC` has exactly one tiebreak column after the two grouping columns. `recorded_at`, `value`, `source`, `confidence`, and `actor` are projected but never ordered on, so no clock skew, no value, and no attribution can move the winner. Replay preserves `facts.id` verbatim in `legacy.id` (item 1), so the sole ordering key survives the v1→v2 mapping unchanged.

   (iv) *Max decomposes over a partition.* By (i), `{ f : f.entity_id ∈ G, f.key = k }` is partitioned by `entity_id` into the member sources. `max` over a union equals the max of the per-part maxima; the per-part maxima are exactly the heads of (ii). Therefore the view's winner is the greatest of the member heads, which is M2, and it is the global maximum, which is M1. ∎

**Scope of the property, stated so nothing is silently assumed.**

   (a) *Merge records stay outside this proof, and that is safe.* The grouping column `en.canonical_id` is **state**, recomputed by `brain.refresh_canonical` from the append-only merge map over reverse reachability (`008:62-74`), so it is transitive and order-independent. It is not version history and no replay ordering affects it. #352 pins only the negative claim the proof needs — that the grouping cannot affect the per-source ordering — and that is (iii). Replaying merges as their own records (`legacy.merge.v1`, reserved in §10.2) is #384's work, not #352's, and cannot invalidate M1/M2 because it adds records without touching `facts.id`.

   (b) *There is no `brain.resolved_current_edges`.* Migrations 005 and 008 define a merge-resolved view for **facts only**; `brain.current_edges` (`001:64-67`) stays keyed on raw `(src_id, dst_id, rel)`. Edge parity from item 2 is therefore merge-independent by construction. The fixture pins this absence with `to_regclass` rather than assuming it, so a future migration that adds such a view fails the test instead of silently escaping the proof.

   (c) *The one way a backfill can break M2.* Keying facts on the **canonical** `(kind, slug)` instead of the raw pair collapses two members into a single logical source. That still happens to select the same winning `facts.id` — which is precisely why the winner assertion alone would not catch it — but it makes `logical_source_id` change retroactively when a later merge lands, violating the immutability acceptance 4 depends on. The fixture asserts pre-merge/post-merge identity equality specifically to catch this, and step 8 of the test is the negative that must fail.

### 10.5 Retrieval consequence

The structured arm's value-equality jsonpath matches `envelope`, `kind`, and `identity` — `identity` is a fixed-shape ASCII token, an ideal equality key — so a record kind is selectable without lexical matching. Because identity is a digest, a caller addresses a specific record only by recomputing `legacyRecordStableKey` from the exact tuple; human-text search goes through the raw `kind` / `slug` / `key` / `rel` fields in the body and through the rendered chunks. Both paths cite one immutable `source_version_id`.

Acceptance 5's proof is unchanged in shape: a PG-gated test ingesting one entity, one fact, one event, one edge and one Markdown document, asserting a single bounded bundle containing all five with complete, distinct, lossless envelopes — plus a shape test pinning, per kind, the identity grammar, `STABLE_KEY` conformance, the ≤256-byte bound, the required `body` members (including exactly which kinds carry `asserted`), and the `legacy` member's decimal-id and RFC3339 forms, so #383 and #384 have an executable contract to code against.

## RISKS

1. **Label↔version correlation remains the one eligibility guarantee the pure assembler cannot provide.** *Mitigation:* the correlated `LATERAL` projection plus the §5.4 mutation test, which now targets that exact predicate and asserts raw `label_keys` and fixture-computed scope so a wrong correlation cannot hide behind a right-looking outcome; the allowlist stays a bound `text[]` of exact generated strings with no `LIKE` or constructed predicate; the assembler re-derives eligibility and scope from local state so any shape error degrades to a counted `scope-ineligible`.

2. **Refactoring #370's memoized helpers could regress extraction paths.** `assertBrainExtractionRegistry`'s `WeakMap` caching and error details are load-bearing for #370's write paths. *Mitigation:* the new `*OnClient` functions are additive and the existing exports become thin delegations that keep the same memoization, code, and `details`; Phase C lands with tests proving behavioral identity before any #352 code depends on them.

3. **Public contract widening breaks the host harness and seeded fixtures.** `selectors`, `label_keys`, `trust`, `retrieval_modes`, the `report` member, the new `request` key, and two new diagnostic codes collide with exact-key assertions (`test/support/host-led-learning-adapter.ts:830-846`, `:938`, `:989-1004`). *Mitigation:* every widening is additive and closed-union; Phase A lands the contract change and harness update **before** the adapter exists; `CONTEXT_TRUST_CLASSES` and `CONTEXT_EXCLUSION_REASONS` stay single sources of truth. Adding `required_selectors_truncated` to `ContextBudget` also moves `BUDGET_BLOCK_RESERVE_BYTES`/`TOKENS` and `MIN_CONTEXT_BUDGET_TOKENS`; every reference is symbolic (`src/lib/context-args.ts:144,148`; `test/context-args.test.ts:108,110,125`) so only the two constants and the key-order assertion at `test/workspace-context.test.ts:1404-1420,1443` change. Revision 5 adds no further budget key.

4. **Phase 0 may show the structured or vector arm is unindexable or too slow at scale.** *Mitigation:* real plans are recorded for the exact predicates before any code depends on them; the embedding arm is optional and inert in production (`EMBEDDING_ADAPTERS` empty); the lexical baseline required by acceptance 3 is unaffected; ANN is deferred to a post-#353 ticket rather than solved with a non-provider-neutral index.

5. **The `details` discriminator is a cross-cutting edit to the registry parser.** A future reader could start consuming it and silently change behavior. *Mitigation:* the caller policy is written into the plan and enforced by a static test asserting `sanitizeContextFailure` is the **only** production consumer of `details.brain_configuration`, plus the three-reader byte-identity baselines that fail if any other command's envelope shifts.

6. **The greedy reservation pass is not an optimal set cover, so it can consume more slots than a perfect solver would.** *Mitigation:* optimal set cover is NP-hard and out of scope, and correctness never depends on optimality — the shortfall is derived from the **bundle** rather than from the heuristic, so any slot the greedy pass wastes is reported honestly instead of being laundered into a false "no eligible evidence" claim. The tested invariant (`|M| ≤ 64` with all delivered candidates eligible ⇒ no truncation) bounds the failure mode to genuine overflow, and the overlap non-waste test fails outright if the `covered` set is removed.

7. **M is the adapter's own signal about its own pool, and the assembler cannot recompute it.** A wrong M mislabels a missing selector as truncated or unmatched. *Mitigation, and the explicit limit of the mitigation:* §6.3 states the boundary as three properties. P1 and P2 are proved for every M that passes V1–V4 on a `seeded` envelope — the shortfall total is exact and always visible, because `missing` is computed from the bundle before M is read, and each counter triggers a **mandatory** warning (an invalid M never reaches the partition; it degrades to `unavailable` with zero counters). P3 is the residual and is documented rather than hidden: it is reduced to one report field (not two claims), a partition (not an intersection, so the labels cannot contradict and a selector cannot be both), catalog containment V2, delivered-candidate containment V3 — which makes an M that contradicts its own candidate array a **detectable invalid envelope** — and the same containment asserted adapter-side so a violation is a caught defect at the source. Both misdirection directions are pinned by tests 7 and 8; neither forces a stale or adversarial adapter honest — the guarantee is shortfall visibility, not label correctness (§6.3 P3). Anything stronger would require the adapter to ship its entire pre-cap pool `P` across the boundary, which the 64-candidate and 16 MiB bounds exist to prevent.

8. **The merge view groups by canonical entity while fact identity is keyed on the raw entity, so #384 could satisfy `current_facts` parity and still break `resolved_current_facts`.** *Mitigation:* §10.4 item 3 proves M1/M2 from the view's verbatim definition, resting only on facts that a backfill cannot change — merge-invariance of `(kind, slug)` under `brain.merge_entities` (`008:144-162`), the view's single `f.id DESC` tiebreak, and `legacy.id` preserving `facts.id` verbatim. The ten-step fixture makes it falsifiable: the winner deliberately belongs to the **merged-away** member, id order and `recorded_at` order deliberately disagree, and two negatives must fail — replay ordered by `recorded_at`, and replay keyed on the canonical `(kind, slug)`. The second negative exists because the canonical-keying defect still selects the *right* winning id and would otherwise pass; only pre-merge/post-merge identity equality catches it. Scope is bounded explicitly: merge rows are `legacy.merge.v1` (#384's work, and additive to `facts.id`-independent state), and `to_regclass('brain.resolved_current_edges') IS NULL` is asserted rather than assumed so a future resolved-edges view fails this suite instead of escaping the proof.

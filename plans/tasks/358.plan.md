## 5. The lifecycle verbs, brokers, and the runtime-grant answer

### 5.1 Verb → role → transport

Unchanged from R2: all five verbs on the runtime pool; `list` mirrors `executeDreamStatus`'s local-only tolerance (`src/commands/dream.ts:49-71`); `create` = broker `record_dream_candidate(text)`; `promote`/`reject`/`retire` = broker `decide_lesson_candidate(text)` (+ Git materialization/removal for promote/retire, run under the held subject lock + the local dream-phase lock, §8).

### 5.2 Broker discipline

Both brokers follow `record_completed_run` (`013:648` onward): one `text` parameter carrying the exact canonical bytes; `assert_keys` closed field set; per-field `assert_*`; advisory locks; `INSERT … ON CONFLICT DO NOTHING`; byte-compare replay; `RETURNS TABLE (status, …)`; terminal `EXCEPTION` block.

**Isolation guard (R4, confirmed).** Both brokers — and the fence function and the verifier — begin by refusing any transaction isolation above READ COMMITTED: `IF current_setting('transaction_isolation') <> 'read committed' THEN RAISE … USING ERRCODE = 'RBE12'`. Grounding: a lock-then-read pattern is only sound when reads after the lock see the latest committed state; under READ COMMITTED each statement takes a fresh snapshot (`014:166-168`), while a REPEATABLE READ snapshot can predate the lock. 014 itself asserts the isolation level for its backfill (`014:185-192`). `RBE12` is a new code, not `RBE04` (§5.4). (The verifier carries the guard for the same reason: its governor read is only meaningful as a latest-committed-state read.)

**A/B/C preamble discipline (R5, review-confirmed), both brokers:** every check-bearing read happens **under** the locks, and the locks' components come from **server-held** state wherever server-held state exists:

- **(A) Identity resolution, no locks.** `decide_lesson_candidate` reads the `dream_candidates` row by the canonical's `candidate_id`; absent → `RBE03`; it extracts the server-held `lesson_agent_key`, `lesson_id`, and `scope_key`. The row is append-only (`reject_evidence_mutation`, §3.5) and its columns are never updated, so these values are immutable from the moment they are read — the read exists **solely to derive lock components**, and no correctness check runs against it. (An `RBE03` here can race the candidate's own concurrent create by microseconds; that is a caller-ordering bug whose re-run succeeds — deciding a candidate before its create committed is not a supported interleaving.) `record_dream_candidate` CREATES the row, so no server copy exists yet: its subject comes from the caller's canonical — **the asymmetry, stated explicitly:** create's subject values are its own canonical claim, validated by the closed grammars (`scope_key` per `014:287-289`; `lesson_scope_key` per §3.1; `lesson_agent_key` derived in the body by the *same expression* as the generated column, §3.1), and the create-time locks serialize against every other create/decide on the same derived subject. A caller that "lies" about the subject only mislocks its own new row — whose actual subject IS the derived value, because the generated column derives from the same `lesson_scope_key` bytes. There is nothing server-side to disagree with.
- **(B) Lock acquisition.** `pg_advisory_xact_lock`, fixed intra-rank order **subject → candidate → watermark**, components from the step-A server-derived values (decide) or the validated canonical values (create).
- **(C) Re-read under the locks.** Re-read the candidate row and `dream_candidate_state` (equivalently, the `lesson_decisions` ledger) and run **every** subsequent check — replay arbitration, transition table, binding, governance, allocation — against the re-read. For the append-only candidate row the re-read can only confirm what step A saw (stated for discipline, not necessity); for the mutable decision STATE the re-read is load-bearing: a decision could have committed between A and B, and only a post-lock read observes it (READ COMMITTED gives the fresh statement snapshot; the `RBE12` guard is what makes that true).
- **Replay-first discipline (confirmed), both brokers:** the first check inside (C) — before any state-transition, snapshot, damping, or binding check — is the lookup by derived identity and byte-compare of `record_canonical` (`013:778` / `014:481-486`). Identical → `'existing'`; different bytes → `RBE02`; absent → full validation. `decide_lesson_candidate`'s `'existing'` return carries the `subject_current` verdict (§5.3 step 12) — the replay return is not, by itself, an authorization to repeat filesystem effects.

**Advisory-lock domains and order** (framed as `013:36-60`; all rank 3 in 014's order, `014:41-47`):

```
roster.brain.dream.lock.subject.v1    ARRAY[lesson_agent_key, lesson_id]   -- NORMALIZED;
                                      -- ALSO held by hold_dream_subject_lock (§8.2)
roster.brain.dream.lock.candidate.v1  ARRAY[candidate_id]
(existing) roster.brain.dream.lock.watermark.v1  ARRAY[scope_key]   (014:472-474)
```

Fixed intra-rank acquisition order everywhere: **subject → candidate → watermark**. Both brokers take all three up front in step B; the nested `advance_dream_watermark` re-acquires the watermark lock it already holds — advisory locks stack within a session, so the nested acquisition cannot self-deadlock. **The fence function acquires ONLY the subject lock — a strict prefix of the order, so it introduces no new cycle possibility. The verifier acquires NO lock at all (§8.2) — it cannot participate in any cycle.** Same order in both brokers, each call touching one subject/candidate/scope → the total order admits no cycle; `register_dream_policy`'s rank-3 policy lock (`014:379-381`) is never held together with any of these (the brokers read `dream_policies` without it — safe, because policy rows are append-only and byte-immutable per version, `014:401-414`, and the built-in version is unreachable by registration on every supported path, §3.6b). `40P01` stays retryable under 014's contract (`014:66-73`).

The **normalized** subject lock is what makes cross-occasion and cross-plan candidates for one physical lesson file serialize as one subject — and what makes the `subject_sequence` allocation, the `subject_current` verdict, and the §8.2 filesystem-phase fence exact.

### 5.3 `decide_lesson_candidate`: the promotion binding

`advance_dream_watermark` is **never granted to the runtime role**. `decide_lesson_candidate(text)` is SECURITY DEFINER, granted to runtime, and calls it internally. #357's granted-to-nobody test (`brain-dream-schema.test.ts:66-89`) and doctor red-test (`:305-335`) stay green, unmodified.

Return shape (R4, confirmed): `RETURNS TABLE (status text, sequence integer, subject_sequence bigint, subject_current boolean, watermark_scope_key text, watermark_sequence bigint)`.

In one transaction, in this order:

1. Isolation guard (§5.2, `RBE12`); parse and closed-schema-validate the canonical record.
2. **(A) Identity resolution, no locks:** read `dream_candidates` by `candidate_id`; absent → `RBE03`; extract server-held `lesson_agent_key`, `lesson_id`, `scope_key`. Lock derivation only — no check runs against this read (§5.2).
3. **(B)** `pg_advisory_xact_lock`: subject (normalized, from step 2) → candidate → watermark (`scope_key`, from step 2).
4. **(C) Re-read under the locks:** re-read the candidate row (append-only ⇒ confirm-only; stated for discipline) and the candidate's `dream_candidate_state` / decision ledger. Every check from here on runs against this re-read.
5. **Replay arbitration:** look up `lesson_decisions` by `lesson_decision_id`; byte-identical → return `'existing'` **with the stored row's `subject_sequence` and the step-12 `subject_current` verdict**; different bytes → `RBE02`. `lesson_decision_id = evidenceDigest('roster.brain.dream.lesson-decision.v1', {workspace_id, candidate_id, decision, human_decision_id})`.
6. Enforce the transition table over the re-read state: `promote` requires `open`; `reject` requires `open`; `retire` requires `promoted`; any decision on `superseded` → `RBE10`; everything else → `RBE10`.
7. Load `human_decisions` by `human_decision_id`; absent → `RBE03`. Bind (`RBE08` on any mismatch): `answer` = `'approved'` (promote, retire) / `'rejected'` (reject); `actor_assurance = 'human-confirmed'`; `action->>'target'` = `candidate_id`; `action->>'effect'` ∈ `{'dream-candidate-promote','dream-candidate-reject','dream-candidate-retire'}` matching the verb; `action->>'scope'` = the candidate's `lesson_scope_key`; supplied `action_digest` = stored `human_decisions.action_digest` (`013:523`).
8. For `promote` — **current-policy/current-time revalidation with policy-identity pinning, all computed in ONE SQL statement** (one CTE tree with `captured AS (SELECT clock_timestamp() AS evaluated_at)` captured exactly once, mirroring `READINESS_SQL`'s capture pattern at `dream-readiness.ts:116-117` but on statement/real time; one statement = one snapshot per §5.2's grounding):
   - **(pin)** `dream_effective_policy(candidate.scope_key).policy_version = candidate.policy_version`, else `RBE07` with "policy changed since draft; re-run `roster dream status` and re-draft". **Version equality is content equality on every supported path (§3.6b, qualified per R5 NB-a):** every registered version is byte-immutable (`014:401-414`), and the built-in `'roster.dream.default.v1'` can never be registered, so when the pin passes, the effective policy used below is by construction the candidate's own policy: either the same immutable stored row, or the code-constant default on both sides. A later policy registration at the scope changes the effective version and promptly refuses here. (The fingerprint needs no SQL twin: version equality pins bytes; the fingerprint remains TS-verified at create, §6.6.)
   - **(a) frontier membership over the bound floor at real time:** `candidate.frontier_ordinal ∈ dream_eligible(candidate.scope_key, captured.evaluated_at, candidate.watermark_ordinal)`. Evidence-window aging refuses here — and because `evaluated_at` is `clock_timestamp()`, a caller who opened its transaction before expiry and invokes promotion later is refused too (`014:24-26`).
   - **(b) the FULL due predicate re-proved over the candidate's own snapshot:** over `E := dream_eligible(scope_key, evaluated_at, watermark_ordinal)` restricted to `ordinal <= frontier_ordinal`: completed-run count `>= min_completed_runs`, feedback count `>= min_feedback_records`, signal-mix count (the `dream-readiness.ts:195-198` filter) `>= min_signal_mix` — all against the pinned policy — and **cooldown inactive against the candidate's BOUND head**: the `dream_watermarks` row at `cursor_ordinal = candidate.watermark_ordinal` (vacuous at genesis 0), i.e. `evaluated_at >= bound_head.advanced_at + cooldown`. Any failure → `RBE07`. Post-015, `bound_head.advanced_at` is an insertion-time stamp (§3.6a), so this term measures the real elapsed time since the bound promotion. Two deliberate choices, retained: *(i)* the cooldown term binds to the bound head, not the current head, because the bound head's `advanced_at` is immutable so the condition is monotone in real time — re-checking against the *current* head would make candidate A's promotion render same-snapshot candidate B unpromotable, contradicting the endorsed same-snapshot convergence in step 10; *(ii)* frontier-**maximality** is deliberately not re-required against *now's* frontier — that is what allows a same-snapshot second promotion and consumes exactly the evidence the candidate cited. **Rejected alternative:** trusting the create-time proof forever would let evidence age out from under a months-old candidate — and let a superseding policy be ignored; rejected.
   - **(c) accompanies a promotion identity:** the advance happens only inside this broker, after steps 5–8 passed, and the decision insert in step 11 cannot be skipped — any failure rolls the advance back.
   - **(d) materialized-identity governance:** refuse `RBE10` when any **other** candidate with the same `(lesson_agent_key, lesson_id)` is currently in state `promoted`. Race-free under the normalized subject lock. Message (retained): "another candidate already governs this lesson file; retire it first". This fires **before** any watermark advance, so a cross-occasion or cross-plan double promotion never commits a second decision or advances a second scope's watermark; the Git-side arms in §8.2 remain as defense against out-of-band files only.
9. **Watermark-canonical field verification:** parse `v_doc->>'watermark_canonical'` as jsonb and compare **every** field of 014's closed nine-key set (`014:450-453`) against server-held values — `kind`/`schema_version`/`reason`/`actor_assurance` pinned constants; `scope_key`/`cursor_ordinal`/`policy_version` = candidate row; `consumed_completed_runs`/`consumed_feedback_records` = the candidate row's create-time server-verified columns, **not** a fresh recount (recounting is non-deterministic under window aging and would break the same-snapshot `existing` replay). Any mismatch → `RBE07`. (Confirmed deviation, retained: the canonical has no fingerprint key.) **`lesson_qualified_id` is additionally server-verified here:** it must equal `candidate.lesson_agent_key || '/playbook/' || candidate.lesson_id` — the exact `qualifiedRecordId` playbook grammar (`workspace-layout.ts:283`) — else `RBE08`. `lesson_content_hash` is shape-checked only: rendering+hashing live in TS by 013's no-hashing-in-SQL rule (`013:20-25`); its binding is the CLI's post-write verification (§8.2 step 9) + H4's render-determinism pin + the §8.3 doctor audit, and — durably — the retire-time server comparison below.
10. **Call `advance_dream_watermark(v_doc->>'watermark_canonical')`** (advance before insert; the nested watermark-lock acquisition stacks, §5.2). 014 owns replay/monotonicity: byte-identical replay of the current head → `'existing'` (`014:476-488`); an older snapshot after a newer promotion → `RBE05` → "snapshot already consumed; re-run `roster dream status` and re-draft". *Same-snapshot double promotion, retained as endorsed:* candidates A and B (different subjects, same scope) sharing `(W, F, policy_version, consumed counts)` produce byte-identical canonicals (`dream-contracts.ts:348-373`) → B's advance replays `'existing'` → B's promote succeeds; divergent counts or policy version → 014's `RBE02`, surfaced as "this snapshot was consumed under a different account; re-run status and re-draft". P4 pins both branches.
11. **Insert `lesson_decisions`** at `sequence = max+1` (per candidate, under the candidate lock) **and `subject_sequence = max+1` over the subject** (under the subject lock — every writer holds it, so the allocation is serialized; the §3.3 UNIQUE is the belt), with `lesson_agent_key`/`lesson_id` server-copied from the candidate row, `watermark_scope_key`/`watermark_sequence` = the advance's returned identity (satisfying the non-deferrable FK), `ON CONFLICT DO NOTHING` + byte-compare on `lesson_decision_id`. For promote: `lesson_qualified_id` (server-verified, step 9) and `lesson_content_hash` (caller-computed, shape-checked). **For `retire`:** load the candidate's **latest promote decision row** (it exists — step 6 required state `promoted`) and refuse `RBE08` unless the supplied `lesson_qualified_id` AND `lesson_content_hash` are byte-equal to that row's stored values; the retire row then stores those same values. The retirement ledger, the §8.5 removal gate, the §8.2 predecessor-cleanup arm, and the §8.3 doctor expectations are therefore all anchored to one committed promotion identity and cannot diverge.
12. **Subject-governor verdict (R4, confirmed):** compute, still under the subject lock, `subject_current := (this decision's subject_sequence = (SELECT max(subject_sequence) FROM lesson_decisions WHERE lesson_agent_key = … AND lesson_id = … AND decision IN ('promote','retire')))` and return it with the row. For a fresh promote/retire this is true by construction; for a replay (step 5) it compares the stored row's `subject_sequence` against the current materialization-ledger max, so a promote replayed after a later retire — or a retire replayed after a later successor promote — returns `'existing'` + `subject_current = false`, and the CLI performs **no filesystem work** (§8.2 fence 1). **Materialization-ledger restriction (R4, review-confirmed):** the comparison excludes `reject` rows — a `reject` decides an *open* candidate, which by the step-6 transition table was never materialized, so it cannot change file governorship; under an all-decisions rule a sibling's reject would flip a committed promote's replay to `false` and permanently strand its crash-interrupted materialization. `reject` rows still receive a `subject_sequence` (uniform allocation; the UNIQUE spans all decisions) and `reject` returns the computed verdict, which the CLI ignores (reject has no filesystem phase — and reject is legal only from `open`, so there is nothing to converge). P4 pins both the fence and the reject-does-not-strand case.

**Atomicity, stated plainly:** steps 1–12 are one transaction. A failure anywhere — including a crash after the advance but before the insert — rolls back both the watermark row and the decision row. Order within the transaction is dictated solely by the FK.

### 8.2 Promote sequence: the held-lock fence, the local dream-phase lock, fence-loss handling, and the convergence invariant (amended — blockers 1 + 2)

**Invariant (restated):** *after a committed promote decision, materialization is REQUIRED and REPLAYABLE **while that decision remains the subject's latest materialization-ledger entry**: re-running `roster dream candidates promote` with the same inputs converges — the decision replays `'existing'` (§5.3 step 5) and the Git write is re-attempted until the workspace matches the recorded `lesson_qualified_id`/`lesson_content_hash`. Once a later promote/retire supersedes it, the replay is a deliberate NO-OP: exit 0, no filesystem change, message "this decision was superseded by later lifecycle activity on this lesson; no filesystem change". No filesystem mutation begins unless the fence is verified alive AFTER the local dream-phase lock is held; a phase whose fence cannot be verified at its end reports **UNVERIFIED** with a nonzero exit and is NEVER reported as success.* The CLI treats decision status `'existing'` identically to `'created'` **only when the fence proves this decision is the current governor**.

**The fence broker — new 015 function:**

```
brain_evidence.hold_dream_subject_lock(p_candidate_id text)
  RETURNS TABLE (lesson_agent_key text, lesson_id text,
                 governor_candidate_id text, governor_decision text,
                 governor_subject_sequence bigint,
                 retired_content_hashes text[])   -- ordered subject_sequence DESC;
                                                  -- COALESCED, never NULL (R6 NB-b)
  -- SECURITY DEFINER, VOLATILE, pinned search_path. EXECUTE granted to runtime.
```

Body: isolation guard (`RBE12`, §5.2 — same lock-then-read grounding); read `dream_candidates` by `p_candidate_id` (absent → `RBE03`), extracting the server-held subject — the CLI never supplies subject values; `PERFORM pg_advisory_xact_lock(brain_evidence.lock_key('roster.brain.dream.lock.subject.v1', ARRAY[lesson_agent_key, lesson_id]))` — **the SAME frame both brokers acquire first (§5.2)**; then, under the held lock: **the governor row via `verify_dream_subject_governor` (below — one SQL spelling of the governor query, §3.4)** and the retired-content list:

```sql
SELECT coalesce(array_agg(d.lesson_content_hash ORDER BY d.subject_sequence DESC),
                ARRAY[]::text[])
  FROM brain_evidence.lesson_decisions d
 WHERE d.lesson_agent_key = $1 AND d.lesson_id = $2 AND d.decision = 'retire'
```

— a retire ROW's existence is the "retire is committed" predicate, and its stored hash equals its promote row's by server construction (§5.3 step 11), so this one query enumerates **every prior retired governor's recorded content**, in explicit ledger order. **The `coalesce` is load-bearing (R6 NB-b, review-confirmed):** `array_agg` over zero rows yields SQL NULL, and the first promotion of a subject has no retire rows — without the coalesce the CLI's hash-walk would receive NULL instead of the empty list.

**The read-only governor verifier — new 015 function (NEW — blocker 1(ii)/(iii)):**

```

  RETURNS TABLE (lesson_agent_key text, lesson_id text,
                 governor_candidate_id text, governor_decision text,
                 governor_subject_sequence bigint)
  -- STABLE, SECURITY INVOKER, pinned search_path. EXECUTE granted to runtime
  -- (pure reads over runtime-SELECTable relations, roles.ts:423 — same posture
  -- as dream_effective_policy/dream_eligible). Acquires NO advisory lock and
  -- issues NO pg_advisory_* call of any kind — the property the deadlock-freedom
```

### 8.5 Retire (membership-first, replay-tolerant, server-bound, fence- and phase-serialized)

Gated on a durable human-confirmed retire decision; state `promoted` required; the supplied `lesson_qualified_id`/`lesson_content_hash` are server-compared against the candidate's stored promote row and refused `RBE08` on any mismatch (§5.3 step 11), so the removal below is always gated on the exact committed promotion identity.

1. `decide_lesson_candidate(decision='retire')` — replay-first, so a re-run returns `'existing'` and proceeds. **Fence 1 (courtesy):** `subject_current = false` → exit 0 no-op ("superseded by later lifecycle activity").
2. **Open the fence** via the same `withSubjectFence` helper: dedicated client, error listener, `BEGIN`, SET LOCALs, `hold_dream_subject_lock(candidate_id)`. **Fence 2 (authoritative):** require `governor_candidate_id = candidate_id AND governor_decision = 'retire' AND governor_subject_sequence = subject_sequence`; otherwise `ROLLBACK`, release, exit 0 no-op. This eliminates the R4 inversion in both directions: a retire filesystem phase delayed past a successor's promote finds the successor as governor and no-ops before removing anything — **even when the successor re-promoted byte-identical content** (the fence is ordering-based, not hash-based); and once this fence is open, the successor's promote broker *blocks at the subject lock* until the retire's phase commits.
3. **Acquire the dream-phase lock; pre-phase `verify_dream_subject_governor` (blocker 1):** identical to §8.2 steps 6–7 — busy → rollback/release/exit-busy; verification failure → **UNVERIFIED (no mutation performed)**, nonzero. This is what closes the round-6 counterexample for retire specifically: a retire whose fence died before its phase can NEVER strip a successor's membership or delete its byte-identical file — either its pre-phase check fails (fence dead — the only world where the successor could have promoted), or the successor's phase is excluded until this one ends and then converges its residue.
4. **Filesystem phase — under ONE `withWorkspaceLock` wrapper, entirely synchronous, under the dream-phase lock** (neither primitive locks itself; no scaffold is called here), in this order:
   a. **Membership removal:** `removeYamlMembership` (new twin of `addYamlMembership`, `workspace-record.ts:813-828`; returns text unchanged if already absent) via `replaceWorkspaceFile` on the agent file with its expected hash.
   b. **Then hash-gated file removal:** `removeManagedWorkspaceFileIfHash(root, path, lesson_content_hash)` (`workspace-io.ts:1738-1745`); already-absent = completed step.
5. `validateWorkspace` (lock-free).
6. **Post-phase verification** (read-only, same as §8.2 step 10): any failure → **UNVERIFIED**, nonzero, "re-run the verb; run `roster brain doctor`" — never success.
7. `COMMIT`; `finally` releases the phase lock and the client.

**Why membership-first** (confirmed, retained): the dangerous intermediate is a *selectable* retired lesson; removing membership first stops selection immediately (`workspace-context.ts:692-707`) and downgrades the orphan file to a soft `UNREGISTERED_RECORD` diagnostic (`workspace-registry.ts:1983-2003`, `:2102`), while the reverse order leaves a registered-but-missing lesson that makes `loadAgent` fail hard (`workspace-registry.ts:854-856`). Every intermediate is recoverable by re-running retire **while it remains the governor** — and a crash-left file is additionally converged by the successor's §8.2 repair arms (full content via the retired-hash arm; a stub via the widened stub arm). Drifted bytes → **`LESSON_RETIREMENT_CONFLICT`** (file left inert, membership gone, `retired-lesson-lingering` until a human resolves). Git history is the archive; the rejected `retired:`-frontmatter alternative stands rejected (`workspace-record.ts:673`).

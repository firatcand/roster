# Issue #349 implementation plan — thin Claude Code and Codex adapters

## Ticket

- GitHub: `firatcand/roster#349`
- Forge task: `P1-T06`
- Branch: `feat/349`
- Type: integration / generated host activation contract

## Outcome

Generate one flat, host-neutral lifecycle contract in `ROSTER.md` and keep the
Claude Code and Codex activation files as minimal wrappers around it. The
contract teaches each host to discover an exact target, request one bounded
context bundle, interpret the complete selected plan, load only the referenced
vendor skills, execute with host-native reasoning/tools, present approvals,
wait for the human,
completed evidence when that capability exists, check Dreamer readiness when
that capability exists, and present decision requests in the host interface.

Roster remains scaffolding, retrieval, durable evidence/learning state, and
generated guidance. It does not execute the plan or become a scheduler,
provider router, reducer, approval authority, or second source of policy.

## Decisions applied

1. **One neutral contract, thin wrappers.** The owner selected Option A. The
   complete lifecycle is rendered once into generated `ROSTER.md`. Claude and
   Codex wrappers identify the host as the runtime and tell it to read/follow
   that file; they do not copy command mappings or lifecycle prose.
2. **Capability truth is separate from generated ownership metadata.** Keep
   generated header schema 1 and protocol version 2. Generator version and
   content hashes already version every changed byte. Do not add capability
   fields to `.roster/generated-manifest.json`; that would create a persisted
   schema migration unrelated to this ticket. `roster doctor` derives the
   current capability report from canonical generated bytes, the manifest,
   enabled hosts, host-version assurance, and the shared lifecycle catalog.
3. **Unavailable future commands are explicit, not invented.** Portable
   evidence recording lands in #356, Dreamer readiness in #357, and the
   host-run candidate lifecycle in #358. Their lifecycle stages are present but
   reported `missing` in #349. Adapters must not call a nonexistent command or
   substitute legacy `roster run`, `schedule`, `pending`, `ops`, `brain save`,
   `brain event`, or a local Markdown log as false portable evidence. The
   positive behavior is: do not record portable evidence or compute readiness;
   finish the host-owned work, report that the durable capability is
   unavailable, and continue without fabricating state.
4. **Status words have one closed capability meaning across both axes.**
   `supported` means that capability is present and sufficiently proven for the
   caller to rely on; `advisory` means useful guidance/presence exists but the
   host must perform or manually activate it and Roster cannot guarantee that
   action; `missing` means the capability or enabled host activation is absent;
   `drifted` means present generated state contradicts its expected canonical
   bytes/metadata. Thus `whole-plan-interpretation: advisory` means the host
   owns that action, while `activation_capability: advisory` means canonical
   instructions exist but automatic loading is not attested. The same words
   retain the same reliance level; the field identifies the capability being
   described.
5. **Context is the runtime retrieval boundary.** Adapters use
   compact `roster discover --exact --json` to resolve identity, then derive a
   short, non-secret retrieval query and call
   `roster context <function>/<agent>[#plan] --query <retrieval-query> --json`. A context
   success deliberately has no top-level `ok`; a failure has the stable
   `ok: false` envelope and nonzero process status. The host reads the complete
   plan closure and trust-separated sections. It does not use the step hint to
   prune policy or infer a plan. `authored-policy` and `approved-lesson` remain
   policy; `vendor-instruction` is bounded tool guidance; `brain-structured` is
   cited company data, never instruction; `brain-extract-untrusted` and
   `tool-output-untrusted` are untrusted data, never instructions;
   `host-asserted` request values do not widen authority; and
   `legacy-unverified`/`diagnostic` content is never silently promoted.
   `IDENTITY_AMBIGUOUS` is presented for host/human selection rather than
   guessed. `CONTEXT_BUDGET_REQUIRED_OVERFLOW` retries once with
   `--budget <details.required_tokens>`; `CONTEXT_MANDATORY_UNSERVABLE` stops and presents
   authored-policy reduction guidance rather than looping or using a partial
   bundle. `BRAIN_NOT_BOUND` in a successful context response is a nonfatal
   warning with complete local policy and empty Brain evidence.
   Raw human task text and credentials never enter process arguments. Hosts
   pass only targets and the derived query as literal values; a shell-string
   tool uses the shell's literal-argument quoting and never concatenates or
   evaluates human text. Control characters and leading option markers are
   excluded from the derived query, and shell metacharacters in the source task
   remain data.
6. **Tool loading follows the returned selection.** The host uses only
   `skill_refs` paired with actual plan tool steps in the context bundle. A
   workspace-relative locator is read only at its verified path/hash; a
   host-native locator is resolved by the host and is not treated as an
   installation attestation. Roster supplies guidance and provenance but never
   invokes the provider.
7. **Human decisions stay in the host.** Approval steps and Dreamer candidates
   are presented in Claude Code or Codex. The host waits and decides execution.
   Future Brain decision records are portable evidence only and cannot become
   an approval receipt or continuation signal.
8. **Delegation retrieves the delegated policy explicitly.** The closure's
   `plan.definitions` order is deterministic serialization, not an execution
   queue; only each definition's authored `steps` array has order semantics.
   For `kind: subagent`, the host retrieves the registered definition with
   `roster discover --kind subagent --exact
   <function>/<agent>/subagents/<id> --full --json`. For `kind: cross-agent`,
   the host requests that target agent's own context before delegating rather
   than treating its plan body as complete nested-agent policy.
9. **Scaffolding remains explicit authorship.** `roster scaffold` is used only
   when the user asks to create a record. The host then edits the draft and
   validates it; discovery/context failure never grants permission to scaffold
   or silently repair policy.

No unresolved product fork remains.

## Public generated contract

`ROSTER.md` remains generated, hash-identified, deterministic, and
non-authoritative. Its body contains:

- the four closed capability-status definitions;
- a ten-capability lifecycle matrix, generated from one typed catalog;
- exact discover/context command shapes and response-envelope guidance;
- complete-plan and trust-separation rules;
- exact subagent discovery and cross-agent context retrieval guidance;
- vendor-skill locator rules;
- compact discovery plus non-secret derived-query and literal-argument rules;
- explicit host ownership of execution, retries, subagents, and decision
  presentation/waiting, while the human owns approval decisions;
- capability-gated evidence/Dreamer behavior; and
- a ban on legacy runtime/scheduler/queue substitutes.

The literal four-field catalog in **Runtime capability report** below is the
only normative row source. `renderRosterBootstrap()` emits exactly those
`id`, `status`, `authority`, and `authority_note` values in that order; no
second prose table is hand-authored.

Claude and Codex generated wrappers contain no copy of this table and no
business workflow. They point at `ROSTER.md`, state the host/runtime boundary,
and identify `roster doctor --json` only as an on-demand diagnostic when the
user asks or activation appears broken. Doctor is never a per-request
handshake, capability negotiation step, or precondition for discovery/context.

## Runtime capability report

Add a typed, immutable host-neutral lifecycle catalog in
`src/lib/generated-artifacts.ts`. Its renderer is the only source for the
generated lifecycle table, and `doctor` projects that catalog once into JSON so
prose and diagnostics cannot drift independently.

The shared catalog appears once at `generated.lifecycle_capabilities`; it is not
copied under each host:

```json
[
  { "id": "workspace-detection", "status": "supported", "authority": "roster", "authority_note": "Roster workspace marker" },
  { "id": "target-discovery", "status": "supported", "authority": "roster", "authority_note": "Roster command and data contract" },
  { "id": "context-retrieval", "status": "supported", "authority": "roster", "authority_note": "Roster command and data contract" },
  { "id": "whole-plan-interpretation", "status": "advisory", "authority": "host", "authority_note": "Host interprets complete plan definitions" },
  { "id": "vendor-skill-loading", "status": "advisory", "authority": "host", "authority_note": "Host resolves and reads selected skills" },
  { "id": "host-execution", "status": "advisory", "authority": "host", "authority_note": "Host owns reasoning, tools, retries, and subagents" },
  { "id": "completed-evidence-recording", "status": "missing", "authority": "roster", "authority_note": "Future Brain evidence contract (#356)" },
  { "id": "dreamer-readiness", "status": "missing", "authority": "roster", "authority_note": "Future readiness status contract (#357)" },
  { "id": "dreamer-candidate-lifecycle", "status": "missing", "authority": "roster-and-host", "authority_note": "Future candidate state and host skill contract (#358)" },
  { "id": "human-decision-presentation", "status": "advisory", "authority": "host", "authority_note": "Host presents and waits; the human decides" }
]
```

The Markdown renderer and doctor projection consume these exact four fields
from the same ordered records; tests compare them field by field.

Each enabled `generated.hosts.<host>` entry keeps its existing assurance fields
and adds only
`"activation_capability": "supported | advisory | missing | drifted"`.

Activation derivation is fail-closed:

1. Parse `roster.yaml` independently of rebuilt generated state. Enumerate
   `Object.keys(registry.hosts)` filtered to `claude | codex`; any unknown host
   keeps the existing structural `UNKNOWN_FIELD` diagnostic. If the registry
   cannot be read/parsed safely, emit no guessed host membership and let the
   structural diagnostics make doctor nonzero. Never enumerate from the rebuilt
   current manifest.
2. Read both the safely parsed canonical raw stored manifest and rebuilt
   canonical current state. `inspectGeneratedActivationState()` alone is
   insufficient because it rebuilds from files and cannot see stale stored
   metadata. Compare the stored/current neutral entry plus each enabled host's
   own summary and file subset; do not use one coarse global failure bit.
3. If an enabled host path is present but edited, noncanonical, unsafe,
   redundant (both Claude primary and fallback), or claims invalid attestation
   metadata, report `drifted`. An `authored` fixed path is explicitly excluded:
   authored root instructions are preserved and fall through to fallback/
   assurance steps 4–6.
4. Otherwise, if the header-derived canonical host summary is absent or has
   `activation_assurance: missing`, report `missing`. This includes no generated
   primary/fallback and an unviable Codex-skill-only state; an authored root
   file alone is not generated activation.
5. Otherwise, if shared `ROSTER.md` is noncanonical, the stored manifest is
   absent/invalid/noncanonical/stale-versioned, or that host's stored/current
   summary/file subset differs, report `drifted`. A stale disabled-host entry or
   leftover remains structural drift but must not contaminate an otherwise
   equal enabled-host subset.
6. Otherwise call `resolveCurrentHostActivationCapability(currentManifest,
   host, detectedHostVersion)`. `supported` requires exactly one matching
   passing `activation-and-shared-lifecycle` proof. When the activation records
   a non-null fixture, that exact fixture must own the broad proof; null fixture
   metadata from an install performed before host detection may use the one
   current broad proof. Narrow-only or ambiguous overlapping proofs remain
   `advisory`. Stored/header assurance is used for integrity comparison, never
   by itself for the final reliance claim.
7. A disabled host is not emitted in the enabled-host report;
   stray disabled generated bytes remain structural drift through the existing
   validator.

The human doctor view prints the derived activation capability alongside the
existing assurance. Capability status is diagnostic/reporting state only. It
does not change doctor exit semantics: existing structural drift/missing errors
already determine nonzero status, while an intact advisory activation remains
healthy.

If registry membership is known but rebuilding current activation state throws,
doctor emits a fail-closed entry for every known enabled host:

```json
{
  "status": "enabled",
  "activation_assurance": "missing",
  "artifacts": [],
  "attestation_fixture": null,
  "detected_host_version": null,
  "activation_capability": "drifted"
}
```

Retain a detected host version instead of `null` when its bounded `--version`
probe succeeded. Structural diagnostics remain the error authority. The
otherwise unusual `activation_assurance: missing` plus
`activation_capability: drifted` pairing is the deliberate signature for
known membership whose current generated state could not be rebuilt, and is
pinned by a doctor test.

## Files and implementation sequence

### 1. Centralize the shared lifecycle and capability vocabulary

Modify `src/lib/generated-artifacts.ts`:

- define the closed capability ID/status types and one immutable ordered
  catalog;
- render the detailed lifecycle only in `renderRosterBootstrap()`;
- reduce `renderHostBootstrapBody()` and the Codex skill fallback to minimal
  pointers to `ROSTER.md` plus the host-runtime boundary; and
- expose a read-only projection of lifecycle statuses for doctor without
  widening the generated manifest parser/schema.

Also export one narrow metadata-only accessor built directly on the existing
private `inspectGeneratedPath()` and canonical renderer checks. For each fixed
activation path it returns host/artifact, exact
`absent | authored | canonical-generated | noncanonical-generated | unsafe`
state, nullable validated assurance metadata, and one shared-bootstrap
canonical flag. It also reports redundant generated activations through the
same private predicate used by structural validation, so doctor does not
reimplement the Claude primary/fallback ownership rule. The same accessor
returns the stored manifest state as
`absent | invalid | noncanonical | stale-version | canonical` plus the safely
parsed manifest when available. It uses the same parser, canonical renderer,
and installed generator-version comparison as validation. It returns no raw
content bytes. Doctor consumes only this accessor and must not reimplement
ownership-header placement, Codex frontmatter, self-hash, manifest
serialization, attestation, or canonical-renderer rules.

Add `src/lib/internal/generated-path-diagnostic.ts` as the single projection
from generated-path I/O failures to public workspace diagnostics. It replaces
absolute upstream paths with the requested workspace-relative path, preserves
only bounded cause/operation/limit details, emits
`FILESYSTEM_ACCESS_FAILED` for genuine access denial, and retains semantic
recovery for bounded reads, write conflicts, and unsupported atomic
publication. Doctor catches an unexpected metadata-inspection throw and uses
an empty invalid projection so known enabled hosts still fail closed.

Extract the nine-value context trust taxonomy into a dependency-free
`src/lib/context-trust.ts` constant/type module. `workspace-context.ts`
re-exports the type for compatibility. The neutral renderer uses a
`satisfies Record<ContextTrustClass, string>` guidance map, so a future trust
class cannot compile until its adapter rule is explicit.

Keep existing deterministic headers, generator/protocol versions, hash
framing, create-only behavior, update transaction, attestation handling, and
drift classification unchanged. The content hashes change naturally because
the generated bodies change.

Do not change `CRITICAL.md` in this ticket. Generated-adapter critical-path
coverage is a sound methodology follow-up, but permanently gating every future
doctor edit is broader than #349. This ticket still receives the owner-required
Claude Opus plan and implementation reviews.

## Edge cases and safety checks

- Existing authored `.claude/CLAUDE.md` or `AGENTS.md` remains untouched; the
  existing fallback behavior is preserved.
- A canonical Claude rule fallback may be `supported` only on its exact passing
  host attestation; without that detected version it is `advisory`. The Codex
  skill fallback remains `advisory` because it has no auto-load attestation.
- An edited generated file with a recomputed self-hash is still `drifted`
  because current canonical rendering and the portable manifest are checked.
- A physically absent activation is `missing`, not collapsed into `drifted`.
- Shared `ROSTER.md` or global/unassignable manifest-integrity drift affects
  every enabled adapter with a viable current activation because those wrappers
  depend on the common contract; an enabled host with no viable activation
  remains `missing` under the earlier precedence;
  host-isolatable disabled-host leftovers remain structural-only and do not
  contaminate an equal enabled-host subset.
- Capability reporting never reads secrets or vendor-skill bytes and never
  serializes/emits machine-specific absolute paths or invokes a host
  model/session. Existing bounded
  `claude --version`/`codex --version` probes remain the only host process calls.
- A context response without top-level `ok` is treated as success based on exit
  status/schema; adapters do not mistake it for an error.
- `plan.definitions` ordering is never presented as execution state; authored
  `steps` order remains the host-interpreted sequence.
- Subagent and cross-agent delegation loads the target definition/policy through
  its exact discovery/context boundary before delegation.
- Missing records do not authorize scaffolding; creation remains an explicit
  user-requested authored action followed by validation.
- Missing evidence/Dreamer capabilities never cause an agent to call legacy
  execution, scheduling, pending, ops, `brain save`, or `brain event` commands
  as a shim; the host reports the durable capability unavailable and continues.
- Later #356–#358 changes update the shared catalog and lifecycle instructions;
  no persisted capability migration is required.

## Contracts and data flow

### 1. `evidence_observations` — the commit-ordered durable accumulator (B1 round 1, B2 round 2)

```sql
CREATE SEQUENCE brain_evidence.evidence_observation_ordinal_seq AS bigint START 1;

CREATE TABLE brain_evidence.evidence_observations (
  ordinal bigint PRIMARY KEY,
  evidence_kind text NOT NULL CHECK (evidence_kind IN ('completed-run','feedback')),
  evidence_id text NOT NULL CHECK (
    octet_length(evidence_id) BETWEEN 1 AND 256
    AND evidence_id ~ '^[A-Za-z0-9][A-Za-z0-9._:@/+~-]*$'),
  workspace_id text NOT NULL CHECK (workspace_id ~ '^[a-z0-9]+(-[a-z0-9]+)*$'),
  recorded_at timestamptz NOT NULL,
  CONSTRAINT evidence_observations_identity UNIQUE (evidence_kind, evidence_id)
);
CREATE INDEX evidence_observations_window_idx
  ON brain_evidence.evidence_observations (recorded_at, ordinal);

-- SECURITY DEFINER is kept as DEFENSE-IN-DEPTH (round-3 reviewer note: PostgreSQL preserves the role that queued a deferred event, which here is already the broker's definer role, so definer rights are not strictly necessary; they are kept so the trigger's privileges never depend on that queuing subtlety): a DEFERRED constraint trigger
-- fires in the pre-commit phase, OUTSIDE the SECURITY DEFINER broker whose
-- INSERT queued the event, so the effective user is back to the runtime role --
-- which holds SELECT and nothing else on this table. The function takes no
-- caller input beyond NEW, pins search_path, is PUBLIC-revoked, is granted to
-- nobody, and cannot be called outside a trigger context.
CREATE FUNCTION brain_evidence.observe_evidence()
RETURNS trigger
LANGUAGE plpgsql
SECURITY DEFINER
SET search_path = pg_catalog, brain_evidence, pg_temp
AS $fn$
BEGIN
  -- One global transaction-scoped lock, acquired in the PRE-COMMIT phase and
  -- held until transaction end. Assignment order therefore EQUALS commit order:
  -- to draw ordinal N+1 a writer must first wait for the holder of N to end.
  -- PostgreSQL removes a committing xid from the ProcArray in
  -- RecordTransactionCommit BEFORE ResourceOwnerRelease frees its locks, so by
  -- the time the next writer holds this lock, the previous holder's commit is
  -- already visible to every new snapshot. Consequently, if any reader observes
  -- ordinal M, every ordinal <= M is settled and every committed one among them
  -- is visible in that reader's snapshot; no future write can ever land at or
  -- below M. That is the commit barrier.
  PERFORM pg_advisory_xact_lock(
    brain_evidence.lock_key('roster.brain.evidence.lock.observation.v1', ARRAY[]::text[]));
  INSERT INTO brain_evidence.evidence_observations
    (ordinal, evidence_kind, evidence_id, workspace_id, recorded_at)
  VALUES (nextval('brain_evidence.evidence_observation_ordinal_seq'),
          TG_ARGV[0],
          to_jsonb(NEW) ->> TG_ARGV[1],
          NEW.workspace_id,
          NEW.recorded_at);
  RETURN NULL;
END; $fn$;

CREATE CONSTRAINT TRIGGER completed_runs_observed
  AFTER INSERT ON brain_evidence.completed_runs
  DEFERRABLE INITIALLY DEFERRED
  FOR EACH ROW EXECUTE FUNCTION brain_evidence.observe_evidence('completed-run', 'run_id');

CREATE CONSTRAINT TRIGGER feedback_observed
  AFTER INSERT ON brain_evidence.feedback
  DEFERRABLE INITIALLY DEFERRED
  FOR EACH ROW EXECUTE FUNCTION brain_evidence.observe_evidence('feedback', 'feedback_id');

REVOKE EXECUTE ON FUNCTION brain_evidence.observe_evidence() FROM PUBLIC;
```

Properties, each testable:

- **Commit-safe.** Proved above. `pg_advisory_xact_lock` is released only at transaction end, and only after the commit is visible.
- **Deferred, not immediate.** The event is queued at INSERT and fired in the pre-commit phase. This is what makes B2's lock order structural (§1a) and what shrinks the critical section (cost, below).
- **Never fires on idempotent replay.** `ON CONFLICT DO NOTHING` (`013:745`) inserts no row, so no AFTER-ROW event is queued: an equivalent replay burns no ordinal and creates no observation. This is unchanged by deferral.
- **The queued row cannot vanish before firing.** `reject_evidence_mutation` (`013:1058`) blocks UPDATE and DELETE for every role including the admin, so the deferred event always resolves to the tuple that was inserted.
- **Total order over both kinds.** One sequence interleaves runs and feedback, so a feedback-only arrival advances the frontier — the property B1 (round 2) requires. The cursor is a single `bigint`: no tuple comparison, no kind rank, no collation dependence anywhere in the readiness path.
- **`recorded_at` and `workspace_id` are copied, not re-derived**, from `NEW`, so divergence is unrepresentable. A PG test asserts equality against the source row for every observation.
- **The runtime role cannot disarm it.** Dropping a trigger requires the TRIGGER table privilege, which `doctor.ts:210` already asserts the runtime role does not hold.

**Cost, stated honestly (B2, round 2).** Every evidence write serializes workspace-wide on one advisory lock. Because the trigger is **deferred**, the critical section is one `nextval` plus one single-row `INSERT` executed immediately before commit — it is **not** held across the run broker's subsequent `run_sources`/`run_tools` inserts (up to 64 + 64 rows, `013:748-768`) nor across their foreign-key checks into `brain.source_versions`, which the Revision-2 immediate-trigger design *would* have covered. The lock is nonetheless held **until the outer transaction ends**, so a client that batches other work after the pre-commit phase, or a slow commit flush (`synchronous_commit` to a lagging standby), extends it; and a client that issues `SET CONSTRAINTS ALL IMMEDIATE` reverts to the Revision-2 duration (correct, just slower). Evidence writes are one per completed run, not per tool call. The alternative is no commit-safe order, which violates acceptance 1. Accepted trade-off; recorded in RISKS and measured by a PG test that asserts the sequence is untouched while a broker transaction is still open.

### 1a. Lock order and deadlock (B2)

**The Revision-2 claim "no deadlock is possible" was false and is retracted.** Codex's disproof stands against the immediate-trigger design: transaction A takes `run-lock(X)` then the observation lock; transaction B takes `feedback-lock(Y)` and waits for the observation lock; A then calls the feedback broker and waits for `feedback-lock(Y)`. PostgreSQL resolves that cycle by *aborting* a transaction — it does not make it impossible.

**Total lock rank order over `brain_evidence`:**

| Rank | Locks | Acquired |
|---|---|---|
| 0 | bootstrap/migration lock (`BRAIN_TARGET.advisoryLockKey`, session-scoped, `workspace-authority.ts:358`) | by bootstrap only |
| 1 | per-record evidence locks — run (`013:716`), artifact (`013:830`), feedback (`013:911`), decision (`013:1004`), promotion (`evidence-store.ts:809`) | during statements |
| 2 | **the single global observation lock** | **pre-commit phase only** |
| 3 | dream watermark (per scope) and dream policy locks | during statements |

**Deferral makes rank 2 the maximum of the acquisition order on Roster's own path** (round-3 reviewer note folded in: deferred firing does not guarantee the observation trigger is a transaction's FINAL lock request in general — later deferred constraints, cascading triggers, or SET CONSTRAINTS can acquire locks afterward; the structural claim below is therefore scoped to Roster's single-broker autocommit path, where no statement follows the pre-commit phase, and every broader batching transaction is governed by the deadlock/retry contract instead). Every rank-1 and rank-3 lock a transaction will ever take is acquired while its statements run; rank 2 is acquired only after the last statement, in the pre-commit phase; and nothing is acquired after it. Therefore:

- Any transaction **holding** rank 2 is in its pre-commit phase and requests no further lock — it can have no outgoing wait-for edge.
- Any transaction **waiting** for rank 2 is also in its pre-commit phase, holding only rank-1/rank-3 locks.

A wait-for cycle `T1 → T2 → … → Tn → T1` would need at least one edge into rank 2, whose holder has no outgoing edge — contradiction. **#357's lock cannot participate in any cycle.** Codex's counterexample is neutralised at its root: A can never hold rank 2 while still able to request `feedback-lock(Y)`.

**The residual hazard is #356's, pre-existing, and unchanged by #357.** A transaction that batches two brokers takes two rank-1 locks with no order between them, so two such transactions in opposite orders can still deadlock among rank-1 locks alone — exactly as they could before `014` existed. #357 neither creates nor fixes it, and states the contract:

> **Deadlock/retry contract.** A `40P01 deadlock_detected` raised by any `brain_evidence` call is **retryable**: every broker is idempotent by construction (`ON CONFLICT DO NOTHING` + byte-compare, `013:745-780`), so a replay after an abort converges to `created` or `existing` with no mutation. An aborted transaction leaves only a harmless gap in `evidence_observation_ordinal_seq` — gaps are expected and never interpreted. Retry is the batching caller's responsibility; **Roster never batches** — `callBroker` issues a bare `pool.query` (`evidence-store.ts:97`) and `evidence-store.ts` contains **no `BEGIN` or `COMMIT` at all**, so every Roster evidence write is a single autocommit statement holding exactly one rank-1 lock. A static test pins that.

### 1b. Backfill (B4)

The Revision-2 justification ("the bootstrap holds an exclusive advisory lock, so every prior write is settled") is **deleted** — that lock (`workspace-authority.ts:358`) is bootstrap-only and no runtime writer takes it. Safety comes from the DDL's own table lock, with the snapshot made explicit:

```sql
-- Order is load-bearing:
--   (1) BOTH constraint triggers are created FIRST. CREATE CONSTRAINT TRIGGER
--       takes SHARE ROW EXCLUSIVE, which conflicts with the ROW EXCLUSIVE an
--       INSERT holds, so each statement waits out every in-flight writer on its
--       table; and the lock is held to COMMIT, so no new writer can insert
--       until 014 lands -- and when it does, its event is queued. There is no
--       window in which a row is inserted with no observation.
--   (2) The isolation level is ASSERTED. The migration runs inside the
--       bootstrap transaction (workspace-authority.ts:360). Under READ
--       COMMITTED each top-level statement takes a FRESH snapshot, so the
--       backfill below sees every writer that committed while the DDL waited.
--       An inherited REPEATABLE READ snapshot, established by earlier bootstrap
--       reads, would predate those waits and could miss such a writer.
--   (3) Ordinals are assigned EXPLICITLY. nextval() in a target list is not
--       guaranteed to be evaluated in ORDER BY order, so row_number() assigns
--       them and setval() then advances the sequence.
--   (4) The sort key is TOTAL. run_id and feedback_id are independent id
--       spaces, so (recorded_at, evidence_id) alone is NOT total -- a run and a
--       feedback may share both. evidence_kind breaks the tie, and (kind, id)
--       is unique by construction. COLLATE "C" removes collation dependence.

DO $$ BEGIN
  IF current_setting('transaction_isolation') <> 'read committed' THEN
    RAISE EXCEPTION
      '014 backfill requires READ COMMITTED; got %', current_setting('transaction_isolation');
  END IF;
END $$;

WITH pending AS (
  SELECT 'completed-run'::text AS kind, r.run_id AS id, r.workspace_id, r.recorded_at
    FROM brain_evidence.completed_runs r
  UNION ALL
  SELECT 'feedback'::text, f.feedback_id, f.workspace_id, f.recorded_at
    FROM brain_evidence.feedback f
), ordered AS (
  SELECT row_number() OVER (ORDER BY recorded_at, kind, id COLLATE "C") AS ordinal,
         kind, id, workspace_id, recorded_at
    FROM pending
)
INSERT INTO brain_evidence.evidence_observations
  (ordinal, evidence_kind, evidence_id, workspace_id, recorded_at)
SELECT ordinal, kind, id, workspace_id, recorded_at FROM ordered;

SELECT setval('brain_evidence.evidence_observation_ordinal_seq',
              coalesce((SELECT max(ordinal) FROM brain_evidence.evidence_observations), 0) + 1,
              false);
```

Backfilled ordinals are a *reconstruction*, not observed commit order — pre-`014` history has none. That is stated in the migration header: the barrier holds strictly for observations created by the triggers, and the backfill only guarantees a stable, total, collation-independent order over rows that were all already committed before the DDL returned. No `ALTER` and no trigger-disable on #356's tables.

### 2. Watermark vs frontier — the two distinct quantities (B1)

| | **Watermark** (processed floor) | **Frontier** (observed evidence ceiling) |
|---|---|---|
| Meaning | Everything at or below this ordinal has been reflected on and promoted | The exact upper bound of the evidence snapshot this occasion covers |
| Storage | `dream_watermarks` row, per scope | **Derived** from `evidence_observations` |
| Advances on | **Promotion only** (`spec/SPEC.md:628-633`) | **Any** new eligible evidence, of **either** kind |
| Moves backward? | Never (`RBE05`) | Only as evidence ages out of the policy window |

**Eligible set.** With `w = watermark ordinal` (0 at genesis) and `t = evaluated_at`:

```
run(o) = the completed_runs row of o, i.e.
         o.evidence_id            when o.evidence_kind = 'completed-run'
         feedback(o.evidence_id).run_id when o.evidence_kind = 'feedback'
         -- feedback.run_id is NOT NULL and FK-guaranteed (013:477), so run(o)
         -- always exists; feedback inherits SCOPE and EXCLUSION from its run
         -- but keeps its OWN recorded_at and ordinal for window and frontier.

E(t) = { o in evidence_observations :
           o.ordinal   >  w
       AND o.recorded_at >  t - policy.evidence_window
       AND o.recorded_at <= t
       AND scope_matches(run(o), requested_scope)
       AND run(o).agent_id <> ALL (policy.excluded_agent_ids) }

frontier_ordinal  = coalesce(max(o.ordinal) over E(t), 0)
eligible_runs     = |{ o in E(t) : kind = 'completed-run' }|
eligible_feedback = |{ o in E(t) : kind = 'feedback' }|
eligible_mix      = |{ o in E(t) : (kind='feedback'      AND feedback(o).signal IN ('negative','mixed'))
                                OR (kind='completed-run' AND run(o).outcome IN ('failed','partial','aborted')) }|
```

**The frontier is the true observed-evidence ceiling.** Revision 2's quantization (`batch_index = floor(eligible_runs / min_completed_runs)`, frontier pinned to a run-batch boundary) is **deleted**, along with `batch_index`. It was wrong on three counts, all verified:

1. It covered only the run leg. With `min_completed_runs = 1, min_feedback_records = 1`, a run at ordinal 1 gives frontier 1 and `not_due`; feedback at ordinal 2 makes the scope `due` with the frontier and key unchanged. A `not_due → due` transition with a frozen activation identity is precisely the bug this ticket exists to kill.
2. Feedback never advanced it at all, so after a rejection no amount of feedback could re-open the occasion.
3. #358's promised `ordinal <= frontier` query would have **omitted** the very feedback that made readiness due.

The claim that `not_due` implies `batch_index = 0` was also false: cooldown, an unmet feedback minimum, or an unmet mix minimum all hold `not_due` at any batch index. It is deleted, not repaired.

**Snapshot-bound tuple — the contract #358 consumes.** The exact predicate that reproduces `E(t)`, every input of which is a field of `dream status` output:

```
ordinal      >  watermark.ordinal
ordinal      <= frontier.ordinal
recorded_at  >  evidence.window_start
recorded_at  <= evidence.window_end
scope_matches(run(o), scope)
run(o).agent_id <> ALL (policy.excluded_agent_ids)
```

**Closure lemma (why `ordinal <= frontier` is exact and permanent).** `frontier = max E(t)`, so `E(t) ⊆ { ordinal <= frontier }` by construction — nothing eligible is omitted. And the set can never *gain* a member: any observation not visible in this snapshot commits later, and by §1's barrier a later commit draws a strictly greater ordinal, so it lands strictly above the frontier. `{ ordinal <= frontier }` is therefore closed forever. #358's reconstruction is exact, not approximate, and is stable across restarts.

**Why derived rather than stored, and why that is still durable.** Storing it would require `dream status` to write, which acceptance 4 forbids. It is durable because (i) an observation row, once committed, is append-only and never removed, (ii) the ordinal is commit-ordered, and (iii) the frontier is therefore a deterministic, reproducible function of durable rows alone — nothing is held in memory, so it survives restart by construction.

**Activation identity.**

```
readiness_key = evidenceDigest('roster.brain.dream.readiness-key.v1', {
  workspace_id, scope_key, policy_version, policy_fingerprint,
  watermark_ordinal, frontier_ordinal })
```

- A rejected candidate no longer ends learning: **any** later eligible evidence, run *or* feedback, raises the frontier, changes the key, and legitimately opens a new occasion. **The watermark still moves only on promotion**, so `spec/SPEC.md:628-633` is untouched and the `reason='operator'` escape hatch stays deleted.
- Two hosts checking over the *same* snapshot get the same key ⇒ #358's candidate identity collapses them to one row on idempotent replay.
- Two hosts checking over *different* snapshots get distinct keys ⇒ distinct candidate identities that replay idempotently instead of colliding.
- `policy_fingerprint` is included so a threshold edit correctly opens a new occasion.

**What #357 deliberately does not provide.** The key now changes on every eligible arrival, including while `not_due`. That is correct — it is an *evidence-snapshot identity*, not an invocation-rate limiter. `dream status` is a pure read with no durable record of a rejection, so it cannot damp post-rejection re-asks without inventing a candidate-lifecycle state that is #358's by scope. The two throttles that do exist are the promotion-anchored **cooldown** and #358's own dedup, for which #357 supplies everything needed (`watermark.ordinal`, `frontier.ordinal`, the eligible counts, and the snapshot-bound tuple). Recorded in Risk 4 and in the composition table.

### 3. `dream status` never mutates

Unchanged and re-affirmed: acceptance 2 ("same status at the same watermark"), acceptance 4 ("no host next-action dispatch in the status command"), and `spec/SPEC.md:601` are all read-shaped. An advancing read also recreates v1's loss-of-eligibility failure (host reads `due`, the read advances, host crashes before invoking). Dedup is the host's, keyed on `readiness_key` — now genuinely fit for that purpose.

### 4. One statement, one snapshot

`computeDreamReadiness` issues **exactly one `pool.query`**. A single CTE, evaluated under one snapshot with one `evaluated_at := now()`, performs all five steps: capture instant → resolve policy → read watermark → scan eligible observations (joining each to its run by primary key, and each feedback observation through `feedback.run_id`) → compute counts, mix, and the frontier maximum. Built-in policy defaults are passed as bind parameters and resolved *inside* the CTE (specificity-ordered `LATERAL` over `dream_policies` with a fallback row), so policy resolution shares the snapshot.

The only permitted fallback, if the CTE proves unmaintainable, is an explicit `BEGIN ISOLATION LEVEL REPEATABLE READ; … COMMIT;`. A static test asserts one of the two holds.

**Equivalence, correctly defined.** Two checks are *equivalent* iff (resolved policy, stored watermark, eligible observation set, cooldown state) are identical at their respective evaluation instants. Tests establish that precondition explicitly — frozen evidence, no concurrent writes, cooldown either absent or far from expiry, window far from aging any row — and then assert identical `status` **and** `readiness_key`. `evaluated_at`, `window_end`, and `cooldown.remaining` are clock-derived and excluded from the equivalence claim. Complementary **positive** tests prove status legitimately *changes* at one stored watermark when cooldown expires, when evidence ages out, and when the frontier advances.

### 5. Policy, predicate, configuration

`DreamPolicy` fields, all named by `spec/SPEC.md:601`:

| Field | Built-in default |
|---|---|
| `policy_version` | `roster.dream.default.v1` |
| `scope_key` | `workspace` |
| `min_completed_runs` | `5` |
| `min_feedback_records` | `0` |
| `min_signal_mix` (`feedback.signal ∈ {negative,mixed}` **or** `outcome ∈ {failed,partial,aborted}`) | `0` |
| `evidence_window` | `30 days` |
| `cooldown` (anchored on the last watermark advance, i.e. on promotion) | `20 hours` |
| `excluded_agent_ids` | `['dreamer']` |

`advance_stability_lag` is **deleted** — the commit-ordered ordinal makes it unnecessary. `min_completed_runs` is a **threshold only**; its Revision-2 second job as "re-ask granularity" is gone with quantization.

```
due ⇔ eligible_runs ≥ min_completed_runs
  AND eligible_feedback ≥ min_feedback_records
  AND eligible_mix ≥ min_signal_mix
  AND NOT (watermark exists AND evaluated_at < watermark.advanced_at + cooldown)
```

**Configuration without a scheduler.**

1. The built-in default is a **code constant** (`DEFAULT_DREAM_POLICY`). Bootstrap ordering (`workspace-authority.ts:365-368` runs migrations before `insertMigratingIdentity`, so `brain_meta.workspace_identity` is empty during `014`) means a migration-time seed cannot derive `workspace_id` — but that does not *force* a constant; a post-identity seed step could be added. The constant is chosen because it is simpler, keeps a fresh Brain functional with zero rows, and needs no new bootstrap hook.
2. Scoped overrides are durable `dream_policies` rows, resolved specificity-first (`plan: → agent: → function: → workspace`), tie-broken `recorded_at DESC, policy_version DESC`. `policy.source ∈ {'built-in','brain'}` is reported.
3. **The runtime role cannot write policy.** `registerDreamPolicy` is admin-only, no broker, no CLI. This is load-bearing: the policy decides when the loop fires, and the runtime pool processes untrusted tool output. Since runtime *can* fabricate evidence via the four record brokers (`roles.ts:393-398`), keeping policy admin-only is what prevents an agent from also lowering the bar it must clear.

**Self-evidence** (`spec/CONTEXT.md:150`): `excluded_agent_ids` is the readiness half — a reflection's own recorded run cannot raise readiness, and neither can feedback on it, because feedback inherits its run's `agent_id`. The citation half is #358's. Policy-configurable, not a hard-coded string.

### 6. Function grants and the doctor change (B3)

`advance_dream_watermark` and `register_dream_policy` are **not** granted to runtime, are **not** added to `EVIDENCE_RECORD_BROKERS`, and are plain `SECURITY INVOKER` plpgsql with pinned `search_path` — `SECURITY DEFINER` would be pointless (definer == caller == admin) and strictly riskier. `observe_evidence` is the **one** `SECURITY DEFINER` function `014` declares, for the reason given in §1; it is PUBLIC-revoked and granted to nobody. **#358 owns the runtime grant and the promotion binding** — it will add a promotion-identity parameter and the corresponding `roles.ts`/`doctor.ts` edits.

**`roles.ts` needs no change — verified.** `GRANT SELECT ON ALL TABLES IN SCHEMA brain_evidence` (`roles.ts:417`) already covers the four new relations; `REVOKE ALL PRIVILEGES ON ALL SEQUENCES IN SCHEMA brain_evidence` (`roles.ts:412`) already covers the new sequence, and it runs *after* migrations in the same bootstrap transaction; the four-broker EXECUTE loop is unchanged; and no `ALTER DEFAULT PRIVILEGES` exists anywhere in `src/` or `data/` that could re-grant.

**`doctor.ts` does need a change — Revision 2's "not touched at all" is retracted.** The `brain-evidence-append-only` check filters `c.relkind = 'r'` in every clause (`:204`, `:210`, `:217`), and the only sequence audit is scoped to `nspname = 'brain'` (`:419`). A runtime grant on `brain_evidence.evidence_observation_ordinal_seq` would therefore pass green under a description that promises "**exactly** USAGE + SELECT + the four record brokers" (`:194`). One additive clause, appended to the same check so the description stays true:

```sql
UNION ALL
SELECT 'brain_evidence.' || c.relname || ' ' || p.priv
  FROM pg_class c JOIN pg_namespace n ON n.oid = c.relnamespace
  CROSS JOIN (VALUES ('USAGE'), ('SELECT'), ('UPDATE')) AS p(priv)
 WHERE n.nspname = 'brain_evidence' AND c.relkind = 'S'
   AND has_sequence_privilege($1, c.oid, p.priv)
```

`SELECT` is included because it exposes `last_value` — an evidence-volume side channel. The existing `missing SELECT` clause keeps `relkind = 'r'`, so sequences are never *required* to be readable. `test/brain-evidence-schema.test.ts:363-406` asserts on this check by name and status only, so #356's tests are unaffected; a new red-path test injects a sequence grant and asserts doctor turns red.

## RISKS

1. **The commit-order invariant is the whole ticket.** If the advisory lock is dropped from `observe_evidence`, released early, or the triggers stop being `AFTER INSERT` row triggers, ordinals stop tracking commit order and acceptance 1 silently breaks — with no visible symptom until an observation is buried. *Mitigation:* the observation tests are written **before** the readiness logic (sequence step 3) and include a control assertion that a 5s lag would have failed; a 20-writer randomized concurrency test; a static assertion that `014` contains `pg_advisory_xact_lock` inside `observe_evidence` and that both triggers are `AFTER INSERT FOR EACH ROW`; the invariant is documented in the migration header and in `CRITICAL.md`.

2. **The deferral is load-bearing for deadlock-freedom, and it is a single keyword.** `DEFERRABLE INITIALLY DEFERRED` is what makes the global lock the strict maximum of the acquisition order; drop it and Codex's cycle (run-lock → observation-lock vs feedback-lock → observation-lock) becomes reachable again, and the critical section re-expands to cover the run broker's 128 `run_sources`/`run_tools` inserts and their cross-schema FK checks. *Mitigation:* a static test pins the exact trigger declaration; a PG test proves the lock is **not** held while a broker transaction is still open; the rank table and the proof are reproduced in the migration header and `CRITICAL.md`. *Residual, accepted:* the lock is still held from the pre-commit phase until transaction end, so a slow commit flush or a client-issued `SET CONSTRAINTS ALL IMMEDIATE` lengthens it (correctness preserved), and #356's pre-existing multi-broker-per-transaction batching can still deadlock among rank-1 locks alone — covered by the retry contract and its test, and unreachable from Roster's own code.

3. **The deferred trigger needs `SECURITY DEFINER` and that is easy to lose.** Deferred firing happens outside the broker's definer context, where the effective user is the runtime role, which holds only SELECT on `evidence_observations`. Dropping `SECURITY DEFINER` makes every runtime evidence write fail at COMMIT — loudly, but only under a real runtime role, which a fresh-admin-only test would miss. *Mitigation:* an explicit runtime-role PG test asserts the observation appears; `014`'s one-`SECURITY DEFINER`-function static assertion names `observe_evidence` explicitly rather than banning the keyword; the function is PUBLIC-revoked, granted to nobody, takes no input beyond `NEW`, and pins `search_path`.

4. **The readiness key now churns on every eligible arrival.** With quantization gone, any new run or feedback re-keys the occasion — including while `not_due`, and including immediately after a human rejects a candidate. That is correct for #358's snapshot query and for re-opening after rejection, but it means the key alone will not throttle re-invocation. *Mitigation:* the key is only *consumed* when `due`; the promotion-anchored cooldown throttles the post-promotion path; and post-rejection damping is explicitly assigned to #358, which records rejections and receives `watermark.ordinal`, `frontier.ordinal`, `frontier.eligible_observations` and the full snapshot-bound tuple — everything needed to require an evidence delta before re-opening. Stated in §2, the scope boundary, and the composition table so #358 cannot inherit it by accident.

5. **The handoff to #358 is load-bearing and easy to lose.** `advance_dream_watermark` ships admin-only and deliberately does **not** verify that the cursor is scope-eligible, equals the computed frontier, or accompanies a promotion. If #358 grants it to runtime without adding those checks, it reintroduces an unauthenticated integrity/availability hole. *Mitigation:* `reason = 'promotion'` (single value) makes a non-promotion advance unrepresentable today; the migration header, this plan's scope boundary, and a comment on the function body all state the three missing checks as #358's precondition for granting; a static test asserts `014` grants EXECUTE to no role; and the now-sequence-aware doctor check (B3) turns red on any unapproved `brain_evidence` grant, including a sequence grant.

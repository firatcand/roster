# Issue #382 — Inventory legacy Brain state

## Goal

Add one internal, bounded, read-only operation that inventories legacy PostgreSQL and S3 state before backfill. It returns deterministic canonical manifest bytes, a SHA-256 digest, and a separately sanitized report. It never migrates, writes, deletes, copies, derives sources, changes roles, or adds a public command.

## Fixed boundaries

- GitHub issue #382 owns scope and acceptance; #384 owns backfill and #363 owns adopter cutover.
- The host remains the runtime. This ticket adds no workflow reducer, provider executor, scheduler, approval engine, or compatibility layer.
- Inventory receives an expected workspace identity plus an already validated S3 namespace. It does not discover credentials or select a workspace.
- PostgreSQL access is one bounded `REPEATABLE READ, READ ONLY` transaction. S3 access is through a Brain-owned interface that exposes only history listing and exact-version metadata reads.
- No filesystem artifact or remote record is written. The caller receives bytes/digest/report in memory; a later migration surface owns persistence and approval.
- Tests use only compact synthetic fixtures. No adopter repository, real Brain, secret manager, database, or bucket is accessed.

## Pending architecture decisions

Implementation is blocked only on these user choices:

1. When protected database identity is absent, either permit explicitly authorized migration-preflight inventory and mark ownership unverified (recommended), or refuse all company-table/S3 reads.
2. Either keep arbitrary IDs/paths/role names/S3 keys tokenized in the canonical manifest and revalidate them during backfill (recommended), or treat the manifest as a private sensitive artifact that retains exact values.
3. Either make a failed run restart from page one with no durable checkpoint (recommended), or add persistent resume state outside this read-only ticket.

Unless changed by the user, a custom relation without a stable primary key returns `incomplete` with no approvable digest.

## Public internal contract

`inventoryLegacyBrain(input)` accepts:

- a narrow PostgreSQL pool/client port;
- `LegacyObjectHistoryReader` with `listHistory()` and `headVersion()` only;
- expected non-secret workspace/namespace fingerprints;
- explicit positive limits for relations, stable-ID rows, S3 pages/items, findings, and transaction duration; and
- the user-selected absent-identity policy.

It returns:

- `complete`: canonical UTF-8 JSON bytes, `sha256:<hex>` over those exact bytes, typed manifest, and sanitized report; or
- `incomplete`: sanitized findings only and no digest/manifest bytes when identity, limits, catalog shape, pagination, ownership, or provider integrity prevents a trustworthy snapshot.

The operation exposes no write-capable database or S3 method.

## Authority ordering

1. Begin the read-only transaction; set `search_path = ''`; pin UTC, ISO/YMD, and deterministic float rendering; and schema-qualify every SQL function, operator target, and relation.
2. Detect protected identity and migration relations through catalog queries (`to_regclass` precedent); never assume a modern schema exists.
3. If protected identity exists, compare its workspace and namespace fingerprints to the expected values. Any mismatch rolls back and stops before company-table reads or S3 access.
4. Apply the selected absent-identity policy. An allowed unidentified database is explicitly marked `unverified` in digest-bearing bytes; it is never silently promoted to the expected identity. That manifest is preflight evidence only and cannot authorize #384 without #363's explicit human decision.
5. Only after this gate, inventory company-table metadata and then the exact validated S3 prefix.

The manifest binds to observed protected identity when present, not merely caller assertions. It also binds to the exact namespace fingerprint used by the hardened S3 adapter.

## PostgreSQL inventory

- Scan every non-system, non-extension-owned user relation, not only `brain`/`brain_meta`, so custom schemas/tables are visible. Classify each as `product-meta`, `product-legacy`, `product-lifecycle`, or `adopter-custom`; non-empty lifecycle tables produce a partial-cutover finding so #384 cannot double-backfill them.
- Record applied migration filename/hash pairs and a deterministic migration-set hash. Missing or malformed migration metadata becomes an explicit finding rather than invoking migrations.
- Record a safe table-definition projection: relation kind, ordered column types/nullability/generated/identity shape, and primary-key positions. Hash raw catalog expressions; never copy raw defaults, checks, index expressions, comments, or arbitrary names into the report. Put a definition hash per relation and one aggregate hash over the sorted relation hashes in canonical bytes.
- Record exact row counts under the same snapshot as decimal strings; never coerce `bigint` counts or identifiers through JavaScript numbers.
- `product-legacy` is the pre-lifecycle set `entities`, `mounts`, `facts`, `events`, `edges`, `documents`, `files`, `entity_aliases`, and `entity_merges`. Read only fixed-schema IDs, timestamps, relationships/redirects, type keys, confidence, actors, source/path/hash/storage metadata, chunk index, and embedding-model name needed for later correlation. Never select bodies, titles, aliases, fact values, event payloads, edge properties, document content/frontmatter/embeddings, or arbitrary source text.
- For custom tables, read only primary-key columns. Produce an ordered, domain-separated stable-ID digest and count; retain individual values only under the user-selected manifest policy.
- Catalog-derived dynamic identifiers are schema-qualified and quoted by an inventory-owned SQL-standard double-quote escaper. Caller-provided identifiers are never interpolated.
- Scope role/ACL inventory to the database plus relevant user schemas/relations: owners, runtime-role membership, explicit grants, and `pg_default_acl`. Never query password hashes, role settings, or connection options.
- Apply statement/transaction time limits. Any cap or timeout produces `incomplete`; it never truncates an apparently complete inventory.

Known legacy file rows have no S3 version ID. Correlate them against history using key, opaque ETag, and size: zero matches is missing; multiple matches is ambiguous. New lifecycle objects with a stored version ID use exact-version correlation.

## S3 history inventory

- `legacy-inventory-s3.ts` constructs a separate read-only AWS adapter behind `createS3NetworkBoundary`; it does not reuse the older generic S3 factory. Missing region fails closed instead of inheriting the generic store's fallback.
- List every version and delete marker beneath the exact validated prefix using bounded `ListObjectVersions` pages.
- A page contains tagged version/delete-marker observations and an opaque cursor binding the format, prefix fingerprint, key marker, and version marker.
- Reject malformed/wrong-prefix/repeated/non-progressing cursors, duplicate `(key, version, kind)` tuples, missing required provider fields, and cap overruns. Every returned key must byte-prefix-match the validated prefix; no `Delimiter` is sent; truncated responses without a next key marker fail; and literal S3 version ID `"null"` remains distinct from an absent version ID.
- Sort canonical history by raw UTF-8 key bytes, version identity, entry kind, and latest flag, independent of provider page partition/order.
- Use `HeadObject` only for exact-version metadata correlation. Never fetch bodies and never call put/delete.
- One complete history pass is an explicitly point-in-time S3 observation, not a database-style snapshot. Database-versus-history and exact-head disagreement produce scoped drift findings; #384 revalidates versions before trusting bytes; do not impose a second full-bucket pass.

## Canonical and redacted outputs

- Use the existing recursively key-sorted canonical JSON helper, pre-sort every array explicitly, append one newline, and hash the exact bytes. Canonical bytes include `manifest_format_version: 1`, `inventory_algorithm: roster-legacy-inventory-v1`, and `token_scheme: sha256-domain-v1`; #384 refuses unsupported versions.
- Exclude timestamps of collection, random IDs, database OIDs, request IDs, page sizes, cursors, and retry counts from digest-bearing bytes.
- Findings sort by `(code, resource_kind, resource_ref, detail_ref)` and are capped.
- Finding codes cover the issue's required classes: absolute/temporary/foreign locator, reused hash, missing bytes, mutable-key history, ETag/version drift, ambiguous ownership, plus integrity/limit failures. Ambiguous ownership means an unowned listed object, a database reference outside the validated namespace, or multiple rows claiming the same key/version. Mutable history means multiple non-delete versions under one key expected to be content-addressed.
- Raw provider/SQL errors are wrapped in stable codes. Neither output nor thrown errors may contain credentials, bodies, userinfo URLs, complete absolute paths, or planted canaries.
- Under the recommended policy, arbitrary identifiers use `sha256("roster/legacy-inventory/v1/" + domain + NUL + canonical_value)` references with a fixed domain per relation name, column name, role name, S3 key, path, and stable ID. Safe fixed-schema numeric/UUID IDs and known product-schema names remain clear when needed for #384; adopter-authored names, paths, role names, and S3 keys do not. A human reviews the sanitized report linked to the exact manifest digest, not raw canonical bytes.

## Synthetic fixture and tests

The tracked fixture contains only invented values and covers:

- legacy migrations, known tables, one custom quoted-name table, and one no-primary-key table;
- safe IDs plus a text/composite ID canary;
- a file matched by ETag/size, missing bytes, reused content hash, and an ambiguous version match;
- multiple versions, one delete marker, mutable-key history, and reordered/paginated pages;
- absolute, temporary, foreign, malformed, and userinfo-bearing locator canaries;
- relevant owner/grant/default-ACL shapes and an unidentified/mismatched identity case.

Tests prove:

1. exact acceptance-field coverage and complete custom-relation discovery;
2. byte-identical manifest/digest across insertion, response, and page-size reorderings;
3. no omission/duplication across pagination and restart-from-zero retry if selected;
4. mismatch-before-content/S3 ordering and selected absent-identity behavior;
5. deterministic missing/ambiguous/drift/ownership findings;
6. incomplete-without-digest on limits, bad cursors, unsafe catalog shape, or no stable key;
7. zero planted secret/body/path canaries in manifest, report, errors, and diagnostics under the selected policy; and
8. query/S3 spies observe no DDL, DML, body GET, PUT, COPY, or DELETE.

No live database/S3 dependency is mandatory. Existing full-suite tests protect ordinary file-store behavior.

## Resolved decisions (owner, 2026-08-08)

1. **Absent protected identity → permit with `unverified` marking.** Explicitly authorized migration-preflight inventory is permitted when protected database identity is absent. Ownership is marked `unverified` inside digest-bearing bytes and is never silently promoted to the expected identity. Such a manifest is preflight evidence only; it cannot authorize #384 without #363's explicit human decision.
2. **Manifest privacy → tokenize.** Arbitrary identifiers (relation names, column names, role names, S3 keys, paths, stable IDs) are tokenized in the canonical manifest as `sha256("roster/legacy-inventory/v1/" + domain + NUL + canonical_value)` with a fixed domain per identifier class. Safe fixed-schema numeric/UUID IDs and known product-schema names remain clear. A sanitized human report accompanies the manifest.
3. **Resume → no durable checkpoint.** A failed run restarts from page one. Determinism guarantees byte-identical rerun output on unchanged source.
4. **Confirmed default:** a custom relation without a stable primary key returns `incomplete` with no approvable digest.

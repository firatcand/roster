## 3. Design

### 3.1 Canonical contract and the version triple (design question 1)

**Decision: no new artifact, no new record.** The canonical contract is `renderRosterBootstrap()` + `renderHostBootstrapBody()` in `src/lib/generated-artifacts.ts`; the version triple is `(generator_version, protocol_version, content_hash)` and it is **already recorded twice at generation time** — in every generated file's self-authenticating ownership header and in `.roster/generated-manifest.json` — and verified at sync time (`entryFromGeneratedContent`) and doctor/validate time (`validateGeneratedArtifacts` cross-checks entry ↔ header ↔ current canonical render, `:1957-2019`). Both records are load-bearing and neither is trusted alone: headers prove per-file integrity without the manifest; the manifest proves cross-file/host **membership** (host slices, `manifest_hosts` vs `roster.yaml` `:1940-1955`) and whole-set integrity (`manifest_hash`). Acceptance 1's remaining work is *surfacing*, not recording: doctor's `generated` block gains a `versions` object (§3.4) and the per-path inspection gains `recorded_generator_version` so mixed versions become a first-class report instead of per-file noise. A separate "content version" is rejected: `content_hash` **is** the content version (deterministic renderer ⇒ same inputs, same hash), and a semantic contract version would duplicate `protocol_version` without a consumer.

### 3.2 The drift decision table (design question 2)

All cells are decided over: marker-at-owned-position, header parse validity, hash validity (recomputed vs recorded `content_hash`), path-identity match, byte-equality with the **current** canonical render (`renderCanonicalGeneratedEntry`, which re-renders from the entry's own recorded assurance validated against `CHECKED_IN_HOST_ATTESTATIONS`), and recorded `generator_version` vs `getPackageVersion()`.

**Canonical owned paths** (the 5 entries of `GENERATED_PATH_IDENTITIES`), per file:

| # | Condition | Inspection state | `roster update` behavior | Validate/doctor code | Fixture |
|---|---|---|---|---|---|
| C1 | file absent, host enabled | `absent` | create (`created`) | pre-sync: manifest-entry mismatch (existing) | deleted-file |
| C2 | bytes == current canonical render | `canonical-generated` | `unchanged` | none | baseline |
| C3 | marker at owned position, header valid, **hash valid**, identity matches, bytes ≠ current render | **`stale-generated` (new)** | replace (`updated`) — unchanged sync behavior, new classification | **`GENERATED_FILE_STALE`** (error), details `{recordedGeneratorVersion, expectedGeneratorVersion, reason}` where `reason` = `'generator-version'` if versions differ else `'content'` | upgrade, mixed-versions |
| C4 | marker at owned position, header invalid OR hash mismatch OR artifact/host ≠ path identity | `noncanonical-generated` (now means exactly *edited*) | refuse (`conflict`), bytes preserved byte-identical | `GENERATED_FILE_EDITED` (error, existing) | edited-generated |
| C5 | no marker at owned position | `authored` | preserve (`preserved-authored`); never written | none (host falls back per existing rules) | authored-preservation |
| C6 | symlink/FIFO/oversize/unreadable | `unsafe` | refuse + pass-through diagnostic | existing unsafe codes (`UNSAFE_GENERATED_PATH_DIAGNOSTIC_CODES` untouched) | existing |
| C7 | present but host disabled in `roster.yaml` | (disabled-artifact path) | canonical → `removed`; else preserved + diagnostic | existing `GENERATED_FILE_EDITED` disabled-host diagnostics — **unchanged** (`:1169-1254`) | existing `:1412-1513` |

The honest edge in C3, stated for the record: the hash chain **cannot** distinguish an old renderer's genuine output from a forged body that was re-hashed at the current version (the `:953-1050` adversarial family). Both are hash-valid, both diverge from the current render, and both are safely replaced by regeneration because the valid header proves Roster ownership. So they share one cell and one remedy (`run roster update`); `details.reason` separates upgrade-lag (`generator-version`) from same-version divergence (`content`) for the human. Severity stays **error** — identical gate behavior to today's `GENERATED_FILE_EDITED` at these sites, so `manifest_status`, `structural.ok`, dreamer-verdict inputs, and exit codes are all preserved; only the code, message, and remedy become truthful.

**Manifest** (`.roster/generated-manifest.json`) — the existing five-state machine is kept verbatim: M1 absent + all headers valid + no missing host claim → reconstruct (`:1621-1628`); M2 absent + missing/edited claim → refuse (`:1603-1619`); M3 unparseable → refuse `GENERATED_FILE_EDITED` (`:1629-1635`); M4 noncanonical serialization → replace; M5 `stale-version` → replace; M6 canonical → unchanged. Validate's stale-generator manifest diagnostic (`:1925-1938`) keeps its existing message but switches code to `GENERATED_FILE_STALE` (same severity), aligning the manifest cell with C3.

**Shadow paths** (§3.3 enumerates them), per file — Roster **never writes or deletes** at these paths under any cell (authored-preservation invariant; a marker-bearing file at a non-owned path has ambiguous ownership, so detection is report-only):

| # | Condition | Kind | Severity | Behavior |
|---|---|---|---|---|
| S0 | absent, or no `<!-- roster:generated` marker at offset 0 | not a shadow | — | silent; authored host memory files are untouched and unmentioned |
| S1 | valid+hash-valid header of any known artifact kind, bytes == that artifact's current canonical render | `duplicate` | error | `GENERATED_SHADOW` — the host will auto-load the same contract twice; today's duplicate becomes tomorrow's stale fork |
| S2 | valid+hash-valid header, bytes ≠ current render | `stale` | error | `GENERATED_SHADOW` with `details.recordedGeneratorVersion` — this is precisely the "two hosts silently run different contracts" state |
| S3 | marker at offset 0, header invalid or hash broken | `edited` | error | `GENERATED_SHADOW` |
| S4 | any S1–S3 at `GEMINI.md` | `unsupported-host` | error | `GENERATED_SHADOW` — explicit "Gemini has no v2 activation contract; remove the file" (acceptance 3's "unsupported host capabilities are explicit", joining the existing `UNKNOWN_FIELD` registry diagnostic `:2054-2065`) |
| S5 | symlink / not-regular / oversize (> `MAX_WORKSPACE_FILE_BYTES` = 512 KiB) / unreadable at a shadow path | `unreadable` | **warning** | `GENERATED_SHADOW` warning naming the risk ("the host may follow this path to content Roster cannot inspect") — warning, not error, because these paths are legitimately user-owned (a symlinked personal `CLAUDE.local.md` is innocent) and Roster never confirmed them workspace-relevant; blocking here would fail workspaces Roster never touched |

The **offset-0 marker rule** is the false-positive defense: an authored `CLAUDE.md` that merely *quotes* the marker mid-file (docs about Roster) is not a shadow. This deliberately mirrors `inspectGeneratedPath`'s existing ownership rule — a marker below authored preamble is authored, per the established taxonomy (`hasGeneratedHeaderAtOwnedPosition`). A hybrid file (authored preamble + pasted generated content) is therefore invisible to the scan; it is also invisible to today's system, and flagging it would require content-sniffing authored files, which the ownership model forbids. Stated as accepted residual risk (§7).

Error-severity shadows flow through the existing `ok` computations: `roster update` exits 1 (files still synced first — fail-loud but repair what is repairable), `roster validate`/structural check fails, and `installV2ProjectActivation` refuses (and rolls back its own writes) until the shadow is reconciled — a host must not be newly activated beside a divergent contract copy. Each of the three gets a fixture (§5).

### 3.3 Shadow enumeration (design question 4)

Shadows are enumerated over a **closed list of workspace-relative paths that a host auto-loads from the project**, read exclusively through `tryReadWorkspaceFile` (component-wise confined, `O_NOFOLLOW`, bounded) and `inspectWorkspaceDirectory` (the same confined primitive the workspace probe uses) — no new raw fs walk, no host-cache probe, no `~` access:

- **Fixed files**: `CLAUDE.md`, `CLAUDE.local.md` (Claude Code project-memory auto-load surface; host attribution `claude`), `GEMINI.md` (host attribution `gemini` → always `unsupported-host`).
- **Bounded enumeration**: `.claude/rules/` via `inspectWorkspaceDirectory(root, '.claude/rules', { maxEntries: 128 })` — every regular `*.md` entry **except** the canonical `.claude/rules/roster.md`, host attribution `claude`. Absent directory (`PARENT_NOT_FOUND`) → no shadows. Truncated enumeration → one `GENERATED_SHADOW` warning `kind: 'unreadable'` for the directory (fail-loud on partial knowledge, non-blocking).
- **Codex**: `AGENTS.md` and `.agents/skills/roster/SKILL.md` are both canonical owned paths (already governed by the C-table, including the copied-artifact refusal pinned at `test/generated-artifacts.test.ts:1227`). Codex's nested-directory `AGENTS.md` merging and Claude's ancestor-directory memory files are **out of scope by constraint** (unbounded agent-writable tree walk) and are named in the doctor detail line and §7 as the residual surface.

Detector: one new pure-scan function `detectGeneratedShadows(root: string): { shadows: GeneratedShadowInspection[]; diagnostics: WorkspaceDiagnostic[] }` in `generated-artifacts.ts`, deterministic (sorted by path), with `GeneratedShadowInspection = Readonly<{ path: string; surface_host: 'claude' | 'gemini'; kind: 'duplicate' | 'stale' | 'edited' | 'unsupported-host' | 'unreadable'; artifact: GeneratedArtifactHeader['artifact'] | null; recorded_generator_version: string | null }>`. Classification reuses `parseGeneratedMarkdown` + `renderCanonicalGeneratedEntry` via a small variant of `entryFromGeneratedContent` that accepts the header's own artifact/host claim instead of requiring a `GENERATED_PATH_IDENTITIES` row (which shadow paths by definition lack).

Consumers (one detector, three surfaces — no duplicate logic):
1. `synchronizeGeneratedActivations` (`:1647-1673`) appends the detector's diagnostics — covering both `roster update` and `installV2ProjectActivation`.
2. `validateGeneratedArtifacts` (`:1852`) calls the detector **immediately after the registry parse** (before the early returns at `:1896`/`:1908`/`:1911-1914`, so a broken manifest cannot hide a shadow).
3. `inspectGeneratedAdapterMetadata` exposes `shadows` for doctor.

### 3.4 Doctor composition — compose, don't fork (design question 5)

- `GeneratedAdapterMetadataInspection` gains `shadows: readonly GeneratedShadowInspection[]`; each path entry gains `recorded_generator_version: string | null` (from the parsed header for hash-valid states; from the claimed header when parseable on edited states; else null). `readV2GeneratedMetadata`'s catch-fallback (`doctor.ts:872-883`) adds `shadows: []`.
- `deriveV2DoctorHosts` `pathDrift` (`:917-919`) extends to `entry.state === 'stale-generated'` (preserving today's behavior for what used to map there) and to `generatedMetadata.shadows.some((s) => s.surface_host === host && s.kind !== 'unreadable')` — so a claude shadow makes claude's `activation_capability` `'drifted'` exactly the way the redundant-pair already does (`:921`).
- Doctor JSON `generated` block (`:1071-1076`) gains `versions: { generator_version: getPackageVersion(), protocol_version: 2, recorded_generator_versions: string[] (sorted unique over hash-valid path headers + stored manifest), mixed: boolean }` and `shadows: [...]`. Human rendering: one line per shadow and a `versions: mixed (a, b)` line when mixed.
- **The #359 dreamer truth table is not touched.** `deriveDreamerActivation` inputs are computed exactly as today; a stale file or shadow reaches it only as the coarse `activation: 'drifted'` it already understands, so `drifted` verdicts compose with zero new rows, and shadows are reported once (in `generated.shadows` / structural diagnostics), never re-reported inside `dreamer_activation`. `UNSAFE_GENERATED_PATH_DIAGNOSTIC_CODES` is unchanged, and the two new codes are deliberately **not** in it (a shadow/stale file is drift, not an unsafe path; S5 unreadables are warnings and must not flip `structural_ok`).

### 3.5 Upgrade path and record migration (design question 3)

**Decision: zero serialized-format change, therefore zero migration.** Header `schema_version` stays `'1'` with the exact key set (`HEADER_KEYS` `:325-335`); manifest `schema_version` stays `1` with the exact key set (`:839-847`). This is forced, not optional: both parsers are exact-key closed, so any added key would make every **existing** workspace's files parse as edited → sync would *refuse* them → upgrade would brick. The pin `test/generated-artifacts.test.ts:298-317` ("doctor-only capability fields never enter generated headers or manifest schema 1") stays green and gains the new fields (`recorded_generator_version`, `shadows`, `versions`) in its assertion list.

Consequences, stated for the reviewer:
- Workspace generated by an older Roster, new CLI runs `roster doctor`: files classify `stale-generated` + `GENERATED_FILE_STALE` (`reason: 'generator-version'`), manifest `stale-version`, `manifest_status: 'drift'`, capabilities `drifted` — same gate outcome as today, truthful code and remedy.
- Same workspace, `roster update`: every hash-valid file is replaced with the current render, the manifest is rewritten, exit 0 (absent other drift). **Idempotent**: a second run reports all `unchanged` (fixture-pinned).
- Older CLI on a newer workspace: unchanged from today — headers parse (same schema), the old CLI regenerates to its own version; normal downgrade churn, and the new taxonomy makes the subsequent re-upgrade legible.
- All "migration" is behavioral reclassification computed at inspection time from data **already recorded** in every existing workspace — nothing to migrate, nothing to journal.

### 3.6 Templates and the probe (design question 6)

Nothing under `templates/` changes. `templates/scaffold/dreamer/agent.md` stays byte-frozen (probe signature + `smoke.sh:115` tarball pin). `workspace-probe.ts` is untouched — its byte-equality reads shipped template files, not generated artifacts, and no path this ticket adds intersects `LEGACY_SIGNATURE_FILES`. Verified: no shipped template or skill contains the `roster:generated` marker, so the shadow scan cannot fire on scaffold output, `pnpm smoke`'s three `roster update` invocations (`test/smoke.sh:442,479,604`), or `pnpm test:scaffold-scripts`.

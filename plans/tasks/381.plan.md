# Issue #381 implementation plan — recoverable Brain source lifecycle

## Ticket and outcome

- GitHub: `firatcand/roster#381` · Forge: `P2-T13` · dependency: closed #351.
- Add the internal, authority-verified source lifecycle that #383 will expose.
- A host supplies selected bytes, provenance, labels, and a stable request key.
- Roster derives continuing source identity, stores immutable bytes and versions,
  and recovers deterministic Postgres/S3 partial failures.

## Questions asked and answers applied

The product owner answered all architecture questions in this task:

- Public-address S3 only: standard AWS origins and explicitly authored public
  HTTPS endpoints. Private/link-local exceptions are not a supported v2 surface.
- The host supplies a bounded `request_key`. Equivalent replay converges; the
  same key with different canonical input returns `IDEMPOTENCY_CONFLICT`.
- Restore/re-ingest must name the exact active tombstone. Stale work cannot
  implicitly resurrect a deleted source.
- One immutable version may carry multiple complete hierarchical retrieval
  labels rather than duplicating the source.
- Fetched media uses host-supplied provider + upstream stable ID, falling back
  only to a host-declared canonical HTTPS URL.
- Trust and actor assurance use closed vocabularies. Free-form or unjustifiably
  stronger assurance is rejected.

No architecture question remains open. Plan approval is waived by the product
owner; Claude Opus 5 xhigh plan review remains required before implementation.

## Scope boundary

In scope:

- source contracts, identities, immutable versions/objects, labels, tombstones,
  durable intents, prepare/publish, inspection/repair, and S3 network policy;
- one additive migration and the minimum runtime-grant fence needed so the new
  lifecycle tables cannot be mutated through the legacy blanket grant loop;
- hermetic tests plus PostgreSQL integration tests and the repository phase gate.

Out of scope:

- public Brain CLI/help/skills/docs and retained-command routing (#383);

  (#370/#352);
- legacy inventory/backfill or adopter mutation (#382/#384/#363);
- provider fetching, file selection, workflow execution, schedules, approvals,
  S3 deletion, or changes to legacy `brain.files`/mount/document behavior.
- hardening legacy `brain fs`/`s3-core.ts`; #381 secures the new lifecycle path,
  while shared-store cutover remains a #383/#363 obligation.

## Contracts and data flow

### 1. Closed input contract

- Kinds: `workspace-file`, `fetched-media`, `inline-text`,
  `structured-record`, `produced-artifact`.
- File identity is exact normalized workspace-relative POSIX path; reject
  absolute, traversal, backslash, control, empty, and temporary/foreign paths.
- Fetched identity is provider + upstream ID; absent an ID, minimally normalize
  the declared HTTPS URL (lowercase host, remove fragment/default port, preserve
  path and query bytes). Never fetch it.
- Other kinds require an opaque, case-sensitive safe stable key.
- IDs and keys use bounded UTF-8/ASCII contracts and injective canonical JSON
  with domain-separated SHA-256, never delimiter framing.
- Source bytes have a fixed exported 64 MiB cap enforced before Postgres/S3;
  larger media requires explicit segmentation or a later streaming surface.
- Privacy: `public | internal | secret`. Trust uses the existing applicable
  context trust subset. Assurance: `system-derived | caller-asserted |
  host-attested | human-confirmed`, with stronger values requiring their closed
  evidence shape.
- Each retrieval label is a complete workspace/function/agent/plan hierarchy;
  narrower components cannot appear without their parents.

### 2. Additive schema

- `brain.source_objects`: one immutable row per SHA-256 object, deterministic
  key, byte length/type, opaque ETag and optional S3 version observation.
- `brain.logical_sources`: continuing identity, next mutation sequence, current
  version, and active tombstone pointer.
- `brain.source_versions`: immutable source + prepared sequence + object +
  metadata/provenance. Equal bytes may share an object, never a source.
- `brain.source_version_labels`: normalized many-label hierarchy.
- `brain.source_tombstones`: retained deletion/restoration history.
- `brain.ingest_intents`: bounded request key, immutable canonical fingerprint,
  expected IDs/hash/key, allocated source sequence, and monotone recovery state.
- No `brain_space`, binding, workspace tenancy column, or RLS policy. The
  protected database identity remains the workspace boundary.
- SQL constraints/triggers reject object/version mutation, TRUNCATE, illegal
  transitions, and labels whose narrower scope lacks its required parent.
- A migration-owned protected-table registry drives `applyGrants`, so current
  and future lifecycle tables receive no runtime DML by construction. The
  injected admin executor performs #381 writes; #383 may broker them later.

### 3. Prepare → object → publish

1. Verify the already-bound Brain connection before lifecycle SQL.
2. Validate/freeze input and compute source ID, object ID/key, version
   fingerprint, and canonical request fingerprint.
3. In a short transaction, compare or create the intent and allocate a monotone
   per-source sequence. Commit before any S3 call.
4. Outside every database transaction, create the deterministic object with
   `If-None-Match: *`; on lost response/race, HEAD and reject unexpected size
   before bounded GET + SHA-256 verification. ETag is never a digest; a different
   version observation for deduplicated bytes is not a content conflict.
5. In a new transaction, lock the source, record/reuse object and immutable
   version, labels and provenance, and complete the intent. Advance current only
   when its prepared sequence is newer, so a slow old publish cannot rewind it.
6. Return stable IDs and sanitized state, including whether the version became
   current or was published only as history. Prepared sequence gaps are valid.

### 4. Tombstone and exact restoration

- Tombstone allocates the next source sequence, records the exact prior version,
  and atomically becomes active; it never issues S3 DELETE.
- Restore or changed-byte resurrection must supply the exact active tombstone
  ID. Under the source lock it either restores the exact prior version or
  consumes that tombstone while publishing the explicit new version.
- A superseded/wrong tombstone conflicts without mutation.

### 5. S3 request policy

- Use an AWS SDK client internally; Claude/Codex still invokes Roster, while the
  AWS CLI remains available for host/admin work with the same ambient secrets.
- A custom Smithy Node request handler checks the actual signed request's HTTPS
  protocol and exact derived host/port before transport.
- Its socket `lookup` resolves with bounded count/time, rejects the whole answer
  set using the classifier shared with config validation, then returns exactly
  one validated address even under `all:true` so Happy Eyeballs cannot bypass it.
- Disable socket reuse so every request performs that guarded lookup. A changed
  DNS answer, redirect, region redirect, sibling hostname, or port fails closed.
- Supply only explicit ambient env credentials so discovery cannot reach IMDS.
  Disable dualstack, accelerate, FIPS, global and region redirects; never rewrite
  the TLS hostname to an IP or relax certificate verification.
- Explicit custom endpoints must remain public HTTPS and produce one predictable
  effective host. Standard AWS origin is derived from concrete region, bucket,
  and path-style configuration; ambiguous endpoint resolution is rejected.

### 6. Report-first recovery

- Inspection is bounded, deterministic, sanitized, and read-only. It reports
  prepared/object-present/publish-pending/complete/conflict/missing/corrupt state.
- Repair requires an exact intent ID and expected request fingerprint. It may
  verify and publish an intent-owned object or retry with caller-supplied bytes
  whose digest matches the intent.
- Never scan/adopt plausible S3 objects, fabricate missing bytes, rewrite an
  immutable version, or delete storage.

## Implementation sequence and ownership

1. Root owns migration numbering, shared exports, roles, integration, and commits.
2. Worker A: source contracts/identity plus identity tests only.
3. Worker B: S3 network policy/object port plus hermetic tests only.
4. Worker C: migration/schema constraints plus PostgreSQL schema tests only.
5. Root integrates prepare/publish/tombstone/recovery and failure/concurrency
   tests after A–C stabilize. Workers are not alone and must not revert others.
6. Run typecheck after each slice; run Opus implementation review and the full
   phase gate after the complete diff stabilizes.

`roles.ts` and the network-policy module are deliberate advisory
`plans/phases.yaml#write_globs` exceptions required by #381's security contract.

# Issue #350 investigation — live-host authentication boundary

## Problem statement

The seeded host-led learning certification was designed as a hermetic provider
test. It creates empty host homes, injects raw Anthropic/OpenAI provider keys,
and rejects ambient host state. That does not match Roster's product boundary:
Claude Code and Codex are the logged-in runtimes, while Roster is their
workspace scaffolding and context layer.

The certification should therefore prove the loop through the installed,
authenticated host applications. It should not prove that Roster can recreate
those applications from an empty home directory or call their model providers
directly.

## Reproduction

On the exact certified binaries:

- Claude Code is `2.1.220` and reports a logged-in Claude account when
  `ANTHROPIC_API_KEY` and `ANTHROPIC_AUTH_TOKEN` are absent.
- Codex is `0.144.1` and reports `Logged in using ChatGPT` when
  `OPENAI_API_KEY` is absent.
- A no-tool Claude model turn succeeds through the logged-in host with the
  provider-key variables absent and returns the expected fixed probe result.
- A read-only, ephemeral Codex turn succeeds through the logged-in host with
  `OPENAI_API_KEY` absent and returns the expected fixed probe result.
- A curated-environment Claude turn also succeeds with the intended
  project-only settings, strict empty MCP, no Chrome, no session persistence,
  and no provider-key/auth-token variables.
- A curated-environment Codex turn also succeeds with strict config,
  `--ignore-user-config`, `--ignore-rules`, ephemeral mode, history persistence
  disabled, and no OpenAI/Codex credential variables. Codex still reports its
  ambient skill-budget condition, which confirms that personal installation
  state can exist even when user config rules are ignored for the session.
- Codex login status and a real model turn both succeed when process `HOME` is
  an isolated temporary directory and only `CODEX_HOME` points to the ambient
  host state. The model-command environment can therefore keep isolated
  `HOME`/`TMPDIR` values without losing ChatGPT authentication.
- A model-free Codex 0.144.1 app-server `config/read` probe under the ambient
  ChatGPT profile reports `model_provider: null`. The corrected verifier can
  pin that observed default and reject any injected `model_providers.*`
  session override.
- The same app-server probe reports `approval_policy: null` and
  `sandbox_mode: null` even when the CLI receives `-a never` and
  `--sandbox workspace-write`. Those two controls must be proven by the closed
  launch arguments and runtime canaries; the verifier pins the observed nulls
  instead of trusting the older hand-authored test fixture values.
- Claude Code 2.1.220 accepts
  `Skill(roster-350-host-led-learning:fixture-dreamer)` as an identity-scoped
  permission and successfully invokes only that fixture skill. The streamed
  initialization also reports `apiKeySource: none`, providing a post-launch
  host-auth signal without reading personal authentication data.
- The same Codex turn observes the real installed skill/plugin environment and
  emits non-fatal ambient warnings, demonstrating that an adopter host is not
  an empty configuration directory.

The current certification still fails before either host can launch:

```text
ANTHROPIC_API_KEY must be injected for live certification.
```

This comes from `hostApiKey()`, not from Claude Code authentication.

## Hypotheses and evidence

### H1 — the machine is not logged in

Rejected. Both host-native login status commands succeed without provider API
key variables, and both small model turns complete through those logins.

### H2 — only the explicit API-key gate is wrong

Rejected as incomplete. Removing `hostApiKey()` alone would still leave both
hosts pointed at new empty homes:

- `explicitHostEnv()` replaces `HOME` and sets a temporary
  `CLAUDE_CONFIG_DIR` or `CODEX_HOME`.
- Claude loses its host-managed login under that empty home/config pair.
- Codex is forced to a custom provider whose authentication contract is
  `OPENAI_API_KEY`.

The launch arguments and environment must change together.

### H3 — every personal customization must be loaded into the proof

Rejected for this seeded fixture. Personal settings, plugins, browser state,
caches, and KState may exist and may be required by later real workflows, but
the #350 fixture uses only fake tools and a checked-in fixture plugin/skill.
Loading every customization here would broaden the proof to unrelated hooks,
MCPs, tools, and instructions without increasing confidence in the seeded
learning loop.

The narrower boundary is sufficient: use host-managed authentication and
state lookup, tolerate the adopter's personal installation, and retain
session-level restrictions for this fake-tool proof. A later real-browser or
vendor workflow should deliberately certify the personal plugin/browser
dependencies it actually needs.

## Root cause

The certification conflates two different responsibilities:

1. **Host responsibility:** Claude Code or Codex authenticates, selects its
   provider, and runs the model as the installed user application.
2. **Roster responsibility:** the prepared workspace, plan, context, skills,
   tool-use policy, evidence, approval boundary, and promoted lesson are exact
   and auditable.

By replacing host state and forcing provider keys, the test accidentally made
Roster responsible for host deployment. The result is a proof that cannot run
in the normal product workflow even though the real hosts are already usable.

## Chosen correction — `ambient-auth-v1`

The live proof will use the real adopter host for authentication while keeping
the Roster behavior boundary closed:

- Use the caller's validated ambient `HOME` for Claude. For Codex, keep process
  and model-command `HOME` isolated and expose only the caller's effective
  `CODEX_HOME` (or its standard location) to the Codex process.
- Do not set `CLAUDE_CONFIG_DIR` to an empty directory for paid Claude turns.
- Do not inject `ANTHROPIC_API_KEY`, `ANTHROPIC_AUTH_TOKEN`, `OPENAI_API_KEY`,
  `CODEX_API_KEY`, or provider-switch variables.
- Remove the custom Codex API-key provider and use the logged-in default host
  provider.
- Preflight each exact paid-host authentication envelope with the host's own
  status command. Persist only a closed, non-sensitive authentication
  projection; never email, organization, token, raw status output, or auth
  files.
- Keep fresh workspaces, fresh processes, temporary `TMPDIR`, exact fixture
  bytes, pinned host/model versions, output schemas, sandbox canaries, closed
  fixture commands, approval ordering, semantic equality, and three passes per
  host.
- Keep Claude project-only settings plus the explicit fixture plugin, and keep
  Codex `--ignore-user-config`/`--ignore-rules`. Those flags do not disable
  host authentication; this was reproduced with actual model turns under the
  restrictive flags. Personal customizations are tolerated on the machine but
  are not authority for this seeded fixture.
- Never copy, delete, recursively scan, hash, or attest the ambient home,
  configuration, cache, browser profile, or KState.
- Do not grant the ambient home as a writable sandbox root.

The attestation claim becomes precise: these exact Roster workspace/runtime
bytes completed through the exact installed, logged-in host binaries under the
`ambient-auth-v1` profile. It does not claim equivalence across every possible
personal customization or certify a real browser/vendor workflow.

## Expected change surface

- Amend `plans/tasks/350.plan.md` and the fixture README/launch contract.
- Replace API-key/environment gates in
  `test/support/host-led-learning-certification.ts` with safe ambient-auth
  resolution and host-native auth probes.
- Bind a non-sensitive auth proof and profile declaration into attestation
  schema v2; bump the fixture iteration.
- Update hardening, live, and static-boundary tests to prove no provider key or
  personal config is persisted and no ambient home is sandbox-writable.
- Regenerate the six-pass attestation on final bytes.
- Do not change production `src/**`, the semantic oracle, the Brain schema, or
  shipped Roster behavior.

### 4. Why a naive fix is unsafe — the exact race trace

For a `chmod 000` candidate directory: `inspectCandidateDirectory` (`workspace-probe.ts:152-176`) → `withWorkspaceDirectoryIdentity` (`workspace-io.ts:394-430`) → `withAnchoredDirectory`'s `process.chdir` (`workspace-io.ts:481`) fails `EACCES` → wrapped `workspaceFailure('WRITE_CONFLICT', {cause:'EACCES'})` (`workspace-io.ts:483-488`) → not converted to an identity-race signal (`cause` isn't in `{undefined, ENOENT, ENOTDIR, ELOOP}`, `workspace-io.ts:420-426`) → `inspectCandidateDirectory`'s catch: `isWorkspaceDirectoryIdentityFailure` is **false**, generic branch, `isWorkspaceFailure(error)` is **true** → `code = 'write_conflict'` → signal `company:unreadable:write_conflict`. Matches the issue's own JSON exactly.

This confirms `isWorkspaceFailure(error)` cannot be the discriminator (it's `true` here, yet this must become non-blocking), and a blanket "ignore all inconclusive" fix cannot be used either (would declassify genuine wrong-type swaps and TOCTOU races — proven by `test/init.test.ts:463-488` and `577-623`, which must keep passing unmodified). The correct discriminator is the innermost OS cause, `EACCES`/`EPERM` specifically, however deep the wrapping:

```ts
function isPermissionDeniedFailure(error: unknown): boolean {
  const cause = isWorkspaceFailure(error)
    ? error.details['cause']
    : (error as NodeJS.ErrnoException).code;
  return cause === 'EACCES' || cause === 'EPERM';
}
```

Safe against spoofing: reads the error object's own metadata, never the human-readable diagnostic *string* (which embeds attacker-influenceable directory names).

## Blocker 1 resolution — accept-and-document, extended to all 3 write-capable paths

**Confirmed threat/harm framing (unchanged core argument, now applied per-path):** the actor capable of hiding a legacy marker behind a permission wall already has local write/chmod access inside the same directory tree — they could delete/rename/replace the markers directly instead, so a permission wall is not a materially stronger attack than what they could already do. The question for each path is simply: *what, concretely, can now get written that couldn't before, and is that bounded/non-destructive/recoverable?*

### Path 1: `init` (`src/commands/init.ts:206`)

Writes `roster.yaml` + `ROSTER.md` into `cwd` when `kind` resolves to `'none'` (previously blocked as `'unsafe'`). Worst case: two new files scaffolded beside an undetected legacy directory — non-destructive, self-correcting (a later probe once permissions are fixed reclassifies as `'mixed'`/`'v2'`).

### Path 2: `install` implicit/non-interactive default to user scope (`src/bin/roster.ts:359` → `installToTool`)

Traced precisely: `runInstall`'s `unsafe`/`legacy`/`mixed` gate (`roster.ts:369-378`) only applies `if (requestedScope !== 'user')`. When `requestedScope === null` (no explicit `--scope`) and non-interactive (`--yes` or non-TTY), scope resolves via `defaultScopeForContext(workspaceExists=false)` = `'user'` (`install-scope.ts:22-24`). Previously, the `unsafe` gate threw before scope resolution was even reached; after this fix, `kind:'none'` no longer trips that gate, so `install` proceeds to `scope='user'` and calls `installToTool(tool, {scope:'user', ...})` — **without** `projectRoot`/`cwd` in the options (`roster.ts:436-443`: `projectRoot` is only spread in when `scope === 'project'`).

Verified in `installToTool` (`install.ts:210-268`) that the `'user'`-scope branch:
- Never enters the `if (opts.scope === 'project')` block (`install.ts:211-252`) — the *only* block in this function that calls `probeWorkspace` on `projectRoot`/writes anything workspace-relative.
- Instead operates exclusively on `installRoot = tool.installRoot ?? tool.configRoot` (`install.ts:261`), i.e. `~/.claude`/`~/.codex`/`~/.gemini` or their `ROSTER_*_HOME` test overrides (`tools.ts:25,29,33`).
- Is guarded by an explicit confinement check, `assertWithinRoot(tool.skillsTarget, installRoot, 'skillsTarget')` (`install.ts:262-264`), backed by a dedicated `WorkspaceConfinementError` ("Refusing to write ... outside configRoot", `install.ts:63`).

**`cwd` is not referenced anywhere in this code path.** Writes land exclusively under the configured tool install root. **Precision correction:** that root is *independent of* `cwd`, not necessarily *outside* it — `ROSTER_CLAUDE_HOME` (and the real `~/.claude`) can legitimately be a descendant of `cwd`, and is exactly that in the pinning test below. The true claim is therefore "nothing on this path is resolved relative to `cwd`, and every target is confined beneath `installRoot` by `assertWithinRoot`", not "writes land outside this tree entirely". Pinned by a new test (below) using the identical pattern the existing suite already uses for `ROSTER_*_HOME`-scoped assertions (`test/cli-install-flags.test.ts:394-408`), plus a `readdirSync(cwd)` before/after comparison to prove `cwd`'s own entry list is untouched.

     ```ts
           : v2.length > 0
             ? 'v2'
             : blockingInconclusive.length > 0
               ? 'unsafe'
               : legacy.length > 0
                 ? 'legacy'
                 : 'none';
     const blockingUnsafe = v2.length === 0 && kind === 'unsafe'
       ? sortedUnique([...unsafe, ...inconclusive])
       : unsafe;
     ```

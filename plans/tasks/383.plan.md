## 1. What the ticket actually is

The orchestrator brief framed #383 as "expose existing library functions as CLI verbs, no new migration." **That framing is wrong on the migration**, because the authoritative acceptance criteria live in `plans/phases.yaml:391-483` (task `P2-T15`) and are stricter than the issue-body summary. Codex round 1 confirmed this reading.

The eight criteria, verbatim source `plans/phases.yaml:401-419`:

1. `init`, `ingest`, `doctor`, `fs`, semantic writes, and **every retained Brain command** reject partial PostgreSQL/S3 configuration and use verified workspace authority; local-only commands unaffected.
2. The runtime role cannot create/alter/drop schema, own protected objects, change identity or provenance, **bypass fixed brokers**, or directly mutate lifecycle state.
3. Doctor and migration diagnostics **may inspect protected metadata before identity is ready** but cannot read company content or touch object storage.
4. Legacy spellings `mount, table, sql, config, reindex, gc, export, import` stay **recognized but fail closed** with stable diagnostics until removal in #363.
5. `query` stays recognized but fails with `BRAIN_RETRIEVAL_NOT_READY` until #370 and #352; *"default context excludes legacy-unverified evidence while preserving it for explicit future retrieval."*
6. Explicit runtime-credential rotation uses a previously authenticated runtime role or a reviewed provider-admin recovery path, updates the operator-selected credential mechanism **without printing secrets**, and **cannot be an init side effect**.
7. `save`, `event`, `link`, `merge` **cite an immutable structured-record source version**, and `fs` removal **tombstones without deleting object bytes**.
8. CLI parsing, help, JSON errors, skills, templates, docs, negative role tests, and both host harnesses pass without API-key-only or named-provider dependencies.

**AC-7 as amended (owner decision D1, 2026-08-10):** the criterion becomes *"`save`, `event`, and `merge` cite an immutable structured-record source version; `link` is handed to #397"*. #383 ships `link` working and **explicitly labelled uncited** — it is not silently deferred (§4.1, §7.2, §8).

**AC-5 second clause is not #383's.** "Default context excludes legacy-unverified evidence" is a `roster context` selection rule owned by #352/#355; no `legacy-unverified` rows can exist before #384 backfills. #383 satisfies AC-5 by fail-closing `query`. Stated in §14.

`write_globs` at `plans/phases.yaml:410-422` explicitly include **`data/brain/schema/*runtime*`** — the roadmap already budgeted a migration for this ticket.

### 1.1 The contradictions, and how this plan resolves them

**(c) Disabling `brain config` (AC-4) breaks `brain fs` (AC-1) unless `fs` is repointed in the same PR.** `roster brain fs` resolves its bucket from `brain_meta.config` via `filesConfig()` (`src/lib/brain/s3.ts:40-50`) consumed at `src/commands/brain.ts:383-395`; the only setter is `roster brain config set` (`src/lib/brain/config.ts:58-62`, `src/commands/brain.ts:616-628`). ### 3.1 Migration numbering — the merge-time rule (round-1 B1)

`validateRecordedMigrations` (`migrate-core.ts:174-197`) requires the applied ledger to be an **exact ordered prefix** of the numerically sorted on-disk set, with matching sha256. `loadMigrations` (`:134-155`) sorts by numeric prefix and rejects duplicates. Consequence: **a number can never be reused, reordered, or gap-filled after any Brain has applied a higher number.**

Therefore the plan **does not claim a number**. The rule is:

1. On-disk today: `001`–`013` (`data/brain/schema/`). Reserved *as of 2026-08-10*: `014` = #357, `015` = #358, `016` = #397 — **reservations reorder if merge order differs; they are not a claim.**
2. During development, PR B's file carries the next free number at branch time and is treated as provisional.
3. **Pre-merge renumber step (mandatory, in the phase sequence at §3.2):** immediately before merge, rebase on `main`, list `data/brain/schema/`, and rename the file so its prefix is exactly `max(on-disk prefix) + 1`. Update the filename anywhere a test names it. No other edit is needed — the sha256 is computed at load (`migrate-core.ts:150`).
4. **The migration may never merge ahead of a gap.** If a lower-numbered migration from #357/#358/#397 is merged-but-not-yet-in-`main` at that moment, PR B waits. A merge that creates `[…,013,015]` is a latent corruption for every Brain that applies it before `014` lands.
5. Enforced by a new hermetic guard (§11.1, T11) asserting the shipped schema directory's prefixes are the contiguous sequence `1..N`. This guard catches the mistake in CI on any branch, for #357/#358/#397 too.
6. The filename keeps the `*runtime*` token so it matches `write_globs: data/brain/schema/*runtime*`: `0NN_runtime_operations.sql`.

## 6. Activation: `BRAIN_NOT_CONFIGURED` vs `BRAIN_CONFIGURATION_INCOMPLETE` — the two-axis state machine (round-1 B6)

### 6.1 Two axes, not one

There are two independent axes and both must produce `BRAIN_CONFIGURATION_INCOMPLETE`:

**Axis 1 — the tracked declaration (`roster.yaml`).** `parseBrainConfig` (`workspace-record.ts:319-345`) requires both `brain.secrets_path` and `brain.storage`, and `brain.storage` requires `bucket` + `region` (`:336-341`). A workspace that declares only one half is a *PostgreSQL-only* or *object-storage-only* declaration — precisely what `plans/phases.yaml:160` and `spec/CONTEXT.md` mean — but today it fails first as a generic `YAML_INVALID` schema error (`workspace-record.ts:220-228`). This axis must be classified **before** the strict parse.

**Axis 2 — ambient credentials.**
- PostgreSQL half: `ROSTER_BRAIN_URL` (runtime verbs) / `ROSTER_BRAIN_ADMIN_URL` (admin verbs) — `BRAIN_ENV_BINDING` at `src/lib/persistence/pool.ts:7-10`.
- Object-storage half: `AWS_ACCESS_KEY_ID` **and** `AWS_SECRET_ACCESS_KEY` — `explicitCredentials` (`object-store.ts:463-479`) throws `S3_CREDENTIALS_MISSING` with **no default-provider-chain fallback**, so the axis is real and checkable ahead of any I/O.

### 6.2 Axis 1 — the pre-parse structural probe

New export in `src/lib/workspace-record.ts` (it already owns `parseYaml` at `:461` and the strict `parseBrainConfig`):

```ts

  | { status: 'absent' }
  | { status: 'partial'; missing: readonly ('postgresql' | 'object-storage')[] }
  | { status: 'declared' };

export function classifyBrainDeclaration(text: string, path?: string): BrainDeclaration;
```

It reuses the existing `parseYaml(text, path)` and inspects **only** `value.brain`:

| Raw `brain:` node | Classification |
|---|---|
| absent | `absent` |
| not a mapping | `declared` — let the strict parse raise `YAML_INVALID` |
| has `secrets_path`, no `storage` | `partial`, missing `['object-storage']` |
| has `storage`, no `secrets_path` | `partial`, missing `['postgresql']` |
| has `storage` mapping missing `bucket` and/or `region` | `partial`, missing `['object-storage']` — an object-storage declaration that names no namespace is *incomplete*, not merely malformed |
| neither key | `partial`, missing `['postgresql', 'object-storage']` |
| both present and `storage` names `bucket` + `region` | `declared` |

`parseWorkspaceRegistry` stays byte-for-byte strict, so no existing test changes: `roster validate`, `roster discover`, `roster init` etc. keep raising `YAML_INVALID` on a malformed block. **Only the brain-activation resolver consumes the classification**, and it runs the probe before delegating to `readWorkspaceRegistry` — so `roster brain save` on a half-declared workspace reports `BRAIN_CONFIGURATION_INCOMPLETE` while `roster scaffold` keeps its schema error. That is the minimal, surgical reading of AC-1's "local-only Roster commands remain unaffected".

Values that are *present but invalid* (a bad bucket name, an `http://` endpoint) remain `YAML_INVALID` — a declared-but-wrong value is a schema error, not incompleteness. Stated explicitly because a reviewer will probe it.

### 7.1 The migration (round-1 B1/B2/B3; round-2 B1/B2/B4)

One file, `data/brain/schema/0NN_runtime_operations.sql`, number assigned by the §3.1 merge-time rule. **Structural change in Revision 3:** the `brain.structured_record_versions` projection table is **gone**. Replacing it with a per-row `BEFORE INSERT` validation removes the derived state entirely, and simultaneously delivers round-2 B2's insert-only semantics.

**(2) The citation gate — one insert-only trigger doing both jobs (round-2 B1 + B2).**

```sql
CREATE OR REPLACE FUNCTION brain.require_structured_record_citation()
RETURNS trigger
LANGUAGE plpgsql
SET search_path = pg_catalog, brain, pg_temp
AS $fn$
DECLARE
  v_kind text;
BEGIN
  -- Three DISTINCT stable SQLSTATEs (round-3 blocker): the 013 broker precedent
  -- (RBE01..RBE05) applied to citations. A shared '23514' made 'missing',
  -- 'unknown-version', and 'not-structured-record' indistinguishable to the
  -- TypeScript layer, and absent versions must NOT fall through to the FK —
  -- a concurrently committed wrong-kind version could then evade the kind check.
  IF NEW.source_version_id IS NULL THEN
    RAISE EXCEPTION '%.% requires an immutable structured-record citation',
      TG_TABLE_SCHEMA, TG_TABLE_NAME USING ERRCODE = 'RBC01';
  END IF;
  SELECT s.source_kind INTO v_kind
    FROM brain.source_versions v
    JOIN brain.logical_sources s ON s.source_id = v.source_id
   WHERE v.source_version_id = NEW.source_version_id;
  IF NOT FOUND THEN
    RAISE EXCEPTION 'citation % is not a known source version',
      NEW.source_version_id USING ERRCODE = 'RBC02';
  END IF;
  IF v_kind <> 'structured-record' THEN
    RAISE EXCEPTION 'citation % is not a structured-record source version',
      NEW.source_version_id USING ERRCODE = 'RBC03';
  END IF;
  RETURN NEW;
END;
$fn$;
REVOKE EXECUTE ON FUNCTION brain.require_structured_record_citation() FROM PUBLIC;

CREATE TRIGGER entities_require_citation      BEFORE INSERT ON brain.entities
  FOR EACH ROW EXECUTE FUNCTION brain.require_structured_record_citation();
CREATE TRIGGER facts_require_citation         BEFORE INSERT ON brain.facts
  FOR EACH ROW EXECUTE FUNCTION brain.require_structured_record_citation();
CREATE TRIGGER events_require_citation        BEFORE INSERT ON brain.events
  FOR EACH ROW EXECUTE FUNCTION brain.require_structured_record_citation();
CREATE TRIGGER entity_merges_require_citation BEFORE INSERT ON brain.entity_merges
  FOR EACH ROW EXECUTE FUNCTION brain.require_structured_record_citation();
```

Why this is correct and complete:

- **Closed against every ordinary DML writer, including the owner.** A row-level trigger fires for the table owner and for SECURITY DEFINER brokers alike. There is no admin-only side door because there is no projection table to seed. (`session_replication_role = 'replica'` bypasses it — but disables declarative FKs identically, so the trigger is not weaker than the FK-to-projection it replaces. The guarantee covers DML; owner-controlled DDL can dismantle any database invariant, declarative or trigger-based, and no design closes that.)
- **No ordering window.** Nothing is derived, so nothing needs backfilling and no maintenance trigger races a concurrent `ingest`.
- **Kind is stable once checked.** `logical_sources.source_kind` is immutable (`brain.guard_logical_source_update()`, `011:335`, wired `011:436-438`) and `source_versions` rows are immutable (`011:448-454`), so a citation that passes at insert time can never later become invalid. This is exactly why the separate `source_kind` immutability trigger Revision 2 proposed is **dropped**.
- **Insert-only, so legacy `UPDATE`s pass (round-2 B2).** `brain.refresh_canonical`'s `UPDATE brain.entities … SET canonical_id` (`008:71-73`) touches legacy rows whose `source_version_id` is NULL on every merge of an upgraded Brain. A `BEFORE INSERT` trigger does not fire on `UPDATE`; a `NOT VALID` CHECK would have. Proven by **P12**.
- **Three stable custom SQLSTATEs discriminate the failure modes (round-3 blocker):** `RBC01` (citation missing), `RBC02` (cited version does not exist), `RBC03` (version exists but is not structured-record) — the same discipline as `013`'s `RBE01–RBE04` broker codes. The TypeScript layer maps them onto `BRAIN_CITATION_INVALID` with `reason: 'missing' | 'unknown-version' | 'not-structured-record'` without string-matching. The trigger decides existence *itself* (single `SELECT … INTO`, `NOT FOUND` ⇒ `RBC02`) rather than letting an absent version fall through to the FK — under READ COMMITTED a concurrently committed wrong-kind version could otherwise arrive between the trigger's check and the FK's and evade the kind check. The FK stays as belt-and-braces referential permanence, not as a diagnostic path.
- The `sha256:` id in the message is legal output under §10.

### 7.5 Rotation (AC-6) — three honest modes (round-2 B3)

`spec/CONTEXT.md:108-109` is a **closed** verb list with no `rotate`, so rotation is an explicit, never-implicit `init` flag (owner decision D3):

```
roster brain init --rotate-runtime-credential [--recovery-provider-reset | --recovery-admin] [--json]
```

**The flag makes `init` do only the rotation.** It runs no migrations, creates no role, and re-applies no grants. That guarantees AC-6's "cannot be triggered as an init side effect" in both directions — a normal `init` never rotates, and a rotation never bootstraps. Without the flag, `init` behaves exactly as today: `ensureWorkspaceRuntimeRole` (`roles.ts:204-247`) sets a password only on `CREATE ROLE` (`:238-242`) and otherwise only re-applies grants (`:232-235`). ✔ AC-6.

#### 7.5.1 The staged credential

Roster never mints or stores credentials (`spec/CONTEXT.md` — "credentials remain ambient"; `test/static-boundaries.test.ts:364-374`). The new password arrives the same way every other credential does: **staged ambiently, in a distinct variable.**

```
ROSTER_BRAIN_URL       = the current, live credential  (unchanged meaning)
ROSTER_BRAIN_URL_NEXT  = the STAGED next credential    (new; read only by this flag)
ROSTER_BRAIN_ADMIN_URL = admin (only --recovery-admin reads it for rotation)
```

The operator's secret manager (Infisical, a workload identity, `env -i`, anything) injects the staged value; Roster makes it authoritative in PostgreSQL and tells the operator to promote it. **Roster never writes the operator's store** — AC-6's "updates the operator-selected credential mechanism" is satisfied by making the operator's chosen new value the live database password, which is the only part Roster can own without becoming a secret store.

**Staged-credential validation (all three modes):**

1. protocol is `postgres:`/`postgresql:`;
2. username equals `deriveWorkspaceRuntimeRoleName(workspaceId, roleBase)` (`roles.ts:50-61`);
3. password matches `^[A-Za-z0-9_-]{43,128}$` — Roster's shipped runtime-credential contract (`connect.ts:104`); a staged value that fails this would be rejected by every other verb after promotion;
4. the **database name** equals `current_database()` read from the connection that will perform the `ALTER` (not parsed-vs-parsed — read from the live session, which is authoritative);
5. the password **differs** from the current one (modes 1 and 2; mode 3 knows no current password, so this rule is skipped and its absence is stated in the output as `unchanged_check: false`).

Failures raise `BRAIN_ROTATION_STAGED_CREDENTIAL_INVALID` with `details: { reason, role_name, secrets_path, staged_env: 'ROSTER_BRAIN_URL_NEXT' }` and never a value.

**Host and port are deliberately NOT compared** (round-2 B3). Justification, against the exact failure the rule must prevent ("rotation must not silently repoint the Brain"):

- Host equality is *unsound as a proxy*: a staged URL with the same host and a different database, or the same host and a different port, passes it while pointing elsewhere.
- Host equality is *incomplete*: managed Postgres routinely exposes one database through several hostnames (Neon's `-pooler` endpoint vs. the direct endpoint), so the rule rejects a correct deployment.
- The property that actually holds is already shipped and already relied on: `initializeCleanBrain` reads `bootstrap.databaseAuthorityId` from the **admin** connection and passes it to a `VerifiedBrainPool` built from a **different** connection string, the runtime URL (`connect.ts:171`, `:186`); `verifyBrainWorkspaceAuthority` then raises `BRAIN_DATABASE_AUTHORITY_MISMATCH` if the two are not the same database (`workspace-authority.ts:143-150`). The codebase therefore *already* proves "the admin URL and the runtime URL address the same database" by a stamped UUID, never by host string — and split pooler/direct endpoints are exactly that shipped case.
- Rotation reuses it: step 6 below reconnects with the staged URL and verifies against the `database_authority_id` read from the ALTER connection, plus workspace_id, namespace fingerprint and `migration_state`. A staged URL pointing at any other Brain fails **before the operator promotes it**.

#### 7.5.2 Mode 1 — `runtime-self` (default; AC-6's "previously authenticated runtime role")

1. Activation preflight, requirement `{ postgres: 'runtime', objectStorage: 'declared' }` (§6).
2. Resolve the **current** credential via the shipped `resolveRuntimeCredential` (`connect.ts:78-106`), strict.
3. Resolve and validate the **staged** credential (§7.5.1).
4. Open a `VerifiedBrainPool` on the current credential; read `current_database()`, `database_authority_id`, and `current_user`; assert `current_user = expectedRole` (the same probe `initializeCleanBrain` uses at `connect.ts:180-190`).
5. `ALTER ROLE CURRENT_USER PASSWORD '<staged>'`. **An ordinary PostgreSQL role may always change its own password** — no CREATEROLE, no ADMIN OPTION, no superuser, so this mode is unaffected by `stripCreatorGrant` (`roles.ts:169-180`) and works identically on Neon and stock PG16. The literal is escaped client-side exactly as `roles.ts:194` already does (`"'" + password.replace(/'/g, "''") + "'"`). The statement text is never logged and never included in an error message (§10, plus a `try/catch` that rethrows a redacted `BRAIN_ROTATION_FAILED`).
6. **Verify by reconnecting:** open a *new* `VerifiedBrainPool` with the staged connection string **and the `databaseAuthorityId` read in step 4**, then assert `current_user = expectedRole`. Success ⇒ the rotation is real, the staged value is live, and the staged URL addresses the same database.
7. Print the §8 receipt with `path: 'runtime-self'`, `rotated: true`, `verified: true` — **never** a password, URL, host, or fragment.
8. Human mode additionally prints: *"the staged credential is now live; promote it in your secret store at `<secrets_path>` and clear `ROSTER_BRAIN_URL_NEXT`."*

**If step 5 succeeds but step 6 fails**, the old password is already gone and there is nothing to roll back. Raise `BRAIN_ROTATION_VERIFICATION_FAILED` whose remedy states plainly that **the staged value is now the live credential and must be promoted immediately**. This is the honest, non-destructive failure mode; restoring the old password (which Roster does not possess) is impossible.

#### 7.5.3 Mode 2 — `provider-reset-adopt` (`--recovery-provider-reset`): the managed-platform recovery path

This is the mode that works when the runtime credential is **lost** on a platform where Roster's admin has no authority over the role — the Neon case, which `roles.ts:151-168` documents as a deliberate one-way door (*"only platform controls remain"*).

The operator first resets the role's password using the provider's own control (Neon console/API, RDS `ALTER ROLE` by a platform superuser, etc.). That yields an **interim** credential whose password shape is the provider's, not Roster's — Neon-issued passwords do not satisfy `^[A-Za-z0-9_-]{43,128}$` (`connect.ts:104`), so *every other Roster verb would reject it*. Mode 2 exists precisely to convert that interim credential into a contract-conforming one in a single step:

1. Activation preflight, requirement `{ postgres: 'runtime', objectStorage: 'declared' }`.
2. Resolve the **current** credential from `ROSTER_BRAIN_URL` with a **relaxed** rule: protocol must be `postgres:`/`postgresql:`, username must still equal the derived runtime role, password must be non-empty, ≤ 512 characters, and free of control characters and whitespace. Rule 3 of §7.5.1 (the base64url shape) is the **only** rule relaxed, and it is relaxed only here. A role-name mismatch still raises `BRAIN_RUNTIME_CREDENTIAL_INVALID` with `reason: 'role-mismatch'`.
3. Staged credential: validated **strictly** (§7.5.1) — the whole point is that the workspace ends the command with a conforming credential.
4.–8. Identical to mode 1, including `ALTER ROLE CURRENT_USER PASSWORD` (again: self-password-change, no admin authority needed) and the step-6 authority-id verification. `path: 'provider-reset-adopt'`.
9. Human mode prints a `⚠` line: *"recovery mode — the interim provider-issued credential has been replaced with the staged credential. Promote it and revoke the interim value at the provider."*

This satisfies AC-6's "reviewed provider-admin recovery path" honestly: the *provider* performs the privileged reset (the only actor that can), and Roster performs the review — role identity, workspace authority, namespace fingerprint, database authority, and credential-contract conformance — and leaves the Brain in a state every other verb accepts.

#### 7.5.4 Mode 3 — `admin-alter` (`--recovery-admin`): only where the admin still holds authority

Kept for self-hosted PostgreSQL, superuser admins, and stock PG16 deployments where `stripCreatorGrant`'s REVOKE silently no-ops (`roles.ts:151-168`) — a state the operator already knows about, because `init` prints `creatorGrantRemains` in both JSON (`commands/brain.ts:91`) and human output (`:100-105`).

1. Preflight requirement `{ postgres: 'admin', objectStorage: 'declared' }`; a missing admin credential raises `BRAIN_ADMIN_CREDENTIAL_INVALID` (§6.4). `ROSTER_BRAIN_URL` is **not** required.
2. On a `VerifiedBrainPool('admin', …)`, assert the target role is the registered derived runtime role by reading `brain_meta.runtime_roles` (the source `registeredRuntimeRoles` uses, `roles.ts:85-90`) — never an arbitrary `--role` string.
3. **Capability probe, before any attempt:**

```sql
SELECT
  (SELECT r.rolsuper      FROM pg_roles r WHERE r.rolname = current_user) AS is_superuser,
  (SELECT r.rolcreaterole FROM pg_roles r WHERE r.rolname = current_user) AS can_create_role,
  EXISTS (SELECT 1 FROM pg_auth_members am
            JOIN pg_roles gr ON gr.oid = am.roleid
            JOIN pg_roles mr ON mr.oid = am.member
           WHERE gr.rolname = $1 AND mr.rolname = current_user AND am.admin_option) AS has_admin_option
```

   Authority = `is_superuser OR (can_create_role AND has_admin_option)` — the PG16 rule (*a CREATEROLE role may alter only roles it holds ADMIN OPTION on*), which `applyGrants` already encodes empirically at `roles.ts:320-323`: *"after stripCreatorGrant the connecting admin no longer holds ADMIN OPTION on the role, so this ALTER would fail on re-init."*
4. **If authority is absent, refuse without attempting the `ALTER`**: `BRAIN_ROTATION_ADMIN_AUTHORITY_UNAVAILABLE`, `details: { role_name, reason: 'no-admin-option' | 'no-createrole' }`, remedy: *"this platform revoked the admin's authority over the runtime role at initialization; reset the role with your provider's own control, then run `roster brain init --rotate-runtime-credential --recovery-provider-reset`."* Refusing rather than attempting keeps a raw `permission denied for role …` out of the output and keeps the failure mapped to a stable code.
   **Transiently re-granting membership WITH ADMIN OPTION is not an option** and is not attempted: `GRANT <role> TO <admin> WITH ADMIN OPTION` itself requires ADMIN OPTION on `<role>`, which is exactly what was revoked; PG16 implements creator authority *through* that auto-grant, and `roles.ts:159-161` records that no superuser exists on Neon to restore it.
5. If authority is present: `ALTER ROLE <derived-role> PASSWORD '<staged>'` on the admin connection, then the identical step-6 verification by connecting **as the runtime role** with the staged URL and the `database_authority_id` read from the admin connection. `path: 'admin-alter'`.

#### 7.5.5 Recording

**Rotation writes nothing to the database, by design.** Two of the three modes hold only the runtime credential, and recording from them would require granting the runtime role a write into `brain_meta` — which AC-2 forbids ("cannot change identity or provenance") and which `applyGrants` structurally prevents (`roles.ts:334-353` grants `brain_meta` SELECT on exactly two relations and nothing else). A ledger written by only one of three modes would be worse than none: an audit that silently omits the common path. The receipt is the command's structured output (§8) plus the exit code; the credential's own lifecycle is recorded where the credential lives — the operator's secret store, per `spec/CONTEXT.md`'s "credentials remain ambient". A rotation-history surface, if wanted, belongs to #366's v2 doctor and is recorded as a residual in §14.

**New codes:** `BRAIN_ROTATION_STAGED_CREDENTIAL_INVALID`, `BRAIN_ROTATION_ADMIN_AUTHORITY_UNAVAILABLE`, `BRAIN_ROTATION_VERIFICATION_FAILED`, `BRAIN_ROTATION_FAILED`.

Also fix the stale claim at `docs/API.md:432` ("prints the runtime connection string once") — false since #351; `executeBrainInit` (`commands/brain.ts:70-113`) prints only the role name and a verification line.

## 10. Privacy rules for command output

Adopt #382's report rule (`plans/phases.yaml:384`: "no credentials, secret values, company-content bodies, URLs with userinfo, complete absolute paths, or private workspace identifiers") as #383's output contract, plus the shipped comment at `commands/brain.ts:701-702`.

**Never printed, by any verb, in any mode:**
- connection strings or any fragment (host, port, user, password) — including the staged and interim rotation credentials;
- runtime role passwords (rotation prints `rotated: true` only);
- `AWS_ACCESS_KEY_ID` / `AWS_SECRET_ACCESS_KEY` / `AWS_SESSION_TOKEN`;
- the S3 **bucket name**, **endpoint**, **object key**, or **`s3://…` URI** — print `namespace_fingerprint` (`sha256:…`, `workspace-record.ts:359-364`) instead. This is what makes `fs.ts:28`'s `sourceUri` output illegal, and it resolves round-1's `object_key` borderline against printing (`object_key` embeds `root_prefix`);
- ingested bytes, extracted chunk text, `structured` extraction JSON, or the ingest manifest;

## 13. Risks and open questions

**R1 — migration numbering (HIGH, was the round-1 #1 blocker).** A merge that creates a gap corrupts `validateRecordedMigrations` for every Brain that applies the higher number first. *Mitigation:* the §3.1 merge-time rule, the mandatory pre-merge renumber step in §3.2, and the T11 contiguity guard that fails CI on any branch.

**R2 — broker rewrite of the semantic write path (HIGH).** `saveEntity` moves an upsert plus an N-row fact insert into PL/pgSQL. Risks: `ON CONFLICT (kind, slug) DO NOTHING` + re-SELECT semantics (`save.ts:34-47`) must be reproduced exactly, and `fact_ids` must be returned in field order for the shipped JSON. *Mitigation:* P9/P11 + the existing `brain-verbs` assertions; the broker is a mechanical translation with the dedup read left in TypeScript.

**R3 — `bin/roster.ts` and `brain/doctor.ts` conflict with #357 (MEDIUM, near-certain).** Mitigated by sequencing #383 PR A first.

**R4 — orphaned modules trip a future dead-code audit (LOW).** Eight `src/lib/brain/*.ts` modules plus `ensureRuntimeRole`/`buildRuntimeUrl` become unreachable from production. Intentional per AC-4 (#363 removes them). Document in the PR body so `/audit` does not "helpfully" delete them and break the `static-boundaries` allowlist and 22 test files.

**R5 — disabling `config` strands `embeddings.enabled` (LOW).** Acceptable: #370 shipped a provider-neutral path (`src/lib/brain/embedding-provider.ts`) whose adapter registry is deliberately empty (`EMBEDDING_ADAPTERS = Object.freeze({})` at `:31`), so no embedding provider is reachable today regardless. AC-8's "no API-key-only or named-provider dependencies" is *helped* by this.

**R6 — `fs` bucket migration (MEDIUM).** Repointing `fs` at the tracked namespace strands objects in a previously-configured `files.bucket`. `brain.files` stores `bucket` per row, so `fs get` refuses precisely (`BRAIN_FS_FOREIGN_BUCKET`) rather than reading a foreign bucket. Long-tail recovery is #384/#363's. Flag in release notes.

**R7 — `brain-export-import.test.ts` vs. the citation gate (MEDIUM).** `import.ts:213` inserts into dynamic table names; a restore must order lifecycle tables before `entities` (FK) and carry citations (trigger). Two resolutions in §11.4; decide during implementation.

**R8 — rotation's non-atomic window (MEDIUM, inherent).** Between `ALTER ROLE` and a successful reconnect, the old credential is dead and the new one is not yet promoted in the operator's store. There is no way to make this atomic without Roster holding the secret store, which the spec forbids. *Mitigation:* the staged-value design means the operator already possesses the new value before the command runs, and `BRAIN_ROTATION_VERIFICATION_FAILED` states plainly that the staged value is now live.

**R9 — activation matrix runtime (LOW).** T4 now spawns `bin/roster.js` 13 × 6 = 78 times plus the 3 × 4 rotation sub-matrix ≈ 90 spawns at ~150 ms each ≈ 14 s. Acceptable; if not, collapse the pure declaration/credential cases to in-process `runBrain` calls and keep one spawn per verb for the exit-code/stderr contract.

**R10 — templates are outside `write_globs` (LOW).** AC-8 names templates explicitly, so the criterion cannot be met without editing them. Justify in the PR body; propose a `write_globs` amendment to the owner alongside the AC-7 amendment.

**R11 — relaxed staged-host rule (LOW, new in Revision 3).** Dropping host/port equality (§7.5.1) means a staged URL for a *byte-identical clone* of the same Brain — same `database_authority_id`, same database name, same role, and a password that already authenticates there — would pass. That state is indistinguishable from "the same Brain" everywhere else in the codebase (`workspace-authority.ts:143-150` is the product's definition of database identity), and reaching it requires the operator to stage a URL for a clone whose credential already matches the one being set. Accepted; the alternative rule rejects every split pooler/direct deployment, which is a real and common configuration.

**R12 — self-password-change assumption (LOW, new in Revision 3).** Modes 1 and 2 rest on the PostgreSQL rule that an ordinary role may change its own password. This is true on stock PostgreSQL and on Neon, but a hardened platform could revoke it. *Mitigation:* P10(g) asserts it explicitly on CI, and the failure is already mapped — the `ALTER` is wrapped and rethrown as a redacted `BRAIN_ROTATION_FAILED` whose remedy names mode 3 and the provider control.

**R13 — trigger-based enforcement vs. a declarative constraint (LOW, new in Revision 3).** A reviewer may prefer a CHECK/FK to a trigger. The trigger is required (a CHECK cannot join, and a `NOT VALID` CHECK breaks legacy `UPDATE`s — round-2 B2), and against ordinary DML writers it is not weaker: the one DML-level bypass, `session_replication_role = 'replica'`, disables declarative FKs identically (owner-controlled DDL can dismantle either kind of invariant). #363 converts the NULL half to a validated `NOT NULL` once #384 backfills (§14).

## Summary (< 300 words)

**All 4 round-2 blockers verified against code; none disputed.** Corrections:

1. **B1 (projection not closed).** Both sub-parts confirmed — an admin can seed `structured_record_versions` directly, and the migration's only lock (`pg_advisory_lock` before `BEGIN`, `workspace-authority.ts:357-359`) serializes bootstraps, not a concurrent `ingest`, so backfill-then-trigger really does race. **Fix: delete the projection.** A single `BEFORE INSERT` trigger joins `source_versions → logical_sources` per row, refusing NULL and non-`structured-record` citations for **every** writer including the owner. 3. **B3 (recovery not viable).** Confirmed by the repo's own comments (`roles.ts:151-168`, `:320-323`). Re-granting ADMIN OPTION is impossible on Neon. 4. **B4 (no PUBLIC revoke).** Confirmed — every shipped migration revokes (`002:99`, `005:67`, `008:78/168`, `011:416-419`, `012:179-181`, `013:1127-1146`) and `applyGrants` (`roles.ts:287`) revokes only from the role.

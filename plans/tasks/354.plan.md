# Issue #354 — Validate real host-executed tool use

## Goal

Prove with one real Claude Code turn and one real Codex turn that a host can consume Roster's resolved Social Media Manager context plus the exact installed `exa:search` vendor instructions, derive request-specific filters, execute the native Exa tool, and return normalized provenance. The safe harness intentionally exposes only the required external tool, so it proves policy application and execution—not competitive tool selection. Roster remains a context validator/resolver; it never executes or routes a provider.

## Boundaries

- Use only the synthetic Roster-owned Social Manager fixture. Never access an adopter workspace, Brain, database, object store, or private business data.
- Use ambient logged-in host accounts and installed Exa plugin/OAuth state. Never inject model or Exa API keys.
- The live check is test-only and opt-in through `ROSTER_REAL_HOST_TOOL_USE=1`. It cannot run during ordinary tests, install, pack, smoke, or CI unless explicitly enabled.
- Exactly one Exa search call per host. A provider/auth/rate-limit failure is a sanitized non-certifying operational outcome, not a fallback or retry.
- Raw native traces and provider rows stay in bounded process memory, are reduced to closed hashes/counts, and are discarded. No transcript, query, URL, account/session/config value, plugin path, or provider response is committed.
- Claude Code and Codex remain the runtimes. This ticket adds no production source, executor, provider adapter, route/health/fallback layer, scheduler, run state, or approval authority.
- Claude Code Opus 5 independently reviews the plan and implementation because Codex is the primary development host.

No product architecture question remains. Missing host login, Exa plugin, OAuth, or native trace support is an operational blocker to report to the user rather than an invitation to enlarge Roster.

## Roster fixture contract

The golden test proves that the effective `social-search` definition contains:

- qualified function/agent/plan scope and business purpose;
- `skill_ref: exa:search` and only the relevant search/retrieval capability subset;
- canonical-public-URL, attributable-source, excluded-topic, profile/homepage, recency, and prior-presentation rules;
- canonical URL, author, publication/retrieval time, and relevance reason expectations;
- requested Brain reads/writes for prior opportunities and retrieval provenance;
- effects limited to external read and declared Brain intent; and
- exact plan-layer `approval: { requirement: human, guidance: ['obtain a human decision before any engagement'] }`, with the effective value and plan-layer field source asserted; this is advisory declaration only, and the already write-forbidden tool-use means the test never claims Roster enforces approval.

The resolved context must contain no credential, provider command syntax, direct MCP arguments, route, current/next step, health/fallback state, or raw Brain data.

## Non-self-fulfilling host input

1. Build a fresh temporary copy of the synthetic workspace and resolve its context through the shipped Roster surface used by both hosts.
2. Construct the host input from three separately hashed values:
   - the exact Roster-resolved context bytes;
   - a neutral synthetic request asking for at most three recent public reply opportunities; and
   - a small wrapper requiring the closed JSON output, no writes/engagement, and one external lookup at most.
3. The request and wrapper must not name Exa, reproduce `skill_ref`, repeat any business-filter sentence/code, or contain the host's derived query. A hermetic guard fails if business policy is duplicated outside the Roster context.
4. The output schema may request generic tool/provenance reporting fields, but cannot instruct the host which provider/tool to choose.

The falsifiable evidence is the derived query, applied policy codes, excluded rows, and normalized output fields: none are authored in the request, wrapper, or schema and all must agree with the Roster bundle. The exact-byte/substring guard cannot exclude every semantic paraphrase, and the receipt states that ceiling. Tool choice itself is not evidence because the safety boundary exposes only one external tool.

## Native host execution

Before the paid turn, each launcher performs a bounded probe and retains only the exact Exa projection:

- installed plugin name/version and skill revision;
- the exact native Exa server/tool identity returned by a model-free MCP `tools/list`/startup-schema probe; and
- executable/patch version, required help flags, logged-in host readiness, and separate Exa OAuth readiness.

The raw plugin catalog is never logged or retained. If the exact Exa tool identity cannot be derived independently of the model's final prose, certification fails closed.

The launch posture is deny-by-default before model execution:

- Validate the installed Exa plugin's public manifest and reviewed `skills/search/**` tree; refuse symlinks, special files, path escapes, manifest drift, or hash drift. Cap the projection at 64 files, 1 MiB total, 256 KiB per file, and depth 8. Fail if it declares hooks, commands, subagents, another skill, or more than the one Exa server.
- Create a minimal temporary Claude plugin projection containing only the validated manifest and `skills/search/**`. For Codex, inject the exact verified `SKILL.md` and required `references/searching.md` bytes as a separately delimited, hashed vendor-instruction block because disabling both Codex shell surfaces removes its ability to read the copied tree. Those bytes are execution input, not retained output.
- Parse the manifest URL, preserve its `client` parameter, set `tools=web_search_exa`, and build a temporary one-entry MCP configuration. A model-free MCP `tools/list`/startup-schema probe must return exactly one matching server/tool before either paid turn. This probe also proves that the projected server identity reuses ambient OAuth; report `EXA_MCP_UNAUTHENTICATED` separately from later `EXA_PROVIDER_FAILURE`. No token or credential is read or copied.
- Pin the certified host patch versions and assert every boundary flag through `--help` before spawning. Claude uses only project settings, the minimal plugin projection, `--strict-mcp-config`, no session persistence/Chrome/prompt suggestions, `--permission-mode dontAsk`, `--tools Skill,Read,mcp__<server>__web_search_exa`, `--allowedTools Skill(exa:search),Read(<projection>/skills/search/**),mcp__<server>__web_search_exa`, and denies `Edit,Write,NotebookEdit,WebFetch,WebSearch,Task,Agent,Bash`. Settings deny every other read and all hooks/customizations.
- Codex uses `--ignore-user-config --ignore-rules` while retaining ambient auth, the exact vendor-instruction block, and one explicit MCP entry. It enumerates exact disables including `shell_tool`, `unified_exec`, apps/plugins, browser/computer/native-search, file mutation, hooks, collaboration/multi-agent, and other external-tool features; uses approvals `never`, an ephemeral session, strict config, and a read-only sandbox. A model-free startup probe must show the actionable catalog is exactly `{web_search_exa}` or the live gate stops before the paid turn.
- Both launchers assert their configured server/tool allowlists have cardinality one. Native-trace rejection of unexpected actions is defense in depth, not the primary permission boundary.

Pin Claude to Opus 5/xhigh with `--max-budget-usd 5` and Codex to GPT-5.6 Sol/xhigh using the locally verified config value. Each host receives one turn, a four-minute wall-clock timeout, 4 MiB stdout and 1 MiB stderr caps, and process-group termination on timeout. Codex has no equivalent spend flag, so one turn plus timeout is its deliberate cost bound. Host/provider failure produces no automatic retry.

The native JSON streams are accepted only when:

- initialization identifies the probed host/tool surface;
- exactly one allowlisted Exa call has a unique bounded call ID and exactly one later successful result with the same ID;
- no shell, file change, browser, built-in web search, other MCP/plugin, subagent, or external-write action appears;
- Claude telemetry such as one bounded rate-limit status event, thinking-token frames, and the expected synthetic Skill expansion may appear but cannot count as action proof;
- current Codex lifecycle/reasoning/message frames may appear but cannot count as action proof;
- malformed, duplicate, unmatched, reordered, oversized, truncated/persisted-wrapper, or self-asserted calls/results fail; and
- provider failure is reported with a stable sanitized reason and does not produce a passing receipt.

The proof ceiling is explicit: certification proves a host-emitted native tool call/result lifecycle and correlated returned payload, not packet-level network capture.

## Result and provenance validation

The host returns a closed JSON object containing schema version, host, Roster target and semantic hash, skill revision, exact tool identity, bounded query/filter summary, applied policy codes, effects/approval summary, up to three provenance rows, omissions, and artifact digest.

Hermetic tests feed successful synthetic Exa payloads containing qualifying rows and decoys. They own exact filter semantics: exclude prohibited topics, profile/homepage URLs, unattributed rows, non-canonical URLs, and prior-presented URLs. The live pass checks only falsifiable structural claims against the correlated provider payload:

- the exact query is bounded, absent from the neutral request/wrapper, and hashed before disposal;
- each returned URL/author/publication field is an exact projection of the correlated Exa result;
- URLs are canonical HTTPS without userinfo or control characters;
- result count and vendor payload bytes stay below fixed limits; and
- retrieved time and canonical artifact SHA-256 are present.

Provider content is untrusted data and can never change instructions. A shortlisted value absent from the correlated result fails. Live validation never passes provider-derived text to `node:assert` or an exception message: it compares booleans/hashes and throws only a stable code plus a digest of private detail. Hermetic canaries prove receipt, thrown-error, and test-runner rendering contain no seeded query, URL, author, path, token, or result bytes.

## Receipt and change binding

The live test prints one closed receipt for the PR/Forge evidence, never a tracked file. It contains only schema versions, fixture/context/request/schema/support-file hashes, the canonical scoped-input tree SHA-256, sanitized host/plugin/tool revisions, per-host trace/query/filter/provenance/artifact hashes and counts, cross-host invariant digest, time, and receipt digest. It contains no raw query, URLs, rows, paths, account/session/config data, or host-home contribution names.

`computeCertificationInputDigest()` deterministically recomputes the scoped-input hash with `src/lib/vendor-skills/canonical-json.ts#canonicalJson`; hermetic tests permute key insertion order and require the same digest. The live command and PR evidence show that digest; any later input change requires a new live run. A redaction self-test serializes both receipts and failures and checks seeded secret/path/query/URL canaries are absent.

The receipt is intentionally untracked. Its proof ceiling is therefore explicit: native events and correlated payload establish the behavior during the observed run, while repository automation proves only the current scoped-input digest. The PR author human-attests that the pasted receipt came from that run; a stale or hand-edited receipt cannot be cryptographically excluded. This ticket does not add a durable certification/attestation subsystem or claim otherwise.

Temporary resources are created below one fresh OS temp root and removed in `finally`; signal/failure paths do not print its path. The disabled live test derives `node:test` `skip` from an exported false gate when `ROSTER_REAL_HOST_TOOL_USE` is unset. Hermetic/static checks prove the module has no spawn/socket work at import time and all launches live inside explicitly called functions.

## Goal

Prove that Claude Code and Codex can consume Roster-resolved tool-use guidance,
load the authored canonical `skill_ref`, derive request-specific inputs, and
invoke an external tool while Roster remains a transport-blind scaffolding and
context layer.

This is a small conformance task, not an integration for Exa or any other named
provider.

## Locked contracts

- Roster owns company-specific tool-use definitions: purpose, scope,
  capabilities, filters, rules, how-to guidance, expected output, Brain intent,
  effects, approval guidance, and evidence requirements.
- The opaque canonical `skill_ref` is the author-time provider/surface binding.
  Changing provider means changing that binding or authoring a sibling
  definition. Roster never chooses or falls back at runtime.
- The referenced vendor or workspace skill owns installation, authentication,
  API/CLI/MCP/browser/connector mechanics, syntax, compatibility, parsing, and
  generic best practices.
- Claude Code or Codex loads the skill, reasons, invokes the external tool, and
  handles operational failures. Roster validates and resolves guidance only.
- Add no Roster external-provider executor, router, health/fallback layer,
  credential injector, response parser, trace grammar, or attestation system.
- Roster Brain remains a separate first-party subsystem. This ticket adds no
  Brain code. Any Brain-backed fixture uses the complete PostgreSQL +
  S3-compatible contract; local-only tool guidance needs neither.
- Existing named examples may remain explicitly non-normative. Renaming the
  merged Social Manager/Exa fixtures or production vendor-skill subsystem is
  out of scope.

## Hermetic proof

For each fictional case:

1. Scaffold a temporary ordinary Roster workspace.
2. Author equivalent business intent with a distinct opaque `skill_ref`.
3. Materialize each reviewed fictional skill tree for both host layouts, then
   generate the real host activations and map using existing vendor-skill seams.
4. Keep CLI/stdio JSON-RPC syntax and authentication guidance only in
   `SKILL.md`; the adjacent `invoke.mjs` files are deterministic fictional
   executables and never touch network.
5. Validate the workspace and resolve tool use plus context through existing
   production APIs.
6. For each host projection, a bounded test-only reference host driver consumes
   the real resolved company guidance and host locator, derives JSON input from
   the synthetic request plus filters/rules/how/expected fields, and invokes
   the reviewed adjacent fixture executable with `process.execPath` and argv or
   JSON stdin, never a shell string.
7. Assert the reference driver for each Claude and Codex projection executes
   its host-specific locator, produces the same semantic result, and exposes
   only transient sanitized provenance: host, canonical `skill_ref`, tool-use
   fragment identity,
   locator assurance, and result count. Raw request, filters, results, command,
   local path, credential material, and private data are forbidden.
8. Assert existing unknown-field/schema rejection refuses attempted provider,
   surface, endpoint, command, and credential fields.
9. Recursively inspect resolved objects for forbidden auth/transport keys and
   run the existing authored-secret detector.

Extend only the smallest applicable seams in `test/workspace-tool-use.test.ts`,
`test/vendor-skill-map.test.ts`, `test/vendor-skill-ref.test.ts`, or the new
focused test. Do not extend the large host-learning certifier.

## Optional live smoke

`test/host-tool-proof-live.test.ts` contains one independently gated test per
host, following the small skip-by-default activation-test precedent.

- Gates: `ROSTER_CLAUDE_HOST_TOOL_PROOF=1` and
  `ROSTER_CODEX_HOST_TOOL_PROOF=1`.
- The public skill identity is supplied by
  `ROSTER_HOST_TOOL_PROOF_SKILL_REF`; no live provider name is committed. A host
  gate without this value fails once with an actionable message. Validate the
  value against the canonical `skill_ref` grammar before writing workspace
  bytes or launching a host.
- Default CI proves both tests stop before spawning a host or touching network.
  An always-run unit assertion injects an empty environment and proves the gate
  helper returns before any spawn/network helper is reached; it does not assert
  that the real process environment is always unset.
- The enabled test uses a temporary synthetic workspace, an explicitly selected
  public skill, harmless public/read-only input, and the normal logged-in host.
- Do not inject Anthropic, OpenAI, or provider API keys. Host and skill login,
  installation, and personal plugin state are acceptable opt-in dependencies.
- Construct the child environment from an explicit minimal allowlist that keeps
  host login/settings discovery plus the proof gates but strips Brain URLs,
  object-storage credentials, service endpoints, model/provider API keys, and
  unrelated tokens inherited from the parent shell. The always-run gate test
  seeds canary secrets in the parent environment and proves none reach spawn.
- Effective effects must allow external reads only. Launch each host with its
  native noninteractive restrictive permission/sandbox mode and the smallest
  exact tool allowlist needed by the selected read-only skill. If that envelope
  cannot enforce read-only execution, record the optional smoke as not
  performed; never relax it. No external mutation or private workspace/Brain
  access is permitted.
- Validate only a small bounded final JSON result; never parse native host event
  streams or provider-specific output.
- Bound duration/output and clean the temporary workspace in `finally`.
- If explicitly enabled but unavailable, fail once with an actionable message;
  do not retry, route, or fall back.

The optional smoke never gates merge and may be recorded as not performed. A
public PR note contains only host/Roster versions, public skill identity when
safe, guidance-resolved yes/no, loaded-without-Roster-mediation yes/no,
result/provenance counts, pass/fail, and confirmation that no provider API key
was injected. It contains no request/filter text, result content, path, session,
endpoint, local skill name/hash, or artifact digest.

# Issue #351 CI investigation

## Reproduction

1. Start a pristine PostgreSQL 16.14 database, matching the major and patch
   version used by CI.
2. Run `CREATE EXTENSION pg_trgm`.
3. Call `isPristineBrainDatabase`.
4. Observe `false` on the stock PostgreSQL catalog used by CI.

## Hypotheses tested

- An unapproved extension was installed: ruled out; only `plpgsql` and
  `pg_trgm` were present.
- `pg_trgm` created a relation, routine, operator, or collation without a direct
  extension dependency: ruled out by catalog inspection.
- PostgreSQL generated a type without a direct extension dependency: confirmed.

## Root cause

PostgreSQL automatically creates `public._gtrgm`, the array type for the
extension-owned `public.gtrgm` base type. `gtrgm` has a direct
`pg_depend.deptype = 'e'` dependency on `pg_trgm`, while `_gtrgm` has an internal
`deptype = 'i'` dependency on `gtrgm`. The pristine classifier recognized only
direct extension dependencies, so it rejected this system-generated array.

## Proposed fix

Treat a type as extension-generated only when both sides of PostgreSQL's
canonical array link agree (`array.typelem = element.oid` and
`element.typarray = array.oid`) and the element type is a direct member of an
approved extension. Keep rejecting every other non-system type. Extend the live
regression to prove that `pg_trgm` alone is pristine and a custom domain over
the extension-generated array is not.

## Verification

- The focused regression and all 20 workspace-authority tests pass on a local
  PostgreSQL 16.14 server, matching CI's server version.
- A `vector` extension catalog probe also remains pristine.
- Claude Opus 5 xhigh reviewed the repair at 8/10 PASS with no blockers. Its
  accepted improvement changed the negative fixture to a domain over
  `gtrgm[]`, directly exercising the reciprocal-array guard.

## 6. Token-reduction measurement (acceptance criterion 3; SPEC.md:830)

- **Unit:** the product's own estimator, `ceil(utf8_bytes / 4)` (`CONTEXT_ESTIMATOR`, workspace-context.ts:60,442–444). Stable because it is a pure byte function of checked-in UTF-8 content — no tokenizer version, no platform variance — and it is the unit the release criterion's budget block already reports; the README states this and notes the bundle side is measured over canonical-JSON-escaped content (escaping inflates the bundle, never the baseline — the gate is conservative).
- **Baseline (FROZEN):** `eager-baseline.json` = `{ schemaVersion, workspaceFixture, files: [{ path, sha256, bytes, tokens }], totals: { files, bytes, tokens: ceil(totalBytes/4) } }` over every checked-in instruction/definition file of the fixture workspace — `ROSTER.md`, `functions/**`, `tools/**` (playbooks included) — EXCLUDING `roster.yaml`/`roster.brain.yaml` and `_setup.ts` (registry config and harness code are not instruction bytes; excluding them shrinks the baseline, hardening the gate). `totals.tokens` uses ceil-of-sum (≤ sum-of-ceils — again conservative). **Freeze mechanism:** the hermetic suite recomputes the entire structure from the checked-in fixture and asserts deep-equality, reporting the recomputed value on mismatch (the retrieval-gold "verified, not trusted" discipline, `test/fixtures/retrieval-gold/README.md:242–246`) — so the baseline never drifts silently and an intentional fixture edit is a reviewed two-file change.
- **Bundle side, per task:** `measured_tokens = max(budget.total_tokens, ceil(stdout_utf8_bytes / 4))` — the reported figure cross-checked against the actual delivered bytes, gated on the larger.
- **Gate (per task, never aggregate):** for every gold task except L7/L8/L10 whose recall/exclusion/coverage gates passed, `measured_tokens ≤ 0.40 × baseline.totals.tokens`. Reduction is computed only after recall passes, so the "without required-context loss" clause is structural: a task that lost required context fails before its ratio is ever read. Brain-tier tasks gate against the SAME frozen baseline (an eager loader injects the authored tree; evidence is additional bundle weight it must still beat). The manifest records per-task `{ baseline_tokens, bundle_tokens, reduction }`.

## 7. Cross-host semantic equivalence (acceptance criterion 2; SPEC.md:829)

**Definition (in the README, verbatim):** Claude Code and Codex receive semantically equivalent bundles because they receive the IDENTICAL bundle — `roster context` has no host input and its output is byte-deterministic — with host variation confined to (i) activation framing outside the bundle and (ii) the per-host locator entries inside each `skill-ref` fragment, which are generated from one canonical `skill_ref` and must resolve to identical content. Three proofs:

1. **Structural (hermetic):** `parseContextArgs` admits no host-shaped argument (pinned by a test enumerating its flag set against a closed list); the bundle's only host-keyed position is `skill_refs[].content.hosts`; for every skill-ref fragment in every gold bundle, `hosts` has exactly the keys `{claude, codex}` and the two locators are deep-equal for `host-native` kind (identity + assurance) — the invariant a project-materialized skill would relax only to per-host reviewed `content_hash` equality of intent, stated in the README.
2. **Empirical (both tiers):** each gold task is invoked twice under host-shaped environment deltas (e.g. `CLAUDECODE=1, TZ=UTC, LANG=C` vs `CODEX_HOME=<tmp>, TZ=Asia/Tokyo, LANG=en_US.UTF-8`) — stdout byte-identical. Combined with the same-environment double-invocation determinism gate (#355's 204–209), this is "deterministic equivalent context selection across Claude Code and Codex" as an observed fact.
3. **Activation parity (hermetic):** `renderClaudeProjectInstructions('claude-project-instructions', a).body` equals `renderCodexProjectInstructions(a).body` after substituting the host display name (both are `renderHostBootstrapBody`, generated-artifacts.ts:617–627); `renderCodexRosterSkill` shares the same body; all route the host to the ONE generated `ROSTER.md` whose capability catalog declares `context-retrieval` `authority: 'roster'` (67–85) and whose trust guidance is the shared `CONTEXT_TRUST_GUIDANCE` table (130–141). So the instructions that CAUSE each host to request context are one contract with host-name framing.

**Explanation stability (criterion 2's second clause):** with `--explain`, every provenance entry carries a non-empty `explanation` and the set of (inclusion_reason → explanation) pairs observed across ALL tasks is closed and identical across double runs, across env-delta runs, and across tiers; every forbidden-entry exclusion surfaces through its declared closed surface (§5) with `reason` ∈ the exported closed vocabularies (`CONTEXT_EXCLUSION_REASONS`, `CONTEXT_RETRIEVAL_FILTER_REASONS` — imported from `src/lib/workspace-context.ts`, an unpinned import test files already use).

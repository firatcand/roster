# Issue #344 implementation plan — validate structured host-interpreted plans

## Ticket

- GitHub: `firatcand/roster#344`
- Forge task: `P1-T03`
- Branch: `feat/344`
- Type: foundation / public authored-plan schema

## Outcome

Turn a scaffolded plan from a loose YAML envelope into a bounded, versioned,
statically validated operating guide that Claude Code or Codex can interpret as
a whole. Roster will prove the plan's schema, ownership, references, artifact
declarations, and nested-plan graph before work begins, while remaining entirely
out of the execution path.

The host still chooses how to reason, carries outputs between steps, invokes its
own subagents and tools, applies retry/condition guidance, and waits for the
human in its native interface. This ticket adds no compiler, reducer, current
step, active-plan snapshot, transition protocol, runtime type gate, worker
queue, provider executor, scheduler, or approval authority.

## Questions asked and answers applied

The public schema forks were front-loaded during the Roster audit and issue
creation. The user approved these decisions before authorizing the roadmap loop:

1. **Who interprets and executes a plan?** The user answered that the host
   (Claude Code or Codex) interprets and executes it; Roster maintains and
   returns the complete plan and its guidelines. Therefore every step field in
   this ticket is inert authored guidance, never an executor opcode.
2. **How are Brain requirements represented?** The approved design uses a
   plan-local, named, credential-free selector catalog. Steps reference those
   names. Static validation does not contact Neon or require a live Brain
   binding; #346 later consumes the selector intent during bounded context
   resolution.
3. **How are tools represented?** A plan references a same-agent Roster
   `tool-use` definition describing the company's use case. Vendor skills remain
   authoritative for setup, authentication, syntax, parsing, and generic best
   practices; #347 owns the broader tool-use overlay contract. Roster does not
   run the provider.
4. **Who owns approvals?** An approval step is guidance for the host to stop and
   wait for the human. Roster neither grants approval nor advances the plan.
5. **What happens at first scaffold?** `roster scaffold plan` creates a useful
   but incomplete draft and succeeds atomically. Semantic `roster validate`
   rejects that draft until the expert has authored a complete plan.
6. **What identity vocabulary is canonical?** Local IDs are used only for
   unambiguous same-agent subagent, tool-use, artifact, and Brain-selector
   references. Cross-agent, nested-plan, and guideline references are fully
   qualified. Nested plan IDs use `function/agent#plan`.
7. **How strict is an incomplete scaffold?** The previously approved semantic
   failure is an error, not a warning. Every command that intentionally relies
   on `validateWorkspace` (`validate`, founder-skill synchronization, and doctor)
   continues to refuse an incomplete plan. The host must finish or remove the
   registered draft before those integrity-dependent operations; the smoke flow
   authors the plan before its first validation boundary. Generated-activation
   `roster update` remains independent and unchanged.
8. **Which fields are explicit?** A requested plan is a versioned record, so all
   top-level catalogs are required even when empty, and every declared input
   explicitly says whether it is required. This does not violate sparse
   initialization: no plan or plan directory exists until requested, but a plan
   that does exist has one deterministic shape.
9. **How is the plan schema versioned?** `schema_version: 2` is the shared v2
   workspace-record version, like every other authored record. Roster will use
   explicit whole-workspace migration if that contract changes rather than add
   a second independently drifting plan version.
10. **What does `tool_use` name?** It is permanently a local logical use-case
    handle, not a provider or path. This ticket resolves the definitions that
    are currently applicable to the owning agent/plan. #347 adds
    workspace/function/agent/plan overlays and most-specific-wins resolution
    without changing the authored field shape.
11. **What is a hidden expression?** It is an expression-bearing schema field or
    executor/control structure, not template-looking prose. Closed nested field
    allowlists reject `expression`, `template`, `command`, `args`, `script`,
    `shell`, `code`, `when`, `goto`, binding, transition, worker, and queue
    fields. Freeform instructions remain inert text that Roster never parses,
    substitutes, or executes, so content heuristics do not misclassify normal
    prose as code.
12. **Are explanatory bindings supported?** No. Impossible forward references
    are rejected by construction because `input_from`, `output_from`,
    `depends_on`, `next`, and every other step/binding grammar are unknown or
    forbidden fields. Array position is the only sequence.
13. **How does targeted validation resolve?** It preserves today's exact
    discovery grammar—qualified ID, local ID, or registered path—with no new
    `plan:`/`agent:`/`function:` CLI syntax. Zero matches still fail
    `PARENT_NOT_FOUND`; multiple matches still fail `IDENTITY_AMBIGUOUS`. After
    exactly one match, a plan selects itself, an agent/function selects its
    descendant plans, and another record kind selects no semantic plan root.
14. **Which tool scope shape is current?** The v2 record implemented by #342
    uses the singular `scope.plan` field. The nearby SPEC example is corrected
    from stale `scope.plans` syntax in this ticket. #347 may add broader overlay
    definitions, but it does not silently reinterpret the current scalar.
15. **What is the performance fixture?** The representative benchmark remains
    50 functions × 10 agents with roughly 500 fully authored plans. The fixture
    is not shrunk to make the gate green; both warmed discovery and static
    validation retain independent p95 assertions under 250 ms.

No unresolved architectural fork remains. This ticket ratifies and exports
named plan limits alongside the existing YAML limits: at most 256 steps/items
per plan collection, retry attempts are positive integers no larger than 256,
and authored cap values must be positive safe integers. Caps and retries remain
host guidance, not Roster-enforced runtime behavior. The plan-specific ceilings
are sub-limits beneath the inherited 10,000-node YAML bound; if the YAML bound
fires first, collection aborts with the existing YAML/resource diagnostic
rather than promising that every theoretical 256-item combination is reachable.

## Canonical schema

Add a dedicated structured-plan parser rather than turning the generic child
record parser into an executor-shaped abstraction. Plan collection uses a
bounded identity-envelope parser that requires `schema_version`, `id`, `agent`,
and `purpose` but deliberately leaves the remaining authored mapping for the
semantic parser. This keeps identity-valid incomplete or semantically malformed
drafts discoverable and lets validation capture one schema failure per plan
instead of aborting the registry at the first plan-shaped unknown field. The
scaffold renderer emits
this intentionally incomplete draft with every top-level catalog visible:

```yaml
schema_version: 2
id: opportunity-discovery
agent: gtm/social-manager
purpose: Produce a reviewed shortlist of relevant reply opportunities.
inputs: {}
brain_selectors: {}
guidelines: []
artifacts: {}
caps: {}
steps: []
completion:
  artifacts: []
  output_guidance: ""
  criteria: []
```

The draft is atomically created and discoverable, but it is not semantically
valid. A minimum complete plan keeps the same explicit shape and supplies at
least one step plus actionable completion guidance:

```yaml
schema_version: 2
id: opportunity-discovery
agent: gtm/social-manager
purpose: Produce a reviewed shortlist of relevant reply opportunities.
inputs: {}
brain_selectors: {}
guidelines: []
artifacts: {}
caps: {}
steps:
  - id: prepare
    kind: reasoning
    instruction: Derive request-specific filters from the human request.
completion:
  artifacts: []
  output_guidance: Return the filters with their rationale.
  criteria:
    - Every filter is traceable to the request.
```

- `inputs.<id>` is strict
  `{ description: string, required: boolean, shape?: string }`; `shape` is
  non-empty inert documentation, never a runtime type grammar.
- `brain_selectors.<id>` is strict
  `{ description: string, required: boolean }` and is resolved locally without
  Brain credentials.
- `guidelines` is a unique list of fully qualified registered guideline IDs.
- `artifacts.<id>` is strict
  `{ description: string, shape?: string }` with the same inert documentation
  semantics.
- `caps.<id>` is strict `{ maximum, guidance }`; `maximum` is a positive safe
  integer presented to the host.
- `steps` is the canonical sequence. It contains 1–256 steps with unique local
  IDs. Array position is the only ordering mechanism.
- `completion` is strict `{ artifacts, output_guidance, criteria }`; criteria
  must be non-empty, artifact references must be declared, and a valid plan must
  promise at least one final artifact or non-empty output guidance.

Every step requires `id`, `kind`, and non-empty `instruction`. Supported kinds
and their one required target are:

| Kind | Required target | Resolution |
|---|---|---|
| `reasoning` | none | host reasoning guidance |
| `subagent` | `subagent` | local same-agent registered subagent |
| `cross-agent` | `agent` | qualified registered agent |
| `nested-plan` | `plan` | qualified registered plan |
| `tool` | `tool_use` | local same-agent applicable tool-use definition |
| `approval` | `approval_guidance` | host waits for the human |
| `artifact` | `artifact` | local declared artifact |

Optional common step fields are strict:

- `context: { brain?: selector-id[], guidelines?: qualified-id[] }`;
- `expected: { artifacts: artifact-id[], output_guidance: string }`, with both
  fields required whenever `expected` is present;
- `condition_guidance: string`; and
- `retry_guidance: { max_attempts: integer, instruction: string }`.

Kind-specific target fields are mutually exclusive. Unknown fields fail at
every mapping depth. Executor-shaped fields such as `command`, `args`, `script`,
`shell`, `code`, `expression`, `template`, `when`, `goto`, `next`,
`depends_on`, `input_from`, `output_from`, `worker(s)`, `queue`, `transition`,
and `current_step` receive a dedicated forbidden-field diagnostic. This
diagnostic classification is not a security denylist: the closed allowlist is
what rejects every unrecognized field. Guidance strings are inert authored
prose and documentation shapes; Roster does not parse, interpolate, substitute,
type-check, or execute their content.

## Static reference and cycle validation

`validateWorkspace` will add one deterministic `structured-plans` check after
declared registry discovery. Validation first collects one complete, unfiltered,
already bounded and ownership-checked record snapshot, then chooses validation
roots separately. It never tries to resolve references from the target-filtered
discovery response. Immutable indexes are keyed by `(kind, qualified_id)`:

```text
validateWorkspace
  -> collect every declared record with exact stored content once
  -> select all plans, or the target plan/scope plus nested-plan closure
  -> parse each registered plan through the strict plan parser
  -> index agents, plans, subagents, guidelines, and tool-use definitions
  -> resolve local and qualified references
  -> build nested-plan adjacency list
  -> linear-time strongly connected component cycle check
  -> return checks + stable diagnostics; write nothing
```

With no target, every registered plan is validated. A qualified plan target
validates that plan and its transitive nested-plan closure; an exactly resolved
agent/function target validates descendant plans and their closures. Other
exact record targets still validate registry integrity but produce no plan
root. Exact matching retains the existing qualified-ID/local-ID/path rules and
hard not-found/ambiguity diagnostics. Unrelated incomplete drafts do not block
a targeted plan, while a malformed or cyclic reachable nested plan does. All
reference catalogs still come from the full snapshot, so targeted validation
cannot hide missing cross-record references.

The full snapshot is a private plan-resolution input only. The existing
target-selected record set still feeds `declared-registry.details.records` and
`portable-authored-paths`, preserving targeted JSON counts and preventing an
unrelated absolute-path diagnostic from leaking into `validate <target>`.
Bare validation supplies the full set to both paths as it does today.

Resolution rules:

- a plan's embedded `agent` continues to match its registered path owner;
- local subagent and tool-use references are qualified through the plan's
  owning agent;
- a plan-scoped tool-use definition applies only to that plan; agent-scoped
  definitions apply to all of that agent's plans;
- Brain context names must exist in the same plan's selector catalog;
- step guidelines must both exist in the workspace and be declared in the
  plan's top-level guideline list; canonical forms are
  `<function>/guidelines/<id>` and
  `<function>/<agent>/guidelines/<id>`;
- expected/completion/artifact-step references must exist in the plan's
  artifact catalog;
- cross-agent and nested-plan references must exactly match registered
  qualified identities; and
- all valid nested-plan edges are indexed in one workspace graph; workspace-wide
  validation reports every deterministic cycle, while targeted validation
  reports only cycles reachable from its selected roots.

Malformed YAML continues to use `YAML_INVALID`; duplicate IDs continue to use
`DUPLICATE_IDENTITY`. Add stable plan-specific codes:

- `PLAN_DRAFT_INCOMPLETE` only when an otherwise shape-valid plan has empty
  `steps`, empty `completion.criteria`, or completion promises neither a
  declared artifact nor non-empty `output_guidance`;
- `PLAN_SCHEMA_INVALID` for typed semantic shape/value violations;
- `PLAN_FIELD_FORBIDDEN` for executor, expression, binding, or control fields;
- `REFERENCE_NOT_FOUND` for absent registered or plan-local references;
- `REFERENCE_NOT_APPLICABLE` for a known tool-use outside the current plan
  scope; and
- `REFERENCE_CYCLE` for direct/transitive nested-plan cycles.

`src/lib/workspace-diagnostics.ts` makes one readonly code tuple the canonical
source, derives `WorkspaceDiagnosticCode` and the runtime membership Set from
that tuple, and tests every new code through `isWorkspaceFailure`; a code cannot
compile into the type while being omitted from runtime recognition.

Each diagnostic carries the authored plan path plus stable details such as
`source_plan`, `step_id`, `field_path`, `reference`, and `expected_kind` when
applicable. Cycle validation emits one deterministic representative for each
cyclic strongly connected component, including a self-edge, in `O(V+E)` time
rather than enumerating exponentially many simple cycles. Details include the
canonical closed path and edge step IDs. Every reported cycle is rotated to
begin with its lexicographically smallest qualified plan ID so workspace-wide
and targeted validation return byte-identical details. When multiple authored
steps create the same graph hop, the diagnostic uses the lexicographically
smallest `step_id`; the equality regression includes parallel edges so the rule
cannot pass accidentally.
The parser catches one schema/shape failure per plan and continues with the next
plan; structurally valid plans aggregate every reference failure and every
deterministic cycle representative. This gives useful workspace-wide
aggregation without replacing the existing exception-based YAML helpers with a
second validation framework. Diagnostics sort deterministically and never
expose machine-specific absolute paths.

If declared-registry collection fails, `structured-plans` is `fail` with
`{ blocked_by: "declared-registry", diagnostics: 0 }`; it never reports a pass
over unavailable/empty input. If no selected root contains plans, it passes with
an explicit zero-plan detail. `ValidateWorkspaceResult.ok` remains derived from
error diagnostics: a blocked structured-plan check relies on the accompanying
declared-registry diagnostic for exit 1, and no independent check may fail with
zero diagnostics.

`roster discover --full` already returns exact authored bytes and remains an
authoring/discovery surface, not a readiness claim: it can return an invalid
draft verbatim. `roster validate` is the explicit semantic gate before host
work. The pure typed validator/exported validated-plan resolver added here is
the mandatory dependency for #346: `roster context` must not return a selected
plan unless this gate succeeds. #349 then teaches Claude Code/Codex to call the
validated context lifecycle. A boundary test pins that discover returns an
invalid nested field unchanged while validate rejects it, preventing accidental
conflation. Missing Brain credentials do not affect local plan validation, and
no compiler surface is added.

## Seeded proof and edge cases

The positive integration fixture models `my-roster` Social Media Manager
discovery. It registers:

- `gtm/social-manager` and a distinct qualified collaborating agent;
- local subagent `researcher`;
- function/agent guideline references;
- inert Brain selectors for company positioning and successful replies;
- local tool-use guidance;
- a non-cyclic nested history-screen plan;
- declared search-brief/opportunity-shortlist artifacts; and
- all seven supported step kinds, including a human approval step.

It proves one complete plan validates without a Brain binding and that
`discover --full` returns its entire authored content. Negative coverage pins:

- incomplete scaffold draft;
- missing agent, subagent, nested plan, guideline, Brain selector, tool-use, and
  artifact references;
- both canonical function/agent guideline forms plus malformed shorthand;
- tool-use scoped to a different plan;
- duplicate/case-only step and catalog IDs;
- direct, two-plan, and transitive nested-plan cycles;
- wrong kind-specific targets and multiple targets;
- empty/non-string guidance, criteria, and descriptions;
- zero/fractional/unsafe retry and cap values;
- 257th step/catalog/reference item;
- YAML byte/node/scalar/depth/alias bounds inherited from #342, which abort the
  registry snapshot rather than pretending to aggregate semantic diagnostics;
- executor/expression/binding fields at every mapping depth while inert prose
  that merely resembles template syntax remains accepted;
- deterministic diagnostic order/path/cycle details, including byte-identical
  canonical cycles from targeted and workspace-wide validation;
- runtime recognition of every new diagnostic code; and
- exact target success, not-found, ambiguity, non-plan, and descendant-root
  behavior without new CLI grammar.

Schema aggregation coverage creates multiple malformed plans and proves one
stable first schema diagnostic per plan while valid plans still report every
missing reference. Targeted-validation coverage proves a qualified plan and
reachable closure succeed, reachable missing references/cycles fail, and an
unrelated incomplete draft is ignored. A registry-collection failure proves the
structured-plan check fails as blocked rather than passing over empty input.

The smoke proof separately confirms that a newly scaffolded draft is editable
and discoverable but does not pass semantic validation—or integrity-dependent
founder-skill synchronization/doctor work—until its complete authored plan
replaces the draft. Generated-activation update stays outside that semantic
gate.

The benchmark covers both discovery and the new static validation snapshot,
including the `#` nested-plan path through the full YAML parser.

The tests inspect data only. They add no `plan compile`, `next`, `submit`,
`approve`, cursor, transition, provider-route, scheduler, or worker-queue API.

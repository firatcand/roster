# Issue #347 implementation plan — scoped workspace tool-use guidance

## Ticket

- GitHub: `firatcand/roster#347`
- Forge task: `P1-T04`
- Branch: `feat/347`
- Type: integration / public authored tool-use schema

## Outcome

Give Claude Code and Codex one deterministic, credential-free company contract
for how a vendor skill is used in a specific workspace, function, agent, or
plan. Authors keep each definition beside the scope that owns it; Roster reads
the complete ancestry, validates that narrower definitions never relax safety,
and returns one flat effective definition with field-level provenance.

This ticket also gives `skill_ref` one stable `package:skill` identity and
generates portable per-host locator data. Global vendor skills remain installed
and resolved by Claude Code, Codex, or their plugin managers. Roster may verify
an explicitly project-materialized skill inside the workspace, but it never
scans host caches, installs a global plugin, injects credentials, or invokes the
provider.

The host still interprets the whole plan, derives request-specific filters,
loads the vendor skill, executes it, evaluates results, records evidence, and
waits for human decisions. Roster adds no provider runner/router, health check,
fallback engine, child process, MCP/API/browser transport, result gate, plan
reducer, scheduler, queue, or approval authority.

## Questions asked and answers applied

The implementation was held at the architecture boundary until the owner
answered the public forks. The safety/installation answer is recorded in Forge
question `019fbe0b-4a1d-742f-ae7c-aeb7b58f1cc2`; the layout answer was confirmed
directly in the resumed owner session.

1. **Where are scoped definitions authored?** The owner chose **1B**:
   workspace-, function-, agent-, and plan-owned files. The CLI composes them
   into one flat runtime object. Flatness is a retrieval/runtime property;
   hierarchical authorship preserves portable agents, local handles, small
   review surfaces, and exact content hashes.
2. **May a narrower definition relax broader safety?** The owner chose **2A**:
   no. Relaxation is a validation error with no authored override escape hatch.
   The existing SPEC sentence permitting a reported override is removed.
3. **Who installs global vendor skills?** The owner chose **3A**: the host or its
   plugin manager. Roster owns canonical references and portable locator data,
   not global installation or host-cache discovery. Existing explicitly
   project-materialized founder skills remain readable as project-local skills;
   this ticket does not expand their installer.
4. **Who interprets and executes tool use?** The previously ratified answer is
   Claude Code or Codex. Every authored field is inert company guidance.
5. **What remains authoritative for provider mechanics?** The vendor skill owns
   setup, authentication, syntax, parsing, compatibility, and generic best
   practices. Roster owns company purpose, applicable capability subset,
   filters, rules, expected results, Brain intent, approval guidance, and
   evidence requirements.
6. **Is workspace scope implicit?** No. Creation requires the explicit literal
   `--scope workspace`; a missing flag must never create the broadest policy.
7. **Are `why` and `purpose` separate?** No. `purpose` is canonical and the
   redundant `why` field is removed from the closed schema and examples.
8. **How are output, effects, and approval represented?** They remain separate
   closed objects because result guidance and the two safety dimensions compose
   independently.

No unresolved product fork remains. Real `my-roster` and `roster-lobu` audits
showed that agents are the portability unit, local tool handles repeat, and the
same browser/provider can have workspace permission, agent fallback guidance,
and plan prohibition. A second Claude Opus review reversed its initial
root-catalog recommendation and scored the scope-owned design at 9/10
confidence.

## Authored layout and identity

Extend the existing sparse registry symmetrically:

```text
roster.yaml                                      # tool_uses: []
tools/<tool-use-id>.yaml                         # workspace

<function-root>/function.yaml                    # tool_uses: []
<function-root>/tools/<tool-use-id>.yaml         # function

<function-root>/agents/<agent>/agent.yaml        # existing tool_uses: []
<function-root>/agents/<agent>/tools/<tool-use-id>.yaml

<function-root>/agents/<agent>/plans/<plan>.yaml
                                                  # tool_uses: []
<function-root>/agents/<agent>/plans/<plan>/tools/<tool-use-id>.yaml
```

`<function-root>` is the registered path from `roster.yaml`, not a derived
`functions/<id>` literal. `tools` becomes both a reserved workspace root and a
reserved logical function ID so the qualified identities below cannot collide.
Registry membership and physical path are authoritative. Each definition also carries
an exact structured scope that must match its owner:

```text
workspace  {}
function   { function }
agent      { function, agent }
plan       { function, agent, plan }
```

Qualified discovery identities are collision-free:

```text
tools/<id>
<function>/tools/<id>
<function>/<agent>/tools/<id>
<function>/<agent>#<plan>/tools/<id>
```

The same local use-case ID may exist once at every scope. Duplicate membership
or physical identity at one scope remains an error. Plans continue to use the
local logical handle shipped by #344:

```yaml
tool_use: social-opportunity-research
```

Provider-shaped handles such as `exa` or generic handles such as `search` are
not required. Different company uses of the same vendor skill should normally
use different purpose-based IDs.

Plan ownership deliberately keeps the existing authored file
`plans/<plan>.yaml` beside a registered companion directory `plans/<plan>/`.
The registry orphan checker must therefore treat the `plans` slot as a bounded
mixed slot: registered `<plan>.yaml` files may have a same-ID directory whose
only recognized child slot is `tools/`; any unmatched directory or surplus
entry remains `UNREGISTERED_RECORD`. This is an explicit `inspectSlot` change,
not directory inference or an alternate plan identity.

## Strict authored schema

Add `src/lib/workspace-tool-use.ts` rather than growing the shallow generic
child parser. Collection first parses a bounded identity envelope so malformed
or incomplete drafts remain discoverable. Semantic validation then applies a
closed schema recursively.

Canonical plan-scoped example:

```yaml
schema_version: 2
id: social-opportunity-research
scope:
  function: gtm
  agent: social-manager
  plan: opportunity-discovery
purpose: Find timely public posts matching company positioning.
skill_ref: exa:search

when:
  - discovering public reply opportunities
capabilities:
  - web-search
  - content-retrieval
filters:
  - exclude previously presented canonical URLs
  - exclude cryptocurrency topics
rules:
  - use first-party or attributable sources
  - never perform an external write
how:
  - search LinkedIn and ordinary public-web sources for the requested lookback
  - return evidence rather than drafting a reply
output_expectations:
  required:
    - canonical_url
    - author
    - published_at
    - relevance_reason
  guidance:
    - reject profile and company-homepage URLs as candidate post URLs
brain:
  read:
    - icp-and-messaging
    - previously-presented-opportunities
  write:
    - discovered-opportunity
    - retrieval-provenance
effects:
  allowed:
    - external-read
    - brain-read
    - brain-write
approval:
  requirement: none
  guidance: []
evidence:
  required:
    - source_url
    - retrieved_at
    - skill_revision
  guidance:
    - preserve the query and filter summary without secret material
```

Rules:

- `schema_version`, `id`, `scope`, `purpose`, and `skill_ref` are required on
  every definition. A narrow record remains independently understandable in
  discovery and must repeat the same canonical skill reference.
- Policy sections are optional overlays. When present, their nested shape is
  closed and collection fields are bounded, unique, and non-empty;
  omission means inherit. Additive constraint objects may use an empty list to
  state that the layer adds nothing, but no field has remove/reset semantics.
- IDs use the existing lowercase kebab-case grammar. Expected/evidence field
  names use bounded lowercase snake-case or dotted field paths.
- `effects.allowed` is a closed set of effect classes. The initial vocabulary
  covers local/external reads, local/external writes, irreversible writes, and
  explicit `brain-read` / `brain-write` classes. Project-owned Brain selectors
  remain separate intent, but a non-empty `brain.read` or `brain.write` is
  invalid unless its matching Brain effect is present in the resolved ceiling.
  Every normative example containing Brain selectors must declare the matching
  Brain effect classes; examples do not receive inferred permissions.
- `approval.requirement` is `none | human`. It tells the host whether it must
  stop for a person; Roster does not grant or observe the approval.
- Unknown fields fail at every mapping depth. Provider/auth/runtime fields such
  as `env`, `token`, `credentials`, `headers`, `endpoint`, `command`, `args`,
  `request`, `response_parser`, `route`, `health`, `fallback`, `retry`, and
  `timeout` have no valid place in this schema.
- Scaffold creates a bounded, discoverable draft with `skill_ref: ""`.
  `assertRenderedScaffold` uses the identity-envelope parser, not the strict
  semantic parser, so creation remains atomic and successful while an expert
  finishes the record through the host. Diagnostic meanings do not overlap:
  absent `skill_ref` is `SKILL_REF_MISSING`; a non-empty malformed value is
  `SKILL_REF_INVALID`; the renderer's explicit empty draft value is
  `TOOL_USE_DRAFT_INCOMPLETE`. Other optional policy sections are not invented
  merely to make scaffold pass.
- Move tool-use out of the generic `parseChildDefinition` union: its legacy
  required `agent` field is removed together with `why`, `ChildDefinition`
  narrows to subagents, and unreleased v2 fixtures move directly to this final
  scope-owned schema.

### Canonical `skill_ref`

`skill_ref` is exactly two bounded lowercase kebab-case components separated by
one colon: `<package>:<skill>`. Each component is 1–63 characters and the total
is at most 127 characters. Reject uppercase, whitespace, controls, `/`, `\\`,
`.`, `..`, URLs, percent encoding, query/fragment syntax, `@version`, extra
colons, environment syntax, aliases, and machine paths. Do not normalize an
invalid value. Reserve the `roster` package for explicitly shipped built-ins;
authored external definitions may not claim it.

Source, revision, content hash, installed host, and locator path are provenance
in the generated map, never part of this stable authored identity.

### Secret-free authoring

Closed objects are the primary defense. Add a shared authored-secret detector
that scans raw bounded YAML bytes before parsing, including comments, keys,
quoted scalars, and block strings. Extract only high-confidence, structurally
anchored detector classes into a leaf module: PEM private-key blocks, JWTs,
`Bearer` values containing a credential-shaped token of at least 20 characters,
`authorization:`/`authorization=` values containing a credential-shaped token
of at least 20 characters, and known vendor token prefixes such as `sk-`,
`sk-ant-`, `AKIA`, `gh[pousr]_`, `xox[baprs]-`, and `apify_api_`. The extracted
module tightens these patterns rather than copying `sanitize-index.ts`, because
redaction tolerates over-matching and hard rejection does not.
The two generic value detectors also require at least two character classes
among lowercase, uppercase, digit, and token punctuation, and explicitly reject
all-lowercase hyphenated prose as evidence; vendor-prefixed tokens and JWTs use
their dedicated detectors.

Do **not** promote redaction-grade generic `key=value`, URL-userinfo, entropy,
or DSN heuristics into hard rejection. They can legitimately appear in a
company prohibition/example, and 2A intentionally supplies no authored bypass.
#364 owns workspace-wide hardening; #347 applies the shared high-confidence
module to tool-use files only.

Diagnostics contain only path, field path when known, detector ID, byte offset,
and match length—never the matched value, a hash of the value, or the invalid raw
ref. A secret-derived hash would be a confirmation oracle. Sanitization is not
validation; a high-confidence match fails instead of being silently redacted.
The bounded detector runs before any tool-use bytes are returned as `content`
or converted into a `content_hash`; compact and `--full` discovery return only a
sanitized diagnostic record for a rejected file, never its bytes or a
secret-derived digest.

## Pure precedence resolver

Expose a filesystem-free resolver over one branded complete full-content
workspace snapshot:

```ts
declare const COMPLETE_WORKSPACE_SNAPSHOT: unique symbol;

type CompleteWorkspaceSnapshot = {
  readonly [COMPLETE_WORKSPACE_SNAPSHOT]: true;
  readonly records: readonly WorkspaceDiscoveryRecord[];
};

resolveToolUse(
  snapshot: CompleteWorkspaceSnapshot,
  context: { function?: string; agent?: string; plan?: string },
  localId: string,
): ToolUseResolution
```

Declare the brand, a module-private `WeakSet` of minted object identities, and an
`@internal` mint function in a filesystem-free leaf module. Minting copies and
recursively freezes the snapshot, record array, records, scope data, content,
and reference metadata. Only `workspace-registry.ts`, behind
its unfiltered full-content `collectWorkspaceRecords(root, true)` path, may
import the mint; the pure resolver imports the snapshot type plus an assertion
that checks `WeakSet` identity, frozen structure, exact-content completeness,
and content-record count before every fold. Add a static boundary test proving
that `workspace-registry.ts` is the sole mint importer. `filterWorkspaceRecords`,
compact discovery, arbitrary arrays, spread copies, and objects whose `records`
were filtered or mutated cannot pass. Fail those cases as
`TOOL_USE_SNAPSHOT_INCOMPLETE`. `plan` without `agent`, or `agent` without
`function`, is invalid; workspace-only resolution legitimately has no function.

Resolution:

1. Build the exact ancestry `workspace → function → agent → plan`.
2. Select at most one same-local-ID definition at each applicable scope.
3. Reject same-scope ambiguity before composition.
4. Compose broadest to narrowest using the field table below.
5. Return one flat effective definition, ordered contributing records,
   field-source metadata, deterministic semantic hash, and diagnostics.
   `effective.scope` is the normalized resolver context, derived rather than
   copied from a contributor; every contributor retains its authored owner scope
   only in provenance. `effective.schema_version` is the resolved v2 constant
   and `effective.id` is the requested local ID. The hash covers this complete
   flat definition, including derived scope and materialized defaults. It
   excludes paths, raw content hashes, contributors, field-source metadata,
   diagnostics, generator versions, and machine/host locators, so whitespace or
   provenance-only changes do not change semantic identity.
6. Perform no filesystem/environment/cache lookup and no provider work.

A chain may begin at any scope. A plan definition never applies to a sibling
plan, agent, or function.

| Field class | Fields | Composition |
|---|---|---|
| Path-owned identity | `schema_version`, `id`, `scope` | Never merged across contributors; each authored value must match its registry/path owner, then the effective identity is derived as specified above. |
| Chain invariant | `skill_ref` | Every applicable layer must match exactly or fail `SKILL_REF_CONFLICT`. |
| Most-specific replacement | `purpose` | Narrowest present value wins; omission inherits; provenance identifies the winner. |
| Stable additive guidance/constraints | `when`, `how`, `capabilities`, `filters`, `rules`, `output_expectations.*`, `approval.guidance`, `evidence.*` | Broad-to-narrow stable union with exact deduplication and per-entry provenance; no remove/reset syntax. Capabilities are advisory lowercase kebab-case IDs, not an authorization lattice. |
| Monotone narrowing sets | `effects.allowed` | Omission imposes no ceiling; after the first explicit set, a narrower explicit set must be a subset and becomes effective. Adding power fails. |
| Monotone stricter scalar | `approval.requirement` | `none → human` is allowed; `human → none` fails. |
| Additive Brain intent | `brain.read`, `brain.write` | Stable union. These are requested selectors, not authorization; Brain binding/scope enforces access independently. |
| Derived only | hashes, provenance, field sources, host locators | Never authored in a definition. |

`when` and `how` never replace broader prose, because a safety condition hidden
in procedural guidance must not disappear. Incompatible procedures are separate
purpose-based local IDs, not overlays of one ID. Broader safety therefore
survives through additive applicability/procedure/filter/rule/evidence guidance
and monotone effect/approval fields. There is no `override`, `clear`, negation,
or relaxation marker.

All invariant and monotonicity comparisons are ancestry-scoped. Two unrelated
agents may reuse one local ID with different `skill_ref` values because neither
record is an ancestor of the other. An omitted broader `effects` or `approval`
field imposes no hidden denial; the first narrower declaration establishes the
ceiling. If no applicable layer declares `approval.requirement`, the resolved
guidance defaults to `none` while the host still owns every actual gate.
Brain selectors remain requested intent rather than authorization, and Brain
binding/scope performs independent authorization. Cross-field validation still
requires `brain-read` or `brain-write` in the effective monotone effect set
before the corresponding selector list may be non-empty, so a narrower layer
cannot add a Brain operation forbidden by an explicit broader effect ceiling.
#346 must intersect requested selectors with the independently loaded workspace
binding and read/write scope; unauthorized selectors are excluded or fail
explicitly. Tool-use files cannot author Brain bindings, grants, credentials, or
authorization overrides.

## Full-snapshot validation and plan integration

Add a deterministic `tool-use-lattice` validation check after declared registry
integrity and before `structured-plans`:

```text
collect one complete bounded snapshot with exact content
  → parse every tool-use envelope and strict definition
  → verify raw-secret freedom and scope/path ownership
  → build a complete scope/local-ID index
  → validate every possible ancestry and safety fold
  → validate/regenerate the vendor-skill map expectation
  → let structured-plan validation resolve each local tool reference
```

Targeted validation continues to select reporting roots separately from the
complete reference catalog. An unrelated unfinished draft may stay outside a
targeted plan's readiness diagnostics, but global integrity failures—secret
material, duplicate identity, unsafe path, or precedence ambiguity—cannot be
hidden by targeting.

Replace #344's single agent-qualified tool map. For every `kind: tool` step,
resolve the local handle against the source plan's exact scope. Emit
`REFERENCE_NOT_FOUND` when no ancestor definition exists and
`REFERENCE_NOT_APPLICABLE` when only sibling/descendant definitions exist.
Nested plans resolve their own tool references against their own scope. The
complete structured plan remains unchanged; Roster never selects a current
step or executes it.

Stable tool diagnostics include:

- `TOOL_USE_DRAFT_INCOMPLETE`
- `TOOL_USE_SCHEMA_INVALID`
- `TOOL_USE_SNAPSHOT_INCOMPLETE`
- `TOOL_USE_PRECEDENCE_AMBIGUOUS`
- `TOOL_USE_POLICY_RELAXATION`
- `SKILL_REF_MISSING`
- `SKILL_REF_INVALID`
- `SKILL_REF_CONFLICT`
- `SKILL_REF_UNMAPPED`
- `SKILL_REF_DRIFTED`
- `SECRET_MATERIAL_FORBIDDEN`

Reuse existing `UNKNOWN_FIELD`, `IDENTITY_PATH_MISMATCH`,
`DUPLICATE_IDENTITY`, `REFERENCE_NOT_FOUND`, `REFERENCE_NOT_APPLICABLE`, and
bounded YAML/path/symlink codes where they already express the failure.
Diagnostics are sorted deterministically and name both ancestor/descendant
paths for a failed safety comparison.

## Portable vendor-skill map

Generate `.roster/vendor-skill-map.json` from the distinct valid `skill_ref`
values in the complete authored snapshot. Sort refs and host keys lexically and
use canonical JSON plus a self-hash. Because this artifact is derived from
authored records rather than manifest metadata alone, do **not** add it to
`CANONICAL_GENERATED_PATHS` or weaken the existing metadata-only renderer
invariant. Give it a dedicated generator and `vendor-skill-map` validation/drift
check; #365 can later consolidate generated-artifact drift surfaces.

Each ref contains per-host locator data:

```json
{
  "schema_version": 1,
  "generator": "@firatcand/roster",
  "generator_version": "<package version>",
  "skills": [
    {
      "skill_ref": "exa:search",
      "hosts": {
        "claude": {
          "kind": "host-native",
          "identity": "exa:search",
          "assurance": "host-resolved"
        },
        "codex": {
          "kind": "host-native",
          "identity": "exa:search",
          "assurance": "host-resolved"
        }
      }
    }
  ],
  "map_hash": "sha256:<canonical payload without map_hash>"
}
```

Locator union:

- `host-native`: opaque exact identity plus `host-resolved` assurance. Roster
  validates syntax/mapping presence only. It never claims the skill is
  installed and never inspects `~/.claude`, `~/.codex`, PATH, plugin databases,
  caches, or MCP inventories. Live capability reporting belongs to #349.
- `workspace-relative`: POSIX path confined to an allowed project skill root,
  independently derived per-host content hash, source/revision metadata, and
  `verified` assurance.

There is one explicit join key for project-materialized skills. Add optional
`skill_ref` to each `founder-skills.yaml` skill entry and propagate it unchanged
into the corresponding lock entry. Existing entries without it retain current
sync behavior but cannot satisfy a workspace-relative tool mapping. A referenced
project skill requires exactly one reviewed manifest/lock entry whose explicit
`skill_ref` matches; missing or duplicate joins fail `SKILL_REF_UNMAPPED`. The
generator never derives a lock name or path by splitting the ref, and adding the
metadata does not install, remove, or otherwise change skill-sync behavior.

The discriminator is explicit and one-directional: the presence of exactly one
enabled-host founder-skill entry whose explicit `skill_ref` matches is the sole
trigger for a `workspace-relative` locator. No matching entry yields
`host-native`. A partial join—matched for one enabled host but not another—or a
duplicate match fails `SKILL_REF_UNMAPPED`; it never falls back to native. A
workspace with no `founder-skills.yaml` legitimately produces an all-native map.
"Enabled hosts" means only the committed `roster.yaml` hosts map. Extract the
current module-private `enabledV2Hosts` logic into one exported pure helper next
to the registry schema and reuse it from activation and map generation; never
use machine-local `detectTools()`. The lock must contain
the matching host target for every enabled host. A partial join diagnostic tells
the adopter to re-run `roster skills sync` in an environment that materializes
all committed enabled hosts, then commit the regenerated lock/map.

The existing lock's single `contentHash` is not treated as a per-host hash.
Generation derives each host hash from its actual allowed project target using
a new confined bounded tree walk: recurse with an explicit depth and total-entry
cap, enumerate every directory through `enumerateWorkspaceSlot`, reject symlink
or non-regular entries, and read files through `readWorkspaceFile` under a total
byte cap. Do not reuse `hashSkillDir`; its `statSync` walk follows symlinks and
is unbounded. Fail with existing `SYMLINK_COMPONENT`, `NOT_REGULAR_FILE`, or
`READ_LIMIT_EXCEEDED` diagnostics before reading outside the workspace.

Declared source/ref metadata is reported honestly. Only a full 40-hex commit
SHA or a `sha256:` digest is marked `revision_immutable: true`; tags, branches,
and every other ref—including the current default `main`—are preserved with
`revision_immutable: false`, never presented as a pin.

Before map generation, validate every serialized manifest/lock provenance field
through a bounded, closed, secret-free schema. Never copy arbitrary `source` or
`ref` text: canonicalize only the existing supported `github:owner/repo` source,
require a bounded safe Git-ref form, reject credentials/userinfo, URL query or
fragment material, environment syntax, controls, machine paths, and every
high-confidence token class, and require exact normalized manifest↔lock
agreement. Apply the same checks at the hand-editable lock read boundary.
Failure emits neither the value nor any derived hash and atomically leaves the
previous map untouched.

Never derive a path by splitting `skill_ref`. Explicit per-host entries prevent
package/name collisions and allow hosts to differ. In this phase, a global ref
defaults to the same exact canonical native identity for Claude and Codex; a
project-materialized ref must be present in reviewed lock metadata for every
enabled host. Missing, ambiguous, escaped, non-regular, or hash-drifted project
locators fail. Native locators remain truthfully advisory rather than falsely
verified. The identity-equals-`skill_ref` native alias is the explicit phase-1
rule and is pinned by tests; #349 must change it deliberately if a host requires
a different installed alias.

`roster update` deliberately gains the bounded second responsibility of
regenerating the map after authored definitions are complete. It preflights and
computes the expected map before any activation or map write. An incomplete
draft exits with the normal invalid-workspace `EXIT_ERROR`, performs no update
write, and reports `TOOL_USE_DRAFT_INCOMPLETE`; it is never skipped and scaffold
does not invent a locator. The final map write is atomic. `roster validate`
is read-only and compares the committed map against deterministic expected
bytes. Minimal #347-generated host guidance may say only: resolve the canonical
ref through this map, read a verified workspace-relative skill, or ask the host
to resolve a host-native identity. #349 owns the complete activation/lifecycle
prose, host-version fixtures, and supported/advisory/missing/drifted capability
states.

## Registry, scaffold, and discovery changes

- Add `tool_uses` to workspace, function, and structured-plan registry schemas
  and renderers; retain agent membership. Update all v2 fixtures directly. This
  is unreleased schema evolution, not a migration command or compatibility shim;
  #363 owns the one-way legacy workspace migrator.
- Remove the existing agent-slot pseudo-plan arm: an authored file under
  `<agent>/tools/` must have scope exactly `{function, agent}` and a `scope.plan`
  there fails `IDENTITY_PATH_MISMATCH`. Plan-owned tool use is valid only under
  `plans/<plan>/tools/`. This does not remove the singular `scope.plan` field
  from an actual plan-owned definition; it removes the old physical owner.
- Extend `childRecordPath`, `qualifiedRecordId`, traversal, membership lookup,
  orphan detection, overlap/reserved-path checks, and reference summaries for
  all four roots. Function paths use the registered function root. Plan-slot
  inspection accepts only the registered `<plan>.yaml` plus its same-ID bounded
  companion directory and inspects only that directory's `tools/` slot.
- Extend `roster scaffold tool-use` to accept exactly
  `--scope workspace|function:<id>|agent:<function/agent>|plan:<function/agent#plan>`.
  Child creation plus correct-parent membership uses the existing workspace
  lock, compare-and-swap, commit-parent-last, rollback, and comment-preserving
  YAML mutation. Omitted scope remains an argument error.
- Extend `ScopeKind`, `ParsedScope`, `parseScope`, `normalizeScopeAlias`,
  `assertScaffoldScope`, `requestedRecordScope`, `expectedQualifiedId`, and
  `scopeMatches` for the colon-free literal `workspace`. It is valid only as
  exactly `--scope workspace`; no `workspace:<id>` or omitted-scope alias exists.
  `discover --scope workspace` matches workspace-owned records only. Applicable
  ancestry is a resolver concern, not discovery's scope-filter semantics.
  `workspace-tool-use.ts` parses its own optional scope mapping and does not
  reuse the generic `parseScopeMapping`, which continues to require a function
  for the remaining agent-owned record kinds.
- Normal discovery continues to enumerate exact accepted authored records.
  `--full` returns exact stored bytes and hashes per scope only after the
  pre-exposure secret check; a rejected record contributes a sanitized
  diagnostic and no content/hash. Discovery does not invent virtual records that
  share one path. The pure resolver is consumed by plan validation
  here and by bounded context resolution in #346. Do not add a provider-shaped
  `roster tool run|route|health|resolve` command or pre-empt #346 with a second
  context API.

## Social Manager / Exa golden flow

gtm/social-manager#opportunity-discovery

functions/gtm/agents/social-manager/plans/opportunity-discovery/tools/
